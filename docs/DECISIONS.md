이 저장소는 패턴을 먼저 손으로 만들어보고 그다음 현업이 실제로 쓰는 기술로 갈아탑니다.
그 갈아타기마다 **면접에서 그대로 말할 수 있는 형태로** 기록을 남깁니다.

## 면접에서 통하는 답과 안 통하는 답

먼저 이것부터. 기술 선택 질문의 답은 **기술 이름이 아니라 문제**로 시작해야 합니다.

| ❌ 안 통함 | 왜 |
|---|---|
| "토스가 쓰니까요" | **회사 이름은 근거가 아닙니다.** 규모도 제약도 다릅니다 |
| "Redisson이 더 좋아서요" | 무엇이 어떻게 더 좋은지가 없습니다 |
| "성능이 좋아집니다" | 숫자가 없으면 안 한 것과 같습니다 |
| "요즘 다들 씁니다" | 유행은 근거가 아닙니다 |

**통하는 답의 뼈대는 다섯 개입니다.**

```
① 어떤 문제가 있었나     구체적인 증상. 가능하면 숫자
② 어떤 대안을 봤나       최소 둘. 하나만 보고 골랐으면 고른 게 아닙니다
③ 왜 이걸 골랐나         우리 제약(팀 규모, 인프라, 트래픽)에 비춰서
④ 무엇을 포기했나        ★ 면접관이 가장 파고드는 곳
⑤ 어떻게 확인했나        도입 전후를 무엇으로 쟀나
```

> **④가 핵심입니다.** 트레이드오프를 말하지 못하면 "장점만 읽고 도입했다"로 들립니다.
> 반대로 단점을 먼저 말하면 **그 기술을 실제로 써봤다는 신호**가 됩니다.

### 이 저장소만의 무기

대부분의 지원자는 "Redisson 써봤습니다"라고 말합니다. 이 저장소는 **직접 만들어보고 갈아탄
과정**이 있습니다. 그래서 이렇게 말할 수 있습니다.

> "분산 락을 `SET NX PX`와 Lua로 직접 구현했었습니다. 해제할 때 단순 `DEL`을 쓰면 TTL로 제 락이
> 풀린 뒤 남이 잡은 락을 지워버리는 문제가 있어서, 값이 제 토큰일 때만 지우도록 Lua로
> 원자성을 맞췄습니다. 그런데 watchdog이 없어서 임계 구역이 TTL을 넘기면 락이 풀린 채로
> 작업이 계속되는 한계가 있었고, 그 지점에서 Redisson으로 갈아탔습니다."

**"왜 직접 만들었다가 바꿨나"가 곧 답변입니다.** 갈아탈 때 자체 구현의 이유를 지우지 마세요 —
코드는 지우되 `PROGRESS.md`의 서술은 남깁니다. 대비가 이 저장소의 자산입니다.

## 교체 이력

### D-001 · `ddl-auto: update`를 Flyway로 (Phase 6)

**면접 한 줄**: "스키마를 `ddl-auto: update`로 만들고 있었는데, `Transfer.idempotencyKey`의
unique를 떼고 테스트했을 때 **컨테이너가 새로 떴기 때문에** 실패가 잡혔습니다. 기존 DB였다면
인덱스가 남아 통과했을 겁니다. **검증 결과가 DB 상태에 따라 달라진다**는 게 드러나서 Flyway로
옮겼습니다. 대신 스키마를 바꿀 때마다 마이그레이션 파일을 함께 써야 합니다."

**바꾼 것**: `ddl-auto: update` → `Flyway 12.4.0` + `ddl-auto: validate`  ·  **커밋**: `f0dcbb2`

#### ① 어떤 문제가 있었나

`ddl-auto: update`는 **더하기만 하고 빼지 않습니다.** 컬럼도 인덱스도 지우지 않습니다.
그래서 스키마가 **어느 DB에서 언제부터 떠 있었느냐**에 따라 달라집니다.

| 증상 | 무슨 일이 일어났나 |
|---|---|
| unique를 뗐는데 테스트가 red | 컨테이너가 새로 떠서 인덱스가 안 만들어졌다. **기존 DB였으면 green** |
| `notification_db`를 추가했는데 안 생김 | `01-databases.sql`은 **볼륨이 비었을 때만** 돈다 |

두 번째가 특히 나쁩니다. "스키마를 누가 만드나"의 답이 **앱, 초기화 스크립트, 사람 손** 셋으로
갈라져 있었고, 셋 다 "이미 있으면 안 한다"라서 **어긋난 상태를 아무도 못 봅니다.**

#### ② 자체 구현이 가르쳐준 것

`ddl-auto`가 만든 스키마를 실제로 뜯어보니, **이름이 전부 Hibernate의 것**이었습니다 —
`UKc662f7lm5ec167m89rp50kb1d` 같은. 인덱스를 지우려면 이 이름을 알아야 하는데,
엔티티 어디에도 적혀 있지 않습니다. **되돌릴 방법이 없는 변경을 계속 쌓고 있었던** 셈입니다.

#### ③ 어떤 대안을 봤나

| 후보 | 채택 안 한 이유 |
|---|---|
| **Flyway** | ← 채택. SQL 그대로 씀. Spring Boot 4.1이 `spring-boot-starter-flyway`로 기본 통합 |
| Liquibase | XML/YAML 추상화로 DB 이식성이 좋지만, **MySQL 하나로 갈 거라 그 이점을 못 씁니다** |
| 계속 `ddl-auto` | 운영에서 못 씁니다. 컨테이너 여럿이 뜨면 DDL이 서로 경합하기까지 합니다 |

#### ④ 왜 이걸 골랐나

혼자 하는 저장소라 **배우는 비용이 가장 싼 것**이 유리하고, Flyway는 파일 이름 규칙과
`flyway_schema_history` 테이블 하나가 전부입니다. 이식성은 애초에 필요가 없습니다.

#### ⑤ 무엇을 포기했나  ★

- **엔티티만 고치면 되던 게 두 곳이 됐습니다.** 컬럼 하나 추가에 SQL 파일이 따라옵니다.
- **`baseline-on-migrate: true`가 남습니다.** 이미 테이블이 있는데 이력이 없으면
  "지금 이게 V1이다"라고 **도장만 찍고 내용을 확인하지 않습니다.** 실제 스키마가 V1과 달라도
  통과합니다. 그래서 `ddl-auto: validate`를 짝으로 켜뒀습니다 — 엔티티와 실제 테이블이
  어긋나면 그쪽에서 기동이 멈춥니다. **한쪽만으로는 부족한 구성**입니다.
- **베이스라인이 예쁘지 않습니다.** `UKc662f7lm5ec167m89rp50kb1d`를 그대로 뒀습니다.
  여기서 이름을 고치면 **도장만 찍고 넘어가는 기존 DB**와 **V1을 실행하는 새 DB**의 스키마가
  갈라집니다. 고치려면 지금부터는 V2입니다.

#### ⑥ 어떻게 확인했나

**둘 다 확인해야 합니다** — 새 DB에서 V1이 맞게 만드는가, 기존 DB에서 안 깨지고 뜨는가.

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| Flyway가 진짜 도는가 | V1의 컬럼 이름 하나를 **일부러 틀리게** 하고 테스트 | notification 7개가 전부 `SchemaManagementException`으로 **red** |
| V1 == 엔티티 | 되돌린 뒤 다섯 서비스 테스트 | 전부 green (새 컨테이너 → V1 실행 → validate 통과) |
| 기존 DB에서 안 깨지나 | 데이터가 든 홈서버 DB에 배포 | 네 DB 전부 `<< Flyway Baseline >>` / `success=1`, **V1은 실행 안 됨** |
| 데이터가 남아 있나 | 재시작 후 행 수 | accounts 61 · transfers 2521 · notifications 5042 — 그대로 |

**일부러 깨보지 않았으면 아무것도 확인 못 했을 겁니다.** 테스트가 green인 것만으로는
"Flyway가 돌았다"가 아니라 "어쨌든 테이블이 있었다"까지밖에 말할 수 없습니다.

#### 겪은 것

- Boot 4.1은 `flyway-core`를 직접 넣지 않고 **`spring-boot-starter-flyway`**를 씁니다
  (→ flyway-core 12.4.0). MySQL은 **`flyway-mysql`이 따로** 있어야 방언을 인식합니다.
- **베이스라인은 설계하는 게 아니라 뜨는 것**입니다. `mysqldump --no-data`로 받아
  `AUTO_INCREMENT=N`(스키마가 아니라 데이터 상태)만 지웠습니다.
- 원장(ledger)은 MongoDB라 이 작업에서 빠집니다. 같은 문제(`MongoIndexInitializer`가
  기동할 때 인덱스를 만든다)가 남아 있고, **Mongock**으로 Phase 7에 옮깁니다.

### D-002 · 직접 만든 격벽·회로 차단기를 Resilience4j로 (Phase 6.5)

**면접 한 줄**: "느린 상대가 내부 송금 p99를 3,071 → 58,790ms로 악화시키는 것을 재현한 뒤
`Semaphore` 격벽과 은행별 회로 차단기를 직접 만들었습니다. 필요한 계약을 테스트로 고정한 뒤
Resilience4j로 교체해 표준 상태 머신과 Micrometer 지표를 얻었습니다. 대신 라이브러리 동작이
블랙박스가 되고, 송금의 `sent` 경계를 지키기 위한 저수준 어댑터는 남습니다."

**바꾼 것**: 직접 만든 `Semaphore` + CLOSED/OPEN/HALF_OPEN 상태 머신 →
`Resilience4j 2.4.0` Bulkhead/CircuitBreaker/Micrometer  ·  **커밋**: `ccb3175`

#### ① 어떤 문제가 있었나

상대 은행이 2초 느려지자 아무 관계 없는 내부 송금 종결 p99가 **3,071 → 58,790ms**,
종결 성공률이 **1.00 → 0.53**으로 떨어졌습니다. 외부 6건/s × 2초 = 12 스레드-초/초인데
리스너 스레드는 6개라 외부 호출만으로 전부 점유했기 때문입니다.

리스너 분리·격벽·회로 차단기로 장애 전파는 막았지만 최종 코드가 직접 만든 동시성·상태 머신과
자체 지표에 기대고 있었습니다. 상태 전이 경합, HALF_OPEN 허가 반환, 지표 누락을 앞으로도 우리가
검증하고 유지해야 하는 형태였습니다.

#### ② 자체 구현이 가르쳐준 것

- **격벽 거절은 실패가 아니라 미전송입니다.** 기다리면 스레드를 지킨다는 목적이 사라지므로
  정원이 차면 즉시 거절하고 `sent=false`로 남겨야 합니다.
- **회로는 은행별이어야 합니다.** KB 장애가 정상인 SH 송금까지 막으면 장애 격리가 아닙니다.
- **POST와 GET의 목적이 다릅니다.** 새 입금 POST는 차단하지만, 이미 보낸 돈을 확인하는 GET은
  회로를 우회해야 `CREDIT_UNKNOWN`을 해소할 수 있습니다.
- `sent=true`는 회로 허가 뒤, HTTP 직전에 영속화해야 합니다. 더 빠르면 안 보낸 돈을 보냈다고
  기록하고, 더 늦으면 응답 대기 중 프로세스가 죽을 때 이중 전송할 수 있습니다.

이 계약을 먼저 알아냈기 때문에 라이브러리의 기본 데코레이터를 그대로 붙이지 않고,
어디서 허가를 얻고 반환해야 하는지 결정할 수 있었습니다.

#### ③ 어떤 대안을 봤나

| 후보 | 판단 |
|---|---|
| **Resilience4j 코어 모듈** | ← 채택. 필요한 패턴만 골라 쓰고, 은행별 registry와 [표준 Micrometer 지표](https://resilience4j.readme.io/docs/micrometer)를 제공 |
| Spring Cloud CircuitBreaker | 구현체 교체 추상화가 장점이지만 구현체를 바꿀 계획이 없고, `sent` 경계에 필요한 저수준 허가 제어가 가려짐 |
| 직접 구현 유지 | 도메인 계약은 가장 잘 보이지만 상태 머신·동시성·지표의 장기 유지 책임이 계속 우리에게 남음 |
| Resilience4j Spring Boot 스타터 | Spring Boot 4 지원이 아직 명확하지 않고 AOP 자동 설정이 필요 없음. 코어 세 모듈만 직접 조립 |

Resilience4j는 semaphore 방식과 thread-pool 방식을 모두 제공하지만, 이미 Kafka 리스너 풀을
분리했습니다. 별도 실행기와 큐를 하나 더 만드는 thread-pool bulkhead 대신 호출 스레드 수만
제한하는 [semaphore bulkhead](https://resilience4j.readme.io/docs/bulkhead)를 골랐습니다.

#### ④ 왜 이걸 골랐나

필요한 것은 재시도나 타임리미터 묶음이 아니라 **격벽과 회로 차단기 두 개**입니다.
Resilience4j는 모듈 단위라 필요한 것만 넣을 수 있고, `CircuitBreakerRegistry`로 은행별 회로를
동적으로 만들며, Micrometer registry에 새 회로도 자동 등록합니다.

직접 구현의 "5회 연속 실패"는 count-based window 5 + minimum calls 5 + failure rate 100%로
옮겼습니다. 최근 5건에 성공이 하나라도 있으면 100%가 아니므로 열리지 않고, 그 성공이 window에서
밀려난 다섯 번째 연속 실패에서 열립니다. OPEN 30초와 HALF_OPEN 한 건도 설정으로 그대로 보입니다.

버전은 당시 최신 안정 릴리스인 [2.4.0](https://github.com/resilience4j/resilience4j/releases/tag/v2.4.0)을
명시했습니다. Spring Boot BOM이 관리하지 않아 세 모듈의 버전을 함께 고정했습니다.

#### ⑤ 무엇을 포기했나  ★

- 직접 구현보다 **내부 상태 전이가 블랙박스**입니다. 설정 조합이 곧 동작이라,
  `slidingWindowSize`와 `failureRateThreshold`의 관계를 모르면 "연속 실패"가 조용히 바뀝니다.
- `sent` 영속화가 회로 허가와 HTTP 사이에 있어야 하므로 **저수준 permission API 어댑터는
  남습니다.** 애너테이션 한 줄짜리 구성은 포기했습니다.
- 의존성 세 개와 버전 관리가 생겼습니다. 특히 Boot 4용 스타터 자동 설정을 쓰지 않아 registry와
  Micrometer 바인딩도 코드에서 직접 합니다.
- 지표 이름이 자체 `remittance.external.*`에서 `resilience4j.*`로 바뀌었습니다. 기존 대시보드가
  있었다면 함께 마이그레이션해야 합니다(현재는 Phase 9 대시보드 전이라 비용이 작습니다).
- 회로 이름에 은행 코드가 들어가므로 은행 코드가 무제한이면 시계열 cardinality가 늘어납니다.
  지금은 설정에 등록된 유한한 은행만 호출할 수 있다는 전제가 있습니다.

#### ⑥ 어떻게 확인했나

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| 격벽 계약 | 정원 초과 동시 호출, 예외 후 허가 반환 | 즉시 `BulkheadFullException`, 다음 호출 정상 |
| 회로 계약 | 실패·성공·은행 격리·가상 시간·동시 HALF_OPEN 시험 | 5회 연속 실패, 30초 OPEN, 시험 한 건 유지 |
| 송금 경계 | 10건 연속 타임아웃 통합 테스트 | HTTP 5회, `sent=true` 5건, 미전송 5건 |
| 테스트 유효성 | 최초 전송 경로에서 회로를 잠시 우회 | `TooManyActualInvocations`로 red, 원복 후 green |
| 관측 | 표준 Micrometer meter 이름·태그 검증 | 회로 거절, 상태, 격벽 정원·남은 허가 노출 |
| 전체 회귀 | `./gradlew test` | **532건 green**, 2분 58초 |

성능은 아직 비교하지 않았습니다. 다음 Step에서 직접 구현 때와 같은 홈서버 장애 시나리오로
재측정하기 전까지 **"Resilience4j가 더 빠르다"고 말하지 않습니다.**

#### 겪은 것

- 테스트용 시계 생성자를 추가하자 Spring이 생성자를 고르지 못해 기본 생성자를 찾았습니다.
  운영 생성자를 `@Autowired`로 명시했습니다.
- Resilience4j OPEN 상태는 `Clock`으로 종료 시각을 계산합니다. NTP 같은 벽시계 보정으로
  30초가 흔들리지 않도록 기동 시각에 `System.nanoTime()` 경과량을 더하는 단조 시계를 넣었습니다.
- 대기시간 경계는 정확히 같은 시각이 아니라 **지난 뒤** 허용됐습니다. 가상 시간을 1ms 더
  전진시켜 실제 OPEN → HALF_OPEN 전이를 sleep 없이 검증했습니다.

## 켜지 않기로 한 것

**안 켜는 것도 결정입니다.** 라이브러리를 붙이면 설정이 딸려 오는데, 그중에는 켜는 순간
**시스템의 성격이 바뀌는 것**이 있습니다. 안 켠 이유를 안 적으면 나중에 "빠뜨린 것"과
구분되지 않고, 면접에서도 *"그건 왜 안 쓰셨어요?"*를 그대로 맞습니다.

번호는 위와 같은 줄에서 이어갑니다 — **결정이라는 점에서 다르지 않기 때문**입니다.

### D-003 · 느린 호출은 실패로 세지 않는다 (Phase 6.5)

**면접 한 줄**: "회로 차단기를 넣고 재보니 상대가 2초씩 끄는데도 회로가 안 열렸습니다.
read-timeout이 3초라 전부 '성공'이었기 때문입니다. Resilience4j에 느린 호출을 실패로 세는
설정이 있어서 켤 수 있었지만, 그러면 **얼마나 느리면 포기하나**를 정하는 값이 타임아웃과
둘이 됩니다. 기준을 하나로 두고 대신 그 하나(read-timeout)를 근거 있는 값으로 유지하기로
했습니다. 대가는 '느리지만 성공하는 상대'가 계속 우리 리스너를 붙든다는 것이고,
그건 전용 리스너와 격벽으로 이미 가둬뒀습니다."

**바꾸지 않은 것**: `slowCallDurationThreshold` · `slowCallRateThreshold`를 **켜지 않는다**
· **근거**: 2026-08-28 재측정 (`PROGRESS.md`)

#### ① 어떤 문제가 있었나

상대 은행을 **2초 지연**으로 두고 30 TPS를 흘렸더니 회로가 **내내 CLOSED**였습니다.

```
successful 586   failed 0   not_permitted 0      평균 2.03초 · 최대 2.15초
```

회로 차단기를 넣은 동기는 `PROGRESS.md`에 이렇게 적혀 있었습니다 —
*"상대가 감당 못 할 만큼 느리면 부르는 것을 멈추는 판단이 필요합니다."*
**그 문장대로면 이건 열렸어야 합니다.**

#### ② 다시 보니 문제 설정이 틀렸다

`read-timeout: 3s`는 이미 **"이만큼 느리면 포기한다"를 정해둔 값**입니다.
그러면 2초는 우리가 정한 선 **안**이므로 "감당 못 할 만큼 느린" 것이 아닙니다.
진짜로 감당 못 하면 3초를 넘고, 그건 타임아웃 → 실패 → **회로가 엽니다.**

**동기는 이미 충족돼 있었고, 기준이 `slowCallRateThreshold`가 아니라 타임아웃이었을 뿐입니다.**
"회로가 안 열린다"를 구멍으로 읽은 것이 잘못된 진단이었습니다.

#### ③ 어떤 대안을 봤나

| 후보 | 판단 |
|---|---|
| **지금대로 — 기준은 타임아웃 하나** | ← 채택. 아래 ④ |
| `slowCallRateThreshold`를 켠다 | "얼마나 느리면 포기하나"가 **두 값**이 된다. 둘이 어긋나면 "왜 안 열렸나"를 설명할 수 없다 |
| read-timeout을 줄인다 (예: 1초) | 회로는 더 잘 열리지만 **멀쩡히 처리 중인 요청을 자꾸 모르는 상태로 만든다.** 이 시스템에서 가장 비싼 상태를 늘리는 방향이다 |

#### ④ 왜 이걸 골랐나

**느리지만 성공하는 상대를 우리가 끊으면, 나가야 할 송금이 안 나갑니다.**
차단된 건은 미전송으로 쌓이고 상대는 멀쩡한데 우리 판단으로 돈이 멈춥니다.

그리고 그 피해는 이미 갇혀 있습니다 — 외부 전용 리스너로 내부 송금과 풀을 나눴고
(내부 p99 58,790 → 2,580ms), 격벽이 이 서비스 전체의 외부 동시성에 상한을 둡니다.
**느린 상대가 만드는 피해는 "우리가 느려지는 것"이 아니라 "외부가 밀리는 것"**이고,
그건 회로로 고칠 문제가 아니라 **용량 문제**입니다.

#### ⑤ 무엇을 포기했나 ★

- **느린 상대에게 계속 왕복 비용을 치릅니다.** 2초짜리 호출이 리스너 스레드 6개를
  계속 붙들고, 외부 송금은 밀립니다(재측정에서 외부 p99 54초).
- **"상대가 아픈 것"을 회로 상태로 못 봅니다.** 느림은 회로가 아니라 호출 지연
  히스토그램으로만 보입니다. 대시보드에서 둘을 같이 놓아야 합니다.
- 상대가 **3초 바로 아래에서 계속 노는** 최악의 경우, 우리는 영원히 안 끊습니다.
  이건 알고 남겨둔 구멍입니다 — 그때는 read-timeout 자체를 다시 재야 합니다.

#### ⑥ 어떻게 확인했나

| 무엇 | 결과 |
|---|---|
| 2초 지연 · 30 TPS | 회로 CLOSED · 실패 0 — **안 열리는 것이 맞다** |
| 같은 조건의 내부 송금 | p99 **2,580ms** · 성공률 **1.00** — 피해가 외부에 갇혀 있다 |
| 5xx 연속 실패 | 회로 OPEN · 차단 801건 · 전부 미전송 — **틀린 상대는 끊는다** |
| 상대 정상화 | 45초 뒤 CLOSED, 320건 전부 해소, 대사 0건 |

**"안 열렸다"와 "못 열린다"는 다릅니다.** 열려야 할 때(5xx) 여는 것을 같은 실행에서
확인했기 때문에, 안 여는 쪽을 결정으로 남길 수 있습니다.

### D-004 · 잔액은 분산 락 + 낙관적 락으로 지킨다 (비관적 락을 안 쓴 이유)

**면접 한 줄**: "잔액 갱신을 Redis 분산 락으로 직렬화하고 `@Version`을 한 겹 더 뒀습니다.
락이 **TTL 기반**이라 임계 구역이 TTL을 넘기면 풀린 채로 진행되는데, 그때 낙관적 락이 잡습니다.
비관적 락(`SELECT ... FOR UPDATE`)을 안 쓴 이유는 정합성이 아니라 **측정** 때문입니다 —
락 대기가 최대 51ms에 획득 실패 0건이라 경합이 낮았고, 진짜 경합 지점인 핫 계좌는
락을 바꾸는 대신 **잔액을 8조각으로 갈라** 25 → 70 TPS로 풀었습니다."

**결정**: 비관적 락으로 **바꾸지 않는다** · **근거**: Phase 5 baseline · Phase 6 핫 계좌 측정

#### ① 먼저 오해를 하나 걷어낸다 — 낙관적 락은 정합성을 떨어뜨리지 않는다

**둘 다 lost update를 막습니다.** 다른 것은 정합성이 아니라 **실패 모드**입니다.

| | 비관적 (`SELECT ... FOR UPDATE`) | 낙관적 (`@Version`) |
|---|---|---|
| 충돌하면 | **기다린다** | **실패하고 재시도한다** |
| 위험 | 락 대기 · 데드락 | 경합이 심하면 **재시도 폭풍**으로 처리량이 무너진다 |
| 유리한 조건 | 충돌이 잦을 때 | 충돌이 드물 때 |

그러니 물어야 할 것은 *"어느 쪽이 안전한가"*가 아니라 **"우리 경합이 잦은가"**입니다.

#### ② 우리는 낙관적 락"만" 쓰지 않는다

`AccountService.guarded()`는 두 겹입니다.

```
Redis 분산 락 (계좌·조각 단위)   ← 1차. 정상 경로를 아예 직렬화한다
        └─ @Version (조각 엔티티)  ← 2차. 락이 풀린 채 진행된 경우를 잡는다
```

**2차가 있는 이유가 핵심입니다.** 우리 분산 락은 `SET NX PX`, 즉 **TTL 기반**이라
임계 구역이 TTL을 넘기면 **락이 풀린 채로 작업이 계속됩니다**(watchdog이 없다).
그때 마지막으로 막는 것이 `@Version`입니다.

> 입금은 **고른 조각 하나**만 잠그고, 출금은 **전 조각**을 잠급니다 —
> 합을 보고 여러 조각에서 빼기 때문입니다. **쪼갠 이득이 출금에는 없다**는 것이 그 대가입니다.

#### ③ 어떤 대안을 봤나

| 후보 | 판단 |
|---|---|
| **지금대로 (분산 락 + 낙관적 락)** | ← 유지. 측정상 경합이 낮고, 핫 계좌는 샤딩으로 이미 풀렸다 |
| **비관적 락으로 단순화** (`FOR UPDATE`) | 장치가 셋(Redis 락·`@Version`·재시도)에서 하나로 준다. **Redis 의존과 TTL 문제가 사라진다.** 대신 **DB 커넥션을 락 대기 동안 붙든다** — 지금은 Redis가 대기를 흡수하는데, 옮기면 커넥션 풀 30이 다시 병목이 될 수 있다 |
| 분산 락만 (낙관적 제거) | TTL이 풀린 경우를 막을 것이 없어진다. **가장 나쁘다** |
| **🔁 Redisson** | watchdog·재진입을 얻지만 **락이 병목이 아니면 값이 없다**(`⏭️` 조건부, ROADMAP) |

#### ④ 왜 이걸 골랐나

**측정이 경합이 낮다고 말했습니다.**

```
baseline (Phase 5)   락 대기 최대 51ms · 획득 실패 0건 · 실패로 인한 재시도 0
```

낙관적 락이 불리해지는 조건(충돌이 잦음)이 **관측되지 않았습니다.**
그리고 진짜로 경합이 심한 자리(핫 계좌)는 **락 방식을 바꿔서가 아니라 경합 자체를 없애서**
풀었습니다 — 잔액을 8조각으로 갈라 25 → 70 TPS(2.8배).

> **"락을 더 좋은 락으로 바꾸는 것"과 "락이 필요 없게 만드는 것"은 다른 선택지입니다.**
> 후자가 가능하면 그쪽이 낫습니다.

#### ⑤ 무엇을 포기했나 ★

- **장치가 셋이라 이해하기 어렵습니다.** 분산 락 · 낙관적 락 · 재시도가 겹쳐 있어
  "무엇이 무엇을 막는지"를 매번 설명해야 합니다. `FOR UPDATE` 하나면 설명이 한 줄입니다.
- **Redis가 잔액 경로의 의존성이 됩니다.** Redis가 죽으면 락을 못 잡습니다
  (지금은 낙관적 락으로 우회되지만, 그러면 경합 시 재시도가 폭증합니다).
- **TTL을 넘기는 임계 구역이 실제로 생기면** 우리가 아니라 `@Version`이 잡습니다 —
  즉 **정상 경로가 아니라 예외 경로로 처리됩니다.**
- ⚠️ **분산 락이 정말 필요한지 자체가 열린 질문입니다.** 잔액은 `account_db` **한 곳**에
  있습니다. 같은 DB 안의 한 행을 지키는 데 분산 락은 과합니다 —
  분산 락의 값은 **여러 저장소에 걸친 자원**을 지킬 때 나옵니다.
  지금 이 구조인 것은 **"패턴을 손으로 만들어본다"는 학습 목적**이 컸다는 점을 인정합니다.

#### ⑥ 어떻게 확인했나

| 무엇 | 결과 |
|---|---|
| 경합이 잦은가 | 락 대기 **최대 51ms**, 획득 실패 **0건** (baseline) |
| 낙관적 락만으로도 되나 | `ACCOUNT_LOCK_STRATEGY`로 분산 락을 꺼보는 비교 실험 경로가 코드에 있다 |
| 핫 계좌는 | 락이 아니라 **한 행에 줄 선 것**이 상한이었다 → 샤딩으로 25 → 70 TPS |
| 정합성 | 모든 측정 뒤 drain → 정식 대사에서 **findings 0** |

#### 언제 이 결정을 뒤집나

- 락 대기가 **길어지거나** 획득 실패(`outcome=timeout`)가 잡히기 시작할 때
- Redis가 잔액 경로의 **단일 장애점**으로 실제 문제를 낼 때
- 수평 확장에서 **Redis가 병목**이 될 때 (제한 카운터와 락이 같은 Redis를 쓴다 — ROADMAP)

### D-005 · Redisson을 지금은 넣지 않는다 (근거였던 문제가 0으로 측정됐다)

**면접 한 줄**: "직접 만든 `SET NX PX` 락을 Redisson으로 갈아타려고 했습니다. 근거는
**watchdog** — 우리 락은 TTL 기반이라 임계 구역이 TTL보다 길면 락이 풀린 채로 진행되는데,
그게 **에러율에도 대사에도 안 나타나서** 있는지 없는지조차 몰랐습니다. 그래서 교체 전에
**해제 실패를 세는 카운터를 먼저 넣었습니다.** 재봤더니 34,200번 놓는 동안 **0건**이었습니다.
막으려던 문제가 없었으므로 교체를 보류했습니다. **측정이 교체를 취소시킨 사례**입니다."

**결정**: Redisson으로 **지금은 바꾸지 않는다**(취소가 아니라 `⏭️` 조건 대기)
· **근거**: 2026-08-31 측정 (`PROGRESS.md`의 "락은 안 새고 있었다")

#### ① 무엇을 재고 무엇이 나왔나

```
70 TPS · 8조각 · 데워진 상태 · 두 실행 누적
  release{released}  34,200      release{lost}  0     ← watchdog이 막으려던 것
  wait{acquired}     34,200      wait{timeout}  0
  최대 대기 605ms                 LOCK_TTL 3초        ← 여유 5배
```

**`lost`가 0이라는 건 임계 구역이 TTL을 넘긴 적이 없다는 뜻입니다.** watchdog은 그 상황을
없애주는 장치이므로, **없는 상황을 없애주는 값**은 0입니다.

#### ② 남은 근거는 하나뿐이고, 그 크기도 쟀다

```
대기 분포 (34,200건)
     ≤ 1ms   27,077   79.2%
   1 ~ 5ms    2,732    8.0%
  5 ~ 50ms       90    0.3%   ← 비어 있다
 50 ~ 100ms   2,774    8.1%   ← 여기 몰린다
100 ~ 250ms   1,403    4.1%
```

`RETRY_INTERVAL`이 50ms라 **한 번에 못 잡으면 락이 5ms 만에 풀렸어도 50ms를 채웁니다.**
그 몫이 **4,301건(12.6%)**입니다. Redisson의 pub/sub 대기는 이걸 지웁니다 —
**그러나 종결 p99는 2,714ms입니다.** 12.6%에 붙는 수십~수백 ms는 **지배 요인이 아닙니다.**

#### ③ 왜 그래도 안 하나 — 이 저장소의 잣대를 나에게도 적용한다

한도 서비스(Phase 6.6)와 Config Server(Phase 4)를 자른 이유가 **"아직 아프지 않다"**였습니다.
같은 잣대를 여기 들이대면 Redisson도 **지금은 근거가 약합니다.**

> *"손댈 때 무엇으로 할지는 현업 기술이 기본"*은 **손대기로 정한 뒤에** 적용되는 규칙입니다.
> **손댈 이유 자체를 만들어주지는 않습니다.** 이 둘을 섞으면 "표준이니까 넣었다"가 됩니다.

#### ④ 언제 이 결정을 뒤집나 (조건)

- **`release{lost}`가 0이 아니게 될 때** — TTL 누수가 실재하면 watchdog 근거가 되살아난다
- **`wait{timeout}`이 잡히거나 대기가 종결 p99의 유의미한 몫이 될 때** — 그때는 폴링이 근거가 된다
- **재진입이 실제로 필요해질 때** — 지금 `guarded()`는 중첩 락을 쓰지 않는다

**감시는 이미 붙어 있습니다.** 카운터와 대시보드 패널이 그대로 남으므로,
조건이 오면 **누가 찾아보지 않아도 보입니다.** 그것이 1번 작업이 남긴 값입니다.

### 3 · `SET NX PX` + Lua → Redisson

> **면접 한 줄**: "계좌별 분산 락을 Redis `SET NX PX`와 Lua로 직접 구현했습니다. 해제 시 단순
> `DEL`을 쓰면 TTL로 제 락이 풀린 뒤 남의 락을 지우게 돼서, 값이 제 토큰일 때만 지우도록
> Lua로 원자성을 맞췄습니다. **다만 watchdog이 없어** TTL(3초)을 넘기면 락이 풀린 채 작업이
> 계속됩니다. 낙관적 락이 받아주긴 하지만 그건 방어선이지 설계가 아니라서 Redisson으로
> 갈아탔습니다. 대신 Redisson 자체가 무겁고 내부 동작이 블랙박스가 됩니다."

**① 문제** — 코드 주석에 이미 적혀 있습니다.

> Redisson 같은 라이브러리와 달리 **자동 갱신(watchdog)이 없다.** 따라서 TTL은 임계 구역이
> 걸리는 최대 시간보다 넉넉해야 하고, 그보다 오래 걸리는 작업을 이 락으로 감싸면 안 된다.

DB가 느려져 잔액 변경이 3초를 넘기면 **락이 풀린 채로 작업이 계속됩니다.**
그리고 대기가 **폴링**이라 경합이 심할수록 Redis를 계속 찌릅니다.

**③ 대안**

| 후보 | 판단 |
|---|---|
| **Redisson** | watchdog, 재진입, **pub/sub 기반 대기**(폴링 아님), Fair lock |
| 자체 구현 유지 + watchdog 직접 | 만들 수는 있지만 **이미 검증된 걸 다시 만드는** 일입니다 |
| DB 비관적 락 (`SELECT FOR UPDATE`) | Redis 의존이 사라지지만 DB 커넥션을 오래 잡습니다 — 커넥션 고갈로 직행 |

**⑤ 포기하는 것** — Redisson은 **의존성이 크고** 내부가 블랙박스가 됩니다. 그리고 여전히
**Redis 장애 시 락이 없는 상태**이므로, 낙관적 락은 그대로 둬야 합니다.

**왜 Phase 6인가** — Phase 6 Step 1(핫 계좌)에서 **락 대기 시간과 획득 실패를 숫자로 본 뒤**
바꿉니다. 그래야 "watchdog이 없어서 불안했다"가 아니라 **"대기가 얼마였고 실패가 몇 %였다"**로
말할 수 있습니다.

> ⚠️ 그리고 Phase 6에서 **락을 아예 빼는 실험**을 먼저 합니다(낙관적 락 + 재시도만).
> 충돌이 적은 계좌는 그게 더 빠르다는 걸 확인하면, **"락을 더 좋은 락으로 바꾸는 것"과
> "락을 안 쓰는 것"이 다른 선택지**라는 게 드러납니다 — 이게 훨씬 나은 답변입니다.

> **면접 한 줄**: "API 스펙을 손으로 관리했는데 **이미 코드와 어긋나 있었습니다** — 새로 추가한
> 개시 이월·알림 엔드포인트가 스펙에 없었습니다. Gateway가 이 스펙을 계약으로 쓸 예정이라
> 어긋난 채로 두면 안 돼서 springdoc으로 자동 생성으로 바꿨습니다. 대신 컨트롤러에 애노테이션이
> 늘고, **내부 API를 노출에서 걸러내는 설정**이 따로 필요했습니다."

**⑤ 포기하는 것** — 스펙이 코드에 종속됩니다. **설계 먼저(spec-first)가 어려워집니다.**
그리고 `/internal/*`이 외부 스펙에 섞이면 그것대로 사고라, 필터링을 반드시 걸어야 합니다.

### 5 · 폴링 Outbox 릴레이 → Debezium (CDC)

> **면접 한 줄**: "Outbox 릴레이가 500ms마다 테이블을 폴링합니다. 트래픽이 없어도 계속 찌르고,
> 인스턴스를 늘리면 중복 발행됩니다. 부하 테스트에서 이게 병목으로 잡히는 걸 확인한 뒤
> Debezium CDC로 바꿨습니다 — binlog를 읽으니 폴링이 사라지고 지연도 커밋 직후로 줄었습니다.
> 대신 **Kafka Connect라는 인프라가 하나 더** 생겼고, binlog 설정·스키마 변경 대응이라는
> 운영 부담이 붙었습니다."

**② 자체 구현이 가르쳐준 것** — Outbox **패턴 자체**는 그대로 갑니다. 바뀌는 건 **발행 방식**뿐입니다.
직접 만들어봤기 때문에 "Debezium이 어느 부분을 대신해주는지"를 정확히 말할 수 있습니다.

**③ 대안**

| 후보 | 판단 |
|---|---|
| **Debezium** | binlog 기반. **우아한형제들이 실제로 쓰는 방식**([출처](https://techblog.woowahan.com/17386/)) |
| 폴링 유지 + 간격 조정 | 지연과 부하를 맞바꿀 뿐 근본이 안 바뀝니다 |
| 트랜잭션 커밋 후 직접 발행 | **원자성이 깨집니다.** Outbox를 쓰는 이유가 사라집니다 |

> 배민은 순서 보장을 위해 **커넥터당 태스크를 1개로 강제**하고, 처리량을 위해 **outbox 테이블을
> 토픽별로 분리하고 식별자 기반 N개로 샤딩**한다고 합니다. 태스크 1개면 그게 병목이 되니
> 테이블을 쪼개 커넥터를 늘리는 구조입니다 — **면접에서 이 정도까지 말하면 깊이가 보입니다.**

**⑤ 포기하는 것** — Kafka Connect 클러스터가 새로 뜹니다(**새 장애점**). binlog 권한과
`ROW` 포맷 설정이 필요하고, **DB 스키마를 바꿀 때 커넥터가 깨질 수 있습니다.**

**왜 Phase 6인가** — Phase 5 baseline에서 **50 TPS 천장의 원인으로 지목된 뒤** 바꾸면
"측정하고 고쳤다"는 답변이 됩니다. 그냥 바꾸면 "좋다길래 썼다"가 됩니다.

### 6 · Choreography Saga → Temporal / Camunda 8

> **면접 한 줄**: "Choreography로 만들었더니 **흐름 전체를 볼 수 있는 코드가 없고, 타임아웃이
> 없었습니다.** 응답이 영영 안 오면 대사가 나중에 발견할 뿐 흐름은 멈춰 있습니다.
> 오케스트레이션으로 바꾸면 흐름이 한 곳에 모이고 타임아웃·재개가 생기지만,
> **지휘자가 단일 장애점이 되고 서비스 간 결합도가 올라갑니다.** 그래서 지우지 않고 둘을
> 나란히 두고 비교했습니다."

**③ 대안**

| 후보 | 판단 |
|---|---|
| **Temporal** | Durable Execution. 워크플로가 그냥 자바 코드인데 죽어도 그 줄부터 재개 |
| **Camunda 8 (Zeebe)** | BPMN이 곧 실행 정의. **금융권에서 실제로 많이 씁니다** |
| Eventuate Tram Saga | 오케스트레이션 Saga 전용이지만 **이미 만든 Outbox와 정면으로 겹칩니다** |
| Axon Framework | 이벤트 소싱 + CQRS까지 딸려옵니다. 받아들이는 결정이 너무 큼 |
| 직접 구현 | 상태 테이블 + 타임아웃 스케줄러면 됩니다. **먼저 이걸 해보는 게 순서** |

**⑤ 포기하는 것** — 지휘자가 **단일 장애점**이 됩니다. transfer가 account의 사정을 알게 되어
**결합도가 오릅니다.** 지금은 notification을 붙일 때 기존 코드를 한 줄도 안 고쳤는데,
오케스트레이션이면 새 단계마다 지휘자를 고쳐야 합니다.

## 도입 대신 **대체**한 것 — CI/CD

기준으로 삼은 스택(토스)에는 GoCD·Jenkins·Harbor·Vault·Spinnaker·Consul·Ceph가 있습니다.
**전부 세우지 않습니다.** 대신 더 가벼운 것으로 대체하고 **왜 대체했는지**를 남깁니다.

> **면접에서는 "안 써봤습니다"가 아니라 "원래 것이 주는 가치가 무엇이고, 그중 무엇을
> 어떻게 대신했고, 무엇은 못 얻었는지"를 말하면 됩니다.** 그게 훨씬 강합니다.

| 원래 | 대체 | 원래 것이 주는 가치 | 무엇으로 대신했나 | **못 얻은 것** |
|---|---|---|---|---|
| **Harbor** | GHCR + Trivy | 사내망 격리, 취약점 스캔, 이미지 서명, 지역 복제 | 스캔은 Trivy로 CI에서 | **격리·서명·복제.** 로컬 학습에선 재현 실익이 낮음 |
| **Vault** | Sealed / External Secrets | 동적 시크릿, 자동 회전, 감사 로그, 리스 | 정적 시크릿 암호화까지만 | **회전·감사·동적 발급.** 금융이면 실제로는 필요한 것들 |
| **Spinnaker** | Argo Rollouts | 배포 전략 + **자동 카나리 분석**, 멀티 클라우드 | Rollouts가 Prometheus 보고 단계 승격/롤백 | 멀티 클라우드, 복잡한 파이프라인 오케스트레이션 |
| **GoCD / Jenkins** | GitHub Actions | 파이프라인 as code, 플러그인 생태계, 사내 실행기 | Actions로 동일한 CI | 사내망 실행기, 대규모 팀의 공유 파이프라인 |
| **Consul** | K8s 디스커버리 + Istio | 디스커버리, KV 설정, 헬스체크, 멀티 DC | K8s Service + Istio | **K8s 밖의 워크로드**를 못 다룸. 지금은 전부 안에 있어 무관 |
| **Ceph** | — | 분산 블록·오브젝트 스토리지 | 대체 안 함 | 스토리지 계층. 이 프로젝트 범위 밖 |
| **Istio** | 빼고 별도 학습 | mTLS, L7 트래픽 정책, 카나리, 사이드카 트레이싱 | mTLS 외에는 **적용할 자리가 없음**. 카나리는 Argo Rollouts + Ingress로 | L7 트래픽 정책 전반. 아래 참고 |

### Istio를 뺀 이유 ★ 면접에서 반드시 나옵니다

토스 스택에 Istio가 있으니 **"왜 안 쓰셨나요?"는 거의 확실히 나옵니다.** 준비된 답이 필요합니다.

> **면접 한 줄**: "서비스 간 동기 호출이 사실상 없는 구조라 메시가 얻을 게 mTLS 정도였습니다.
> 트래픽 분할은 나눌 서비스 간 트래픽이 없고, 회로 차단은 Kafka 컨슈머에 안 걸려서
> `DefaultErrorHandler`로 이미 하고 있었고, 트레이싱은 사이드카가 있어도 Kafka를 건너면
> 끊겨서 어차피 애플리케이션에서 붙여야 했습니다. **비용은 다 치르고 배우는 건 적다**고 판단해
> 범위에서 뺐고, 대신 동기 호출이 많은 별도 샘플에서 공부하기로 했습니다."

| Istio가 주는 것 | 이 프로젝트에서 |
|---|---|
| 트래픽 분할·카나리 | ❌ 나눌 **서비스 간** 트래픽이 없음 (대사의 읽기 조회 하나뿐) |
| 재시도·타임아웃·회로 차단 | ❌ **Kafka 컨슈머에 안 걸림.** 이미 `DefaultErrorHandler`로 처리 |
| 분산 트레이싱 | 🟡 **Kafka를 건너면 끊김.** trace context를 이벤트에 싣는 건 애플리케이션 몫 |
| mTLS | 🟢 이건 됨 — 얻는 게 사실상 이것뿐 |

**중요한 건 "설계가 잘못된 게 아니라 도구가 안 맞는다"는 구분입니다.**
비동기 이벤트 중심은 Phase 2의 의도된 선택이고(부분 실패에 강해집니다),
Istio는 서비스들이 서로 HTTP/gRPC로 부르는 구조에서 빛납니다.

> ⚠️ **Istio를 쓰려고 동기 호출을 만들면 안 됩니다.** 아키텍처를 도구에 맞추는 건 거꾸로이고,
> 면접에서 **"왜 이벤트 기반인데 동기 호출이 있죠?"**로 되돌아옵니다.
> "도구가 안 맞아서 안 썼다"가 "도구에 맞추려고 설계를 비틀었다"보다 훨씬 나은 답변입니다.

**카나리까지 포기하지는 않습니다.** 트래픽 분할은 Ingress로도 되고, 메시가 주는 건
*더 정밀한 분할*이지 *카나리 그 자체*가 아닙니다 → Phase 9에서 Argo Rollouts로 합니다.

### ArgoCD는 실제로 세웁니다 (Phase 8)

대체하지 않는 이유는 **GitOps가 개념이지 도구가 아니기 때문**입니다. 가볍기도 하고,
직접 겪어야 아는 게 있습니다.

- **Pull 기반** — 클러스터가 Git을 보고 스스로 맞춥니다. CI가 클러스터 자격증명을 들고 있을 필요가 없습니다
- **Drift 감지** — 누가 `kubectl edit`으로 손대면 잡힙니다
- **되돌리기가 `git revert`** — 배포 이력이 곧 Git 이력

> **ArgoCD vs Spinnaker는 좋은 면접 소재입니다.**
> ArgoCD는 **"상태를 맞추는"**(선언형·pull) 쪽이고, Spinnaker는 **"절차를 밟는"**(파이프라인·push)
> 쪽입니다. 카나리 자동 분석처럼 **절차가 복잡한 일**은 Spinnaker가 강하고,
> 그래서 Argo 진영도 Rollouts라는 별도 컨트롤러로 그 자리를 메웁니다.

## 왜 버전에 커밋 해시를 넣지 않았나

**"무엇이 배포됐는지 구분할 수 없다"는 문제는 맞지만, 버전 문자열은 그 답이 아닙니다.**

| | 무엇을 위한 것인가 |
|---|---|
| **아티팩트 버전** (`0.0.1-SNAPSHOT`) | *제품*이 몇 번째 판인가. 사람이 읽는 것 |
| **이미지 태그** (`github.sha`) | 어떤 이미지를 배포했나. 배포하는 쪽이 쓰는 것 |
| **build-info** (`/actuator/info`) | **지금 떠 있는 이 프로세스가 어느 커밋인가** |

셋째가 진짜 필요한 것입니다. 장애 대응 중에 필요한 건 "이 파드에 물어보면 답이 나오는 것"이고,
버전 문자열을 커밋 해시로 바꿔도 **실행 중인 프로세스에 물어볼 수단은 여전히 없습니다.**

그리고 버전에 해시를 넣으면 커밋마다 아티팩트 이름이 바뀌어 Gradle 캐시가 계속 무효화됩니다.
얻는 것 없이 빌드만 느려집니다.

```
GET /actuator/info
{ "build": { "commit": "9994bacb802f", "branch": "develop", "time": "...", ... } }
```

`BuildInfoTest`가 이걸 고정합니다 — 루트 `build.gradle`의 `bootBuildInfo` 설정이 사라지면 빨개집니다.
Docker가 필요 없어 `unitTest`에 포함됩니다.

> **면접 한 줄**: "버전을 커밋 해시로 바꾸는 것도 방법이지만, 정작 필요한 건 **실행 중인 프로세스에
> 물어보는 것**이라 build-info로 심었습니다. 아티팩트 버전은 제품 버전으로 두고, 이미지 태그는
> 커밋 SHA, 런타임 식별은 `/actuator/info`로 역할을 나눴습니다."

## 배포 순서 문제 — 이 저장소 고유의 숙제

**독립 배포하기로 해놓고, 계약 변경은 함께 배포해야 하는 모순이 있습니다.**

공유 모듈을 두지 않기로 해서 `TransferEvents`·`AccountEvents`가 **네 서비스에 중복 정의**되어
있습니다(`ARCHITECTURE.md` §1). 그래서 이벤트에 필드를 하나 바꾸면:

```
transfer의 이벤트 필드 변경  →  account·ledger·notification도 고쳐야 함
                            →  그런데 배포는 서비스별로 따로 나감
                            →  ★ 배포 사이 구간에 이벤트를 못 읽는 창이 생김
```

CD가 생기면 **바로 이게 첫 사고**가 됩니다. 지금은 손으로 다 띄우니 안 보일 뿐입니다.

| 대응 | 내용 | 비용 |
|---|---|---|
| **하위 호환만 허용** | 필드 **추가만** 되고 삭제·의미 변경 금지 | 규율에 의존. 강제 수단이 없음 |
| **Consumer 먼저 배포** | 읽는 쪽을 먼저 올리고 쓰는 쪽을 나중에 | 배포 순서를 사람이 기억해야 함 |
| **스키마 레지스트리** | Avro/Protobuf로 **빌드 타임에 호환성 강제** | 계약이 코드 밖으로 나감. 지금 구조를 크게 바꿈 |

지금은 `@JsonIgnoreProperties(ignoreUnknown = true)`가 **필드 추가에 한해** 절반을 해주고 있습니다.
**삭제와 의미 변경은 막을 장치가 없습니다.** Phase 8에서 CD를 세울 때 정할 문제입니다.

## 이미 현업 표준인 것

교체 목록만 있으면 지금까지 만든 게 다 임시방편처럼 보입니다. **바꿀 필요 없는 것**도 적어둡니다.

| | 면접에서 |
|---|---|
| **Testcontainers** | "H2로 돌리다 MySQL에서만 터지는 버그를 두 번 겪고 옮겼습니다 — `@Lob`이 TINYTEXT로 만들어진 것과 예약어 문제입니다" |
| **spring-kafka `DefaultErrorHandler` + DLT** | "기본값이 지연 없이 10회 시도 후 **로그만 남기고 오프셋을 커밋**해서, 메시지가 조용히 사라집니다. 그래서 백오프와 DLT를 명시했습니다" |
| **Transactional Outbox 패턴** | 배민과 같은 패턴. 발행 방식만 폴링 → CDC로 바뀝니다 |
| **낙관적 락 (`@Version`)** | "분산 락이 뚫렸을 때의 최후 안전망으로 남겨뒀습니다" |
| **Micrometer + Actuator** | Phase 9에서 Prometheus가 그대로 긁어갑니다 |

## 방어하기 어려운 선택 — 미리 준비할 것

**면접에서 반드시 물어볼 것들입니다.** 숨기는 것보다 반박을 준비하는 게 낫습니다.

### "왜 원장(ledger)에 MongoDB를 쓰셨나요?" ★ 가장 위험

금융에서 원장은 정합성의 최후 보루인데, **MongoDB는 단일 노드에서 다중 문서 트랜잭션을 쓸 수
없습니다.** 실제로 코드 주석에도 그 이유로 Outbox를 안 뒀다고 적혀 있습니다.
현업 금융 원장은 대부분 RDB + 파티셔닝입니다.

**준비할 답** — 이 원장은 **정합성의 원천이 아니라 파생 데이터**입니다. 원천은 account의
잔액이고, 원장은 그걸 이벤트로 재구성한 것이며, 어긋나면 대사가 잡습니다. 조회 트래픽이
압도적으로 몰리는 쪽이라 읽기에 맞춰 골랐습니다.

> ⚠️ **다만 이 답에는 빈틈이 있습니다.** 파생 데이터인데 **대사의 한쪽 기준**으로 쓰이고 있어
> 역할이 애매합니다. 되물으면 정직하게 인정하는 게 낫습니다 — "지금 설계의 약점이고,
> 원장을 MySQL로 옮기고 MongoDB는 조회 캐시로 내리는 게 맞다고 봅니다"까지 준비해두세요.

### "시크릿이 평문으로 커밋되어 있는데요?"

`application.yml`에 `username: root` / `password: root`가 그대로 있습니다.

**준비할 답** — 로컬 개발용 값이고 운영 자격증명이 아니지만, **변명이 아니라 부채로 보고 있습니다.**
Phase 8에서 Sealed/External Secrets로 걷어내는 게 계획에 있습니다. 지금 구조에서도
환경변수로 빼는 건 언제든 할 수 있는데, **컨테이너화 전에 하면 두 번 일이 되어** 묶어뒀습니다.

> ⚠️ 이건 방어하기보다 **먼저 인정하는 게 낫습니다.** 금융 도메인을 다루는 프로젝트에서
> 시크릿 관리를 안 했다는 건 지적당하기 딱 좋고, "알고 있고 언제 처리할지도 정해뒀다"가
> 최선의 답입니다.

### "왜 Kotlin이 아니라 Java인가요?"

토스는 Kotlin 비중이 높고 배민도 늘고 있습니다.

**준비할 답** — 분산 시스템 패턴 연습이 목적이라 **언어를 바꾸는 데 드는 시간을 패턴에 쓰기로**
했습니다. 다만 이 프로젝트의 대부분이 DTO·이벤트 계약이라 Kotlin의 data class와 null 안정성이
잘 맞는 영역인 건 맞습니다.

### "서비스를 왜 이렇게 잘게 나눴나요?"

5개는 이 도메인 규모에 비해 많습니다.

**준비할 답** — 서비스 수가 늘 때 생기는 문제(디스커버리, 트래픽 정책, 크로스 서비스 관측)를
겪어보는 게 목적 중 하나였습니다. **분리 기준은 있습니다** — 대사는 세 저장소를 가로질러야 해서,
알림은 송금을 막으면 안 돼서입니다.

### "공유 모듈 없이 DTO를 중복 정의한 이유는?"

**준비할 답** — 공유 모듈은 배포 결합을 만듭니다. 한 서비스가 필드를 바꾸면 전부 다시 배포해야
합니다. 대신 **계약이 어긋날 위험**을 떠안았고, `@JsonIgnoreProperties(ignoreUnknown = true)`로
필드 추가는 견디게 했습니다. 규모가 커지면 **스키마 레지스트리(Avro/Protobuf)**로 가야 할 자리입니다.
