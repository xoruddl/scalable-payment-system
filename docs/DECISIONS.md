# 기술 결정 기록

**이 저장소는 패턴을 먼저 손으로 만들어보고, 그다음 현업이 실제로 쓰는 기술로 갈아탑니다.**
이 문서는 **그 갈아타기를 기록하는 곳**입니다.

| 문서 | 무엇을 적나 |
|---|---|
| `PROGRESS.md` | **무슨 일이 있었나** — 시간순 작업 기록 |
| `ARCHITECTURE.md` | **지금 이렇게 생겼다** — 현재 구조 |
| `DECISIONS.md` (이 문서) | **왜 이걸 골랐나** — 무엇을 무엇으로 바꿨고, 무엇을 얻고 잃었나 |

## 왜 처음부터 검증된 기술을 안 쓰나

**쓸 줄 아는 것과 왜 필요한지 아는 것은 다르기 때문입니다.**

Redisson을 먼저 붙였다면 `RLock`을 호출할 줄은 알았겠지만, **왜 해제할 때 내 토큰인지 확인해야
하는지**는 몰랐을 겁니다. 직접 만들어보면 "단순 `DEL`을 쓰면 TTL로 내 락이 풀린 뒤 남이 잡은
락을 내가 지운다"를 몸으로 겪습니다. 그 뒤에 Redisson을 보면 watchdog이 왜 있는지 압니다.

**그래서 자체 구현은 목적지가 아니라 중간 기착지입니다.** 배울 것을 다 배웠으면 갈아탑니다.

> ⚠️ 갈아탈 때 **자체 구현의 이유를 지우지 마세요.** 대비가 이 저장소의 자산입니다.
> 코드는 지우되 `PROGRESS.md`의 서술은 남기고, 여기에 "무엇을 배웠나"를 적습니다.

## 교체 예정 목록

**언제 아프기 시작하는지** 순으로 놓았습니다. 우선순위는 "더 좋아 보여서"가 아니라
**어느 Phase에서 실제로 막히는가**로 정합니다.

| # | 지금 (자체 구현) | 바꿀 것 | 언제 아픈가 |
|---|---|---|---|
| 1 | `ddl-auto: update` | **Flyway** | Phase 6~7 — 컨테이너·K8s |
| 2 | 맨 `@Scheduled` | **ShedLock** | Phase 7 — 인스턴스가 늘어날 때 |
| 3 | `SET NX PX` + Lua 직접 구현 | **Redisson** | 지금도 조용히 위험 |
| 4 | 폴링 Outbox 릴레이 | **Debezium (CDC)** | Phase 10 — 부하 테스트 |
| 5 | 손으로 쓴 `openapi.yaml` | **springdoc-openapi** | Phase 4 — Gateway |
| 6 | Choreography Saga | **Temporal / Camunda 8** | 지금도 — 흐름이 안 보임 |

### 1 · `ddl-auto: update` → Flyway

**가장 급합니다.** 네 서비스 전부 `ddl-auto: update`로 스키마를 만들고 있습니다.
이건 **로컬 개발 편의 기능이지 운영에 쓰는 물건이 아닙니다.**

무엇이 문제냐면:

| | `ddl-auto: update` | Flyway |
|---|---|---|
| 컬럼·인덱스 삭제 | **안 합니다.** 조용히 남습니다 | 마이그레이션에 쓴 대로 |
| 데이터 마이그레이션 | 불가능 | 가능 |
| 되돌리기 | 불가능 | 버전으로 관리 |
| 인스턴스 여럿이 동시 기동 | **경합.** 각자 DDL을 날림 | 잠금으로 하나만 |
| 지금 스키마가 무엇인지 | **아무도 모릅니다.** 엔티티에서 추론할 뿐 | 파일로 남음 |

> 이번 세션에서 실제로 겪었습니다. `Transfer.idempotencyKey`의 `unique = true`를 떼고
> 테스트를 돌렸는데, **컨테이너가 새로 떴기 때문에** 인덱스 없이 만들어져 red가 나왔습니다.
> 기존 DB였다면 인덱스가 그대로 남아 **테스트가 통과했을 것**입니다.
> 검증이 DB 상태에 따라 달라지는 상태입니다.

또 `docker/mysql-init/01-databases.sql`로 DB를 만드는데, **볼륨이 이미 있으면 그 스크립트는
다시 돌지 않습니다.** `notification_db`를 추가했지만 기존 볼륨에는 안 생깁니다.
이런 것도 마이그레이션이 관리할 일입니다.

### 2 · 맨 `@Scheduled` → ShedLock

세 군데에 `@Scheduled`가 있습니다.

```
account/OutboxRelay          500ms마다 미발행 이벤트 발행
transfer/OutboxRelay         500ms마다
reconciliation/Scheduler     60초마다 대사 한 회차
```

**전부 "인스턴스가 하나"를 전제로 합니다.** Phase 7에서 HPA로 replica를 늘리는 순간:

- **Outbox 릴레이** — 두 인스턴스가 같은 행을 읽어 **같은 이벤트를 두 번 발행**합니다.
  컨슈머가 멱등해서 사고는 안 나지만, 배치를 순서대로 보내려던 설계가 무너집니다
- **대사** — 회차가 중복 생성되고, 같은 어긋남이 두 번 보고됩니다

ShedLock은 **스케줄 작업 하나를 클러스터에서 한 번만 돌게** 합니다. Redis나 DB를 잠금 저장소로
씁니다 — 둘 다 이미 있습니다.

> ⚠️ Phase 7에서 HPA 오토스케일링을 검증할 때 이게 없으면, **스케일 아웃이 곧바로 버그**가 됩니다.
> Phase 7보다 먼저 들어가야 합니다.

### 3 · `SET NX PX` + Lua → Redisson

`account-service`의 `DistributedLock`은 획득/해제가 정확합니다. 해제할 때 **내 토큰일 때만**
지우도록 Lua로 원자성까지 맞췄습니다. 배울 건 다 배운 코드입니다.

**없는 것은 watchdog입니다.** 코드 주석에도 적혀 있습니다.

> Redisson 같은 라이브러리와 달리 **자동 갱신(watchdog)이 없다.** 따라서 TTL은 임계 구역이
> 걸리는 최대 시간보다 넉넉해야 하고, 그보다 오래 걸리는 작업을 이 락으로 감싸면 안 된다.

지금 TTL은 3초입니다. **DB가 느려져 잔액 변경이 3초를 넘기면 락이 풀린 채로 작업이 계속됩니다.**
낙관적 락이 최후 방어선으로 남아 있어 사고로 이어지진 않지만, 그건 방어선이지 설계가 아닙니다.

| Redisson이 더 주는 것 | |
|---|---|
| watchdog | 작업이 살아 있는 동안 TTL 자동 연장 |
| 재진입(reentrant) | 같은 스레드가 다시 잡을 수 있음 |
| pub/sub 대기 | 지금은 폴링으로 기다림 — Redis 부하 차이가 큼 |
| Fair lock, RedLock | 필요해지면 |

### 4 · 폴링 Outbox 릴레이 → Debezium (CDC)

지금은 500ms마다 `outbox_events`를 `SELECT`합니다. **트래픽이 없어도 계속 찌릅니다.**

| | 폴링 (지금) | Debezium |
|---|---|---|
| 지연 | 최대 500ms | 커밋 직후 (binlog) |
| DB 부하 | 초당 2회 × 인스턴스 수 × 서비스 수 | 없음 (binlog를 읽음) |
| 인스턴스 늘리면 | 중복 발행 (→ ②) | 커넥터가 알아서 |
| 붙는 인프라 | 없음 | **Kafka Connect가 필요** |

Debezium은 MySQL **binlog**를 읽어 테이블 변경을 그대로 Kafka로 흘립니다. 폴링이 사라집니다.
대신 Kafka Connect라는 인프라가 하나 더 붙으므로, **Phase 6에서 컨테이너 구성이 잡힌 뒤**가 맞습니다.

> 부하 테스트(Phase 10)에서 폴링 릴레이가 병목으로 잡히는 걸 먼저 **보여주고** 바꾸면
> 이 저장소의 방식에 가장 잘 맞습니다.

### 5 · 손으로 쓴 `openapi.yaml` → springdoc-openapi

`docs/openapi.yaml`을 손으로 관리하고 있습니다. **코드와 어긋나도 아무도 모릅니다.**
이번 세션에 추가한 `/internal/accounts/{id}/opening-balance`와 `/notifications/*`도 거기 없습니다.

springdoc은 컨트롤러에서 스펙을 뽑아냅니다. Phase 4에서 Gateway가 이 스펙을 계약으로 쓸 거라
그전에 정리하는 게 좋습니다.

> 다만 **내부 API(`/internal/*`)는 노출에서 빼야** 합니다. 대사·이월 엔드포인트가 외부 스펙에
> 섞이면 그것대로 사고입니다.

### 6 · Choreography Saga → Temporal / Camunda 8

**가장 크고, 가장 나중입니다.** 앞의 다섯은 부품 교체지만 이건 **흐름 전체를 다시 쓰는 일**입니다.

지금 방식의 대가는 `ARCHITECTURE.md`에 적어둔 그대로입니다 — **흐름 전체를 볼 수 있는 코드가
없습니다.** 그리고 **타임아웃이 없습니다.** 응답이 영영 안 오면 대사가 나중에 발견할 뿐,
흐름 자체는 멈춰 있습니다.

| 후보 | 성격 | 걸리는 점 |
|---|---|---|
| **Temporal** | Durable Execution. 워크플로가 그냥 자바 코드인데 죽어도 그 줄부터 재개 | 별도 클러스터 + 자체 DB |
| **Camunda 8 (Zeebe)** | BPMN이 곧 실행 정의. 금융권에서 실제로 많이 씀 | 무겁고, 흐름이 코드가 아닌 그림에 있음 |
| Eventuate Tram Saga | 오케스트레이션 Saga 전용 라이브러리 | 이미 만든 Outbox와 정면으로 겹침 |
| Axon Framework | Saga + 이벤트 소싱 + CQRS | 딸려오는 게 너무 많음 |

**Choreography를 지우지 말고 나란히 두는 것**을 권합니다. 같은 도메인을 두 방식으로 구현해놓고
비교하는 것 자체가 이 저장소가 만들려는 자산입니다.
