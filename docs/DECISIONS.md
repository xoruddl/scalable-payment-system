# 기술 결정 기록

**이 문서는 "무엇을 썼나"가 아니라 "왜 그걸 골랐나"를 적는 곳이다.**

이 저장소는 패턴을 먼저 손으로 만들어보고 그다음 현업이 실제로 쓰는 기술로 갈아탄다.
그 갈아타기마다 **면접에서 그대로 말할 수 있는 형태로** 기록을 남긴다.

| 문서 | 무엇을 적나 |
|---|---|
| `PROGRESS.md` | **무슨 일이 있었나** — 시간순 작업 기록 |
| `ARCHITECTURE.md` | **지금 이렇게 생겼다** — 현재 구조 |
| `DECISIONS.md` (이 문서) | **왜 이걸 골랐나** — 문제, 대안, 근거, **포기한 것** |

## 면접에서 통하는 답과 안 통하는 답

먼저 이것부터. 기술 선택 질문의 답은 **기술 이름이 아니라 문제**로 시작해야 한다.

| ❌ 안 통함 | 왜 |
|---|---|
| "토스가 쓰니까요" | **회사 이름은 근거가 아니다.** 규모도 제약도 다르다 |
| "Redisson이 더 좋아서요" | 무엇이 어떻게 더 좋은지가 없다 |
| "성능이 좋아집니다" | 숫자가 없으면 안 한 것과 같다 |
| "요즘 다들 씁니다" | 유행은 근거가 아니다 |

**통하는 답의 뼈대는 다섯 개다.**

```
① 어떤 문제가 있었나     구체적인 증상. 가능하면 숫자
② 어떤 대안을 봤나       최소 둘. 하나만 보고 골랐으면 고른 게 아닙니다
③ 왜 이걸 골랐나         우리 제약(팀 규모, 인프라, 트래픽)에 비춰서
④ 무엇을 포기했나        ★ 면접관이 가장 파고드는 곳
⑤ 어떻게 확인했나        도입 전후를 무엇으로 쟀나
```

> **④가 핵심이다.** 트레이드오프를 말하지 못하면 "장점만 읽고 도입했다"로 들린다.
> 반대로 단점을 먼저 말하면 **그 기술을 실제로 써봤다는 신호**가 된다.

### 이 저장소만의 무기

대부분의 지원자는 "Redisson 써봤습니다"라고 말한다. 이 저장소는 **직접 만들어보고 갈아탄
과정**이 있다. 그래서 이렇게 말할 수 있다.

> "분산 락을 `SET NX PX`와 Lua로 직접 구현했었다. 해제할 때 단순 `DEL`을 쓰면 TTL로 제 락이
> 풀린 뒤 남이 잡은 락을 지워버리는 문제가 있어서, 값이 제 토큰일 때만 지우도록 Lua로
> 원자성을 맞췄다. 그런데 watchdog이 없어서 임계 구역이 TTL을 넘기면 락이 풀린 채로
> 작업이 계속되는 한계가 있었고, 그 지점에서 Redisson으로 갈아탔다."

**"왜 직접 만들었다가 바꿨나"가 곧 답변이다.** 갈아탈 때 자체 구현의 이유를 지우지 않는다 —
코드는 지우되 `PROGRESS.md`의 서술은 남긴다. 대비가 이 저장소의 자산이다.

## 교체 이력

### D-001 · `ddl-auto: update`를 Flyway로 (Phase 6)

**면접 한 줄**: "스키마를 `ddl-auto: update`로 만들고 있었는데, `Transfer.idempotencyKey`의
unique를 떼고 테스트했을 때 **컨테이너가 새로 떴기 때문에** 실패가 잡혔다. 기존 DB였다면
인덱스가 남아 통과했을 것이다. **검증 결과가 DB 상태에 따라 달라진다**는 게 드러나서 Flyway로
옮겼다. 대신 스키마를 바꿀 때마다 마이그레이션 파일을 함께 써야 한다."

**바꾼 것**: `ddl-auto: update` → `Flyway 12.4.0` + `ddl-auto: validate`  ·  **커밋**: `f0dcbb2`

#### ① 어떤 문제가 있었나

`ddl-auto: update`는 **더하기만 하고 빼지 않는다.** 컬럼도 인덱스도 지우지 않는다.
그래서 스키마가 **어느 DB에서 언제부터 떠 있었느냐**에 따라 달라진다.

| 증상 | 무슨 일이 일어났나 |
|---|---|
| unique를 뗐는데 테스트가 red | 컨테이너가 새로 떠서 인덱스가 안 만들어졌다. **기존 DB였으면 green** |
| `notification_db`를 추가했는데 안 생김 | `01-databases.sql`은 **볼륨이 비었을 때만** 돈다 |

두 번째가 특히 나쁘다. "스키마를 누가 만드나"의 답이 **앱, 초기화 스크립트, 사람 손** 셋으로
갈라져 있었고, 셋 다 "이미 있으면 안 한다"라서 **어긋난 상태를 아무도 못 본다.**

#### ② 자체 구현이 가르쳐준 것

`ddl-auto`가 만든 스키마를 실제로 뜯어보니, **이름이 전부 Hibernate의 것**이었다 —
`UKc662f7lm5ec167m89rp50kb1d` 같은. 인덱스를 지우려면 이 이름을 알아야 하는데,
엔티티 어디에도 적혀 있지 않는다. **되돌릴 방법이 없는 변경을 계속 쌓고 있었던** 셈이다.

#### ③ 어떤 대안을 봤나

| 후보 | 채택 안 한 이유 |
|---|---|
| **Flyway** | ← 채택. SQL 그대로 씀. Spring Boot 4.1이 `spring-boot-starter-flyway`로 기본 통합 |
| Liquibase | XML/YAML 추상화로 DB 이식성이 좋지만, **MySQL 하나로 갈 거라 그 이점을 못 쓴다** |
| 계속 `ddl-auto` | 운영에서 못 쓴다. 컨테이너 여럿이 뜨면 DDL이 서로 경합하기까지 한다 |

#### ④ 왜 이걸 골랐나

혼자 하는 저장소라 **배우는 비용이 가장 싼 것**이 유리하고, Flyway는 파일 이름 규칙과
`flyway_schema_history` 테이블 하나가 전부다. 이식성은 애초에 필요가 없다.

#### ⑤ 무엇을 포기했나  ★

- **엔티티만 고치면 되던 게 두 곳이 됐다.** 컬럼 하나 추가에 SQL 파일이 따라온다.
- **`baseline-on-migrate: true`가 남는다.** 이미 테이블이 있는데 이력이 없으면
  "지금 이게 V1이다"라고 **도장만 찍고 내용을 확인하지 않는다.** 실제 스키마가 V1과 달라도
  통과한다. 그래서 `ddl-auto: validate`를 짝으로 켜뒀다 — 엔티티와 실제 테이블이
  어긋나면 그쪽에서 기동이 멈춘다. **한쪽만으로는 부족한 구성**이다.
- **베이스라인이 예쁘지 않는다.** `UKc662f7lm5ec167m89rp50kb1d`를 그대로 뒀다.
  여기서 이름을 고치면 **도장만 찍고 넘어가는 기존 DB**와 **V1을 실행하는 새 DB**의 스키마가
  갈라진다. 고치려면 지금부터는 V2이다.

#### ⑥ 어떻게 확인했나

**둘 다 확인해야 한다** — 새 DB에서 V1이 맞게 만드는가, 기존 DB에서 안 깨지고 뜨는가.

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| Flyway가 진짜 도는가 | V1의 컬럼 이름 하나를 **일부러 틀리게** 하고 테스트 | notification 7개가 전부 `SchemaManagementException`으로 **red** |
| V1 == 엔티티 | 되돌린 뒤 다섯 서비스 테스트 | 전부 green (새 컨테이너 → V1 실행 → validate 통과) |
| 기존 DB에서 안 깨지나 | 데이터가 든 홈서버 DB에 배포 | 네 DB 전부 `<< Flyway Baseline >>` / `success=1`, **V1은 실행 안 됨** |
| 데이터가 남아 있나 | 재시작 후 행 수 | accounts 61 · transfers 2521 · notifications 5042 — 그대로 |

**일부러 깨보지 않았으면 아무것도 확인 못 했을 것이다.** 테스트가 green인 것만으로는
"Flyway가 돌았다"가 아니라 "어쨌든 테이블이 있었다"까지밖에 말할 수 없다.

#### 겪은 것

- Boot 4.1은 `flyway-core`를 직접 넣지 않고 **`spring-boot-starter-flyway`**를 쓴다
  (→ flyway-core 12.4.0). MySQL은 **`flyway-mysql`이 따로** 있어야 방언을 인식한다.
- **베이스라인은 설계하는 게 아니라 뜨는 것**이다. `mysqldump --no-data`로 받아
  `AUTO_INCREMENT=N`(스키마가 아니라 데이터 상태)만 지웠다.
- 원장(ledger)은 MongoDB라 이 작업에서 빠진다. 같은 문제(`MongoIndexInitializer`가
  기동할 때 인덱스를 만든다)가 남아 있고, **Mongock**으로 Phase 7에 옮긴다.

### D-002 · 직접 만든 격벽·회로 차단기를 Resilience4j로 (Phase 6.5)

**면접 한 줄**: "느린 상대가 내부 송금 p99를 3,071 → 58,790ms로 악화시키는 것을 재현한 뒤
`Semaphore` 격벽과 은행별 회로 차단기를 직접 만들었다. 필요한 계약을 테스트로 고정한 뒤
Resilience4j로 교체해 표준 상태 머신과 Micrometer 지표를 얻었다. 대신 라이브러리 동작이
블랙박스가 되고, 송금의 `sent` 경계를 지키기 위한 저수준 어댑터는 남는다."

**바꾼 것**: 직접 만든 `Semaphore` + CLOSED/OPEN/HALF_OPEN 상태 머신 →
`Resilience4j 2.4.0` Bulkhead/CircuitBreaker/Micrometer  ·  **커밋**: `ccb3175`

#### ① 어떤 문제가 있었나

상대 은행이 2초 느려지자 아무 관계 없는 내부 송금 종결 p99가 **3,071 → 58,790ms**,
종결 성공률이 **1.00 → 0.53**으로 떨어졌다. 외부 6건/s × 2초 = 12 스레드-초/초인데
리스너 스레드는 6개라 외부 호출만으로 전부 점유했기 때문이다.

리스너 분리·격벽·회로 차단기로 장애 전파는 막았지만 최종 코드가 직접 만든 동시성·상태 머신과
자체 지표에 기대고 있었다. 상태 전이 경합, HALF_OPEN 허가 반환, 지표 누락을 앞으로도 우리가
검증하고 유지해야 하는 형태였다.

#### ② 자체 구현이 가르쳐준 것

- **격벽 거절은 실패가 아니라 미전송이다.** 기다리면 스레드를 지킨다는 목적이 사라지므로
  정원이 차면 즉시 거절하고 `sent=false`로 남겨야 한다.
- **회로는 은행별이어야 한다.** KB 장애가 정상인 SH 송금까지 막으면 장애 격리가 아니다.
- **POST와 GET의 목적이 다르다.** 새 입금 POST는 차단하지만, 이미 보낸 돈을 확인하는 GET은
  회로를 우회해야 `CREDIT_UNKNOWN`을 해소할 수 있다.
- `sent=true`는 회로 허가 뒤, HTTP 직전에 영속화해야 한다. 더 빠르면 안 보낸 돈을 보냈다고
  기록하고, 더 늦으면 응답 대기 중 프로세스가 죽을 때 이중 전송할 수 있다.

이 계약을 먼저 알아냈기 때문에 라이브러리의 기본 데코레이터를 그대로 붙이지 않고,
어디서 허가를 얻고 반환해야 하는지 결정할 수 있었다.

#### ③ 어떤 대안을 봤나

| 후보 | 판단 |
|---|---|
| **Resilience4j 코어 모듈** | ← 채택. 필요한 패턴만 골라 쓰고, 은행별 registry와 [표준 Micrometer 지표](https://resilience4j.readme.io/docs/micrometer)를 제공 |
| Spring Cloud CircuitBreaker | 구현체 교체 추상화가 장점이지만 구현체를 바꿀 계획이 없고, `sent` 경계에 필요한 저수준 허가 제어가 가려짐 |
| 직접 구현 유지 | 도메인 계약은 가장 잘 보이지만 상태 머신·동시성·지표의 장기 유지 책임이 계속 우리에게 남음 |
| Resilience4j Spring Boot 스타터 | Spring Boot 4 지원이 아직 명확하지 않고 AOP 자동 설정이 필요 없음. 코어 세 모듈만 직접 조립 |

Resilience4j는 semaphore 방식과 thread-pool 방식을 모두 제공하지만, 이미 Kafka 리스너 풀을
분리했다. 별도 실행기와 큐를 하나 더 만드는 thread-pool bulkhead 대신 호출 스레드 수만
제한하는 [semaphore bulkhead](https://resilience4j.readme.io/docs/bulkhead)를 골랐다.

#### ④ 왜 이걸 골랐나

필요한 것은 재시도나 타임리미터 묶음이 아니라 **격벽과 회로 차단기 두 개**다.
Resilience4j는 모듈 단위라 필요한 것만 넣을 수 있고, `CircuitBreakerRegistry`로 은행별 회로를
동적으로 만들며, Micrometer registry에 새 회로도 자동 등록한다.

직접 구현의 "5회 연속 실패"는 count-based window 5 + minimum calls 5 + failure rate 100%로
옮겼다. 최근 5건에 성공이 하나라도 있으면 100%가 아니므로 열리지 않고, 그 성공이 window에서
밀려난 다섯 번째 연속 실패에서 열린다. OPEN 30초와 HALF_OPEN 한 건도 설정으로 그대로 보다.

버전은 당시 최신 안정 릴리스인 [2.4.0](https://github.com/resilience4j/resilience4j/releases/tag/v2.4.0)을
명시했다. Spring Boot BOM이 관리하지 않아 세 모듈의 버전을 함께 고정했다.

#### ⑤ 무엇을 포기했나  ★

- 직접 구현보다 **내부 상태 전이가 블랙박스**다. 설정 조합이 곧 동작이라,
  `slidingWindowSize`와 `failureRateThreshold`의 관계를 모르면 "연속 실패"가 조용히 바뀐다.
- `sent` 영속화가 회로 허가와 HTTP 사이에 있어야 하므로 **저수준 permission API 어댑터는
  남는다.** 애너테이션 한 줄짜리 구성은 포기했다.
- 의존성 세 개와 버전 관리가 생겼다. 특히 Boot 4용 스타터 자동 설정을 쓰지 않아 registry와
  Micrometer 바인딩도 코드에서 직접 한다.
- 지표 이름이 자체 `remittance.external.*`에서 `resilience4j.*`로 바뀌었다. 기존 대시보드가
  있었다면 함께 마이그레이션해야 한다(현재는 Phase 9 대시보드 전이라 비용이 작다).
- 회로 이름에 은행 코드가 들어가므로 은행 코드가 무제한이면 시계열 cardinality가 늘어난다.
  지금은 설정에 등록된 유한한 은행만 호출할 수 있다는 전제가 있다.

#### ⑥ 어떻게 확인했나

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| 격벽 계약 | 정원 초과 동시 호출, 예외 후 허가 반환 | 즉시 `BulkheadFullException`, 다음 호출 정상 |
| 회로 계약 | 실패·성공·은행 격리·가상 시간·동시 HALF_OPEN 시험 | 5회 연속 실패, 30초 OPEN, 시험 한 건 유지 |
| 송금 경계 | 10건 연속 타임아웃 통합 테스트 | HTTP 5회, `sent=true` 5건, 미전송 5건 |
| 테스트 유효성 | 최초 전송 경로에서 회로를 잠시 우회 | `TooManyActualInvocations`로 red, 원복 후 green |
| 관측 | 표준 Micrometer meter 이름·태그 검증 | 회로 거절, 상태, 격벽 정원·남은 허가 노출 |
| 전체 회귀 | `./gradlew test` | **532건 green**, 2분 58초 |

성능은 아직 비교하지 않았다. 다음 Step에서 직접 구현 때와 같은 홈서버 장애 시나리오로
재측정하기 전까지 **"Resilience4j가 더 빠르다"고 말하지 않는다.**

#### 겪은 것

- 테스트용 시계 생성자를 추가하자 Spring이 생성자를 고르지 못해 기본 생성자를 찾았다.
  운영 생성자를 `@Autowired`로 명시했다.
- Resilience4j OPEN 상태는 `Clock`으로 종료 시각을 계산한다. NTP 같은 벽시계 보정으로
  30초가 흔들리지 않도록 기동 시각에 `System.nanoTime()` 경과량을 더하는 단조 시계를 넣었다.
- 대기시간 경계는 정확히 같은 시각이 아니라 **지난 뒤** 허용됐다. 가상 시간을 1ms 더
  전진시켜 실제 OPEN → HALF_OPEN 전이를 sleep 없이 검증했다.

## 켜지 않기로 한 것

**안 켜는 것도 결정이다.** 라이브러리를 붙이면 설정이 딸려 오는데, 그중에는 켜는 순간
**시스템의 성격이 바뀌는 것**이 있다. 안 켠 이유를 안 적으면 나중에 "빠뜨린 것"과
구분되지 않고, 면접에서도 *"그건 왜 안 쓰셨어요?"*를 그대로 맞는다.

번호는 위와 같은 줄에서 이어간다 — **결정이라는 점에서 다르지 않기 때문**이다.

### D-003 · 느린 호출은 실패로 세지 않는다 (Phase 6.5)

**면접 한 줄**: "회로 차단기를 넣고 재보니 상대가 2초씩 끄는데도 회로가 안 열렸다.
read-timeout이 3초라 전부 '성공'이었기 때문이다. Resilience4j에 느린 호출을 실패로 세는
설정이 있어서 켤 수 있었지만, 그러면 **얼마나 느리면 포기하나**를 정하는 값이 타임아웃과
둘이 된다. 기준을 하나로 두고 대신 그 하나(read-timeout)를 근거 있는 값으로 유지하기로
했다. 대가는 '느리지만 성공하는 상대'가 계속 우리 리스너를 붙든다는 것이고,
그건 전용 리스너와 격벽으로 이미 가둬뒀다."

**바꾸지 않은 것**: `slowCallDurationThreshold` · `slowCallRateThreshold`를 **켜지 않는다**
· **근거**: 2026-08-28 재측정 (`PROGRESS.md`)

#### ① 어떤 문제가 있었나

상대 은행을 **2초 지연**으로 두고 30 TPS를 흘렸더니 회로가 **내내 CLOSED**였다.

```
successful 586   failed 0   not_permitted 0      평균 2.03초 · 최대 2.15초
```

회로 차단기를 넣은 동기는 `PROGRESS.md`에 이렇게 적혀 있었다 —
*"상대가 감당 못 할 만큼 느리면 부르는 것을 멈추는 판단이 필요합니다."*
**그 문장대로면 이건 열렸어야 한다.**

#### ② 다시 보니 문제 설정이 틀렸다

`read-timeout: 3s`는 이미 **"이만큼 느리면 포기한다"를 정해둔 값**이다.
그러면 2초는 우리가 정한 선 **안**이므로 "감당 못 할 만큼 느린" 것이 아니다.
진짜로 감당 못 하면 3초를 넘고, 그건 타임아웃 → 실패 → **회로가 연다.**

**동기는 이미 충족돼 있었고, 기준이 `slowCallRateThreshold`가 아니라 타임아웃이었을 뿐이다.**
"회로가 안 열린다"를 구멍으로 읽은 것이 잘못된 진단이었다.

#### ③ 어떤 대안을 봤나

| 후보 | 판단 |
|---|---|
| **지금대로 — 기준은 타임아웃 하나** | ← 채택. 아래 ④ |
| `slowCallRateThreshold`를 켠다 | "얼마나 느리면 포기하나"가 **두 값**이 된다. 둘이 어긋나면 "왜 안 열렸나"를 설명할 수 없다 |
| read-timeout을 줄인다 (예: 1초) | 회로는 더 잘 열리지만 **멀쩡히 처리 중인 요청을 자꾸 모르는 상태로 만든다.** 이 시스템에서 가장 비싼 상태를 늘리는 방향이다 |

#### ④ 왜 이걸 골랐나

**느리지만 성공하는 상대를 우리가 끊으면, 나가야 할 송금이 안 나간다.**
차단된 건은 미전송으로 쌓이고 상대는 멀쩡한데 우리 판단으로 돈이 멈춘다.

그리고 그 피해는 이미 갇혀 있다 — 외부 전용 리스너로 내부 송금과 풀을 나눴고
(내부 p99 58,790 → 2,580ms), 격벽이 이 서비스 전체의 외부 동시성에 상한을 둔다.
**느린 상대가 만드는 피해는 "우리가 느려지는 것"이 아니라 "외부가 밀리는 것"**이고,
그건 회로로 고칠 문제가 아니라 **용량 문제**다.

#### ⑤ 무엇을 포기했나 ★

- **느린 상대에게 계속 왕복 비용을 치른다.** 2초짜리 호출이 리스너 스레드 6개를
  계속 붙들고, 외부 송금은 밀린다(재측정에서 외부 p99 54초).
- **"상대가 아픈 것"을 회로 상태로 못 본다.** 느림은 회로가 아니라 호출 지연
  히스토그램으로만 보다. 대시보드에서 둘을 같이 놓아야 한다.
- 상대가 **3초 바로 아래에서 계속 노는** 최악의 경우, 우리는 영원히 안 끊는다.
  이건 알고 남겨둔 구멍이다 — 그때는 read-timeout 자체를 다시 재야 한다.

#### ⑥ 어떻게 확인했나

| 무엇 | 결과 |
|---|---|
| 2초 지연 · 30 TPS | 회로 CLOSED · 실패 0 — **안 열리는 것이 맞다** |
| 같은 조건의 내부 송금 | p99 **2,580ms** · 성공률 **1.00** — 피해가 외부에 갇혀 있다 |
| 5xx 연속 실패 | 회로 OPEN · 차단 801건 · 전부 미전송 — **틀린 상대는 끊는다** |
| 상대 정상화 | 45초 뒤 CLOSED, 320건 전부 해소, 대사 0건 |

**"안 열렸다"와 "못 열린다"는 다르다.** 열려야 할 때(5xx) 여는 것을 같은 실행에서
확인했기 때문에, 안 여는 쪽을 결정으로 남길 수 있다.

### D-004 · 잔액은 분산 락 + 행 락 두 겹으로 지킨다 (Phase 6.7에서 행 락을 더했다)

> **2026-09-13에 바꿨다.** 아래 "바꾸기 전 결정"은 분산 락 + 낙관적 락이었고, 그 ⑤에 열린 질문으로
> 적어둔 것 — *"같은 DB 안의 한 행을 지키는 데 분산 락은 과하다"* — 을 Phase 6.7이 쟀다.
> 한때 분산 락을 걷어내는 쪽(`PESSIMISTIC` 단독)으로 구현까지 했다가, 소유자 결정으로
> **둘 다 쓰는 쪽(`LAYERED`)**으로 갔다. 걷어낸 구현은 `refs/backup/phase-6-7-step3-remove-redis`에 있다.
> 바꾸기 전의 판단과 숫자는 지우지 않는다. 무엇이 바뀌었는지가 이 기록의 값이다.

**면접 한 줄**: "잔액을 Redis 분산 락으로 줄 세우고, 트랜잭션 안에서 행 락(`SELECT ... FOR UPDATE`)을
한 번 더 잡는다. 둘은 하는 일이 다르다 — Redis 락은 **기다리는 줄을 DB 밖에 세워** 대기 중에
커넥션을 쥐지 않게 하고, 행 락은 **락 수명이 트랜잭션과 같아** Redis 락이 먼저 사라져도(연장 실패 · 장애 전환 · 폴백) 막는다.
전에는 그 틈을 `@Version`이 충돌 → 재시도로 막았는데, 이제는 기다림으로 막는다.
**정합성이 더 좋아진 것은 아니다** — 둘 다 lost update는 막는다. 막는 자리가 예외 경로에서
정상 경로로 옮겨왔다."

**결정**: `LAYERED`(Redis 락 + 행 락)를 기본값으로 · **근거**: 소유자 결정 (2026-09-13).
**측정이 시킨 선택이 아니다** — 아래 "무엇을 포기했나"

#### 두 락이 맡는 일

| 겹 | 무엇 | 막는 것 |
|---|---|---|
| 1 | Redis 락 (Redisson, 조각 단위, 트랜잭션 밖) | 줄을 DB 밖에 세운다 — 기다리는 동안 DB 커넥션을 쓰지 않는다. 락이 새도 되는 **효율용** 락이다 (D-006) |
| 2 | 행 락 (`FOR UPDATE`, 트랜잭션 안) | Redis 락이 먼저 사라진 틈(watchdog 연장 실패 · 장애 전환 · 폴백) — 락 수명이 트랜잭션과 같다 |
| — | `@Version` | 막지 않는다. 행 락 뒤에서는 날 수 없는 충돌이라 **탐지기**다 |

`LayeredLockStrategyTest`가 2번을 흉내 내 확인한다 — Redis를 거치지 않은 트랜잭션이 행을 쥔
동안 들어온 입금은 행 락에서 기다렸다가 새 값을 읽어, `@Version` 충돌이 0건이다.

#### 무엇을 재고 무엇이 나왔나 (Phase 6.7 Step 2)

같은 jar(`b5b343e`), 서버 안에서 부하, 핫 계좌 8조각, 워밍업은 버렸다. ROADMAP이 정한 판정 순서대로다.

| 순위 | 지표 | DISTRIBUTED | PESSIMISTIC | |
|---|---|---|---|---|
| 1 | account 풀 pending 최대 | 0 | **0** | 통과 — 이 전략의 실패 모드(풀 고갈)가 안 나왔다 |
| 2 | 교착 · 락 포기 | 교착 0 · Redis 락 타임아웃 3·2건 | 교착 0 · 행 락 타임아웃 1건 | 둘 다 0은 아니다. 경합으로 재시도돼 갇힘으로 가지 않았다 |
| 3 | 갇힌 송금 · 대사 불일치 · 낙관적 충돌 | 0 · 0 · 0 | **0 · 0 · 0** | 통과 — 탐지기(`@Version`)가 조용하다 |
| 4 | 종결 p99 (60 / 70 TPS) | 10.5·8.0초 / 13.0초 | 9.4초 / 9.5초 | **판정 불가** — 아래 |
| 5 | 처리량 | 미발사 7~64 | 미발사 21~123 | 판정 불가 |

**4순위는 측정으로 판정하지 못했다.** 기준선인 DISTRIBUTED도 60 TPS에서 SLO(5초)를 깼고
(08-24에는 3.1~3.4초로 통과했던 조건이다), 전 실행에서 미발사가 0이 아니었으며,
같은 DISTRIBUTED 60 TPS가 20분 사이 10.5 → 8.0초로 움직여 **드리프트가 두 전략의 차이보다 컸다.**
말할 수 있는 것은 **"PESSIMISTIC이 더 나빴던 실행은 없었다"**까지다.

**`LAYERED`는 이 표에 없다.** Step 2는 DISTRIBUTED와 PESSIMISTIC을 비교했고, 그 결과로 PESSIMISTIC
단독 + Redis 락 제거까지 구현했다. 그 뒤 소유자가 두 락을 함께 쓰기로 정했다 — `LAYERED`는
두 측정 대상을 합친 것이지만, 합친 것 자체는 재지 않았다.

#### 무엇을 포기했나 ★

- **장치가 셋이다** (Redis 락 · 행 락 · `@Version`). Phase 6.7이 원래 줄이려던 것이 이것이었다 —
  "무엇이 무엇을 막는지"를 계속 설명해야 한다
- **Redis가 잔액 경로에 남는다.** 다만 Redis가 죽어도 멈추지는 않는다 — 락을 잡는 단계에서 닿지 못하면
  행 락만으로 진행한다(폴백, D-006). 그동안은 줄 세우기가 빠져 요청이 DB에서 기다린다
- **요청마다 Redis 왕복이 붙는다.** 우리 구현은 50ms 폴링이라 한 번에 못 잡으면 락이 곧 풀려도
  50ms를 채운다 (08-31 측정에서 12.6%)
- **측정 근거 없이 기본값이 됐다.** `LAYERED`가 막으려는 문제 — 행 락 대기 중 커넥션 점유 — 는
  PESSIMISTIC 단독의 60·70 TPS 측정에서 나타나지 않았다(pending 0). 그 문제가 가장 드러날
  1조각 핫 계좌는 재지 않았다
- **교착이 생길 수 있다.** 두 락 모두 조각 번호 순서로 잡아 막는다. PESSIMISTIC 측정에서 교착 0건

#### 언제 다시 보나

- **`LAYERED`를 재서 PESSIMISTIC 단독과 차이가 없을 때** — Redis 락을 뺄 근거다. 걷어낸 구현이
  백업 ref에 그대로 있다
- `remittance.balance.lock.failure`가 **폴백 중이 아닌데 뜰 때** — Redis가 줄을 세우는데도 행 락에서
  포기했다면 Redis 락이 먼저 사라진 틈이 실제로 있다는 뜻이다. `remittance.lock.release{lost}`를 함께 본다
- ~~**Redis 장애가 잔액 경로를 실제로 멈출 때**~~ — 폴백으로 멈추지 않게 했다 (2026-09-14, D-006)
- **잔액이 여러 저장소로 갈라질 때** — 그때는 분산 락이 원래 값(여러 저장소에 걸친 자원)을 되찾는다

#### 바꾸기 전 결정 (2026-08-24 ~ 09-13) — 분산 락 + 낙관적 락으로 지킨다 (비관적 락을 안 쓴 이유)

**면접 한 줄(당시)**: "잔액 갱신을 Redis 분산 락으로 직렬화하고 `@Version`을 한 겹 더 뒀다.
락이 **TTL 기반**이라 임계 구역이 TTL을 넘기면 풀린 채로 진행되는데, 그때 낙관적 락이 잡는다.
비관적 락(`SELECT ... FOR UPDATE`)을 안 쓴 이유는 정합성이 아니라 **측정** 때문이다 —
락 대기가 최대 51ms에 획득 실패 0건이라 경합이 낮았고, 진짜 경합 지점인 핫 계좌는
락을 바꾸는 대신 **잔액을 8조각으로 갈라** 25 → 70 TPS로 풀었다."

**결정**: 비관적 락으로 **바꾸지 않는다** · **근거**: Phase 5 baseline · Phase 6 핫 계좌 측정

#### ① 먼저 오해를 하나 걷어낸다 — 낙관적 락은 정합성을 떨어뜨리지 않는다

**둘 다 lost update를 막는다.** 다른 것은 정합성이 아니라 **실패 모드**다.

| | 비관적 (`SELECT ... FOR UPDATE`) | 낙관적 (`@Version`) |
|---|---|---|
| 충돌하면 | **기다린다** | **실패하고 재시도한다** |
| 위험 | 락 대기 · 데드락 | 경합이 심하면 **재시도 폭풍**으로 처리량이 무너진다 |
| 유리한 조건 | 충돌이 잦을 때 | 충돌이 드물 때 |

그러니 물어야 할 것은 *"어느 쪽이 안전한가"*가 아니라 **"우리 경합이 잦은가"**이다.

#### ② 우리는 낙관적 락"만" 쓰지 않는다

`AccountService.guarded()`는 두 겹이다.

```
Redis 분산 락 (계좌·조각 단위)   ← 1차. 정상 경로를 아예 직렬화한다
        └─ @Version (조각 엔티티)  ← 2차. 락이 풀린 채 진행된 경우를 잡는다
```

**2차가 있는 이유가 핵심이다.** 우리 분산 락은 `SET NX PX`, 즉 **TTL 기반**이라
임계 구역이 TTL을 넘기면 **락이 풀린 채로 작업이 계속된다**(watchdog이 없다).
그때 마지막으로 막는 것이 `@Version`이다.

> 입금은 **고른 조각 하나**만 잠그고, 출금은 **전 조각**을 잠근다 —
> 합을 보고 여러 조각에서 빼기 때문이다. **쪼갠 이득이 출금에는 없다**는 것이 그 대가다.

#### ③ 어떤 대안을 봤나

| 후보 | 판단 |
|---|---|
| **지금대로 (분산 락 + 낙관적 락)** | ← 유지. 측정상 경합이 낮고, 핫 계좌는 샤딩으로 이미 풀렸다 |
| **비관적 락으로 단순화** (`FOR UPDATE`) | 장치가 셋(Redis 락·`@Version`·재시도)에서 하나로 준다. **Redis 의존과 TTL 문제가 사라진다.** 대신 **DB 커넥션을 락 대기 동안 붙든다** — 지금은 Redis가 대기를 흡수하는데, 옮기면 커넥션 풀 30이 다시 병목이 될 수 있다 |
| 분산 락만 (낙관적 제거) | TTL이 풀린 경우를 막을 것이 없어진다. **가장 나쁘다** |
| **🔁 Redisson** | watchdog·재진입을 얻지만 **락이 병목이 아니면 값이 없다**(`⏭️` 조건부, ROADMAP) |

#### ④ 왜 이걸 골랐나

**측정이 경합이 낮다고 말했다.**

```
baseline (Phase 5)   락 대기 최대 51ms · 획득 실패 0건 · 실패로 인한 재시도 0
```

낙관적 락이 불리해지는 조건(충돌이 잦음)이 **관측되지 않았다.**
그리고 진짜로 경합이 심한 자리(핫 계좌)는 **락 방식을 바꿔서가 아니라 경합 자체를 없애서**
풀었다 — 잔액을 8조각으로 갈라 25 → 70 TPS(2.8배).

> **"락을 더 좋은 락으로 바꾸는 것"과 "락이 필요 없게 만드는 것"은 다른 선택지다.**
> 후자가 가능하면 그쪽이 낫다.

#### ⑤ 무엇을 포기했나 ★

- **장치가 셋이라 이해하기 어렵다.** 분산 락 · 낙관적 락 · 재시도가 겹쳐 있어
  "무엇이 무엇을 막는지"를 매번 설명해야 한다. `FOR UPDATE` 하나면 설명이 한 줄이다.
- **Redis가 잔액 경로의 의존성이 된다.** Redis가 죽으면 락을 못 잡는다
  (지금은 낙관적 락으로 우회되지만, 그러면 경합 시 재시도가 폭증한다).
- **TTL을 넘기는 임계 구역이 실제로 생기면** 우리가 아니라 `@Version`이 잡는다 —
  즉 **정상 경로가 아니라 예외 경로로 처리된다.**
- ⚠️ **분산 락이 정말 필요한지 자체가 열린 질문이다.** 잔액은 `account_db` **한 곳**에
  있다. 같은 DB 안의 한 행을 지키는 데 분산 락은 과하다 —
  분산 락의 값은 **여러 저장소에 걸친 자원**을 지킬 때 나온다.
  지금 이 구조인 것은 **"패턴을 손으로 만들어본다"는 학습 목적**이 컸다는 점을 인정한다.

#### ⑥ 어떻게 확인했나

| 무엇 | 결과 |
|---|---|
| 경합이 잦은가 | 락 대기 **최대 51ms**, 획득 실패 **0건** (baseline) |
| 낙관적 락만으로도 되나 | `ACCOUNT_LOCK_STRATEGY`로 분산 락을 꺼보는 비교 실험 경로가 코드에 있다 |
| 핫 계좌는 | 락이 아니라 **한 행에 줄 선 것**이 상한이었다 → 샤딩으로 25 → 70 TPS |
| 정합성 | 모든 측정 뒤 drain → 정식 대사에서 **findings 0** |

#### 언제 이 결정을 뒤집나

> 2026-09-13에 바꿨는데, **아래 세 조건 중 어느 것도 아니었다.** 락 대기는 짧았고 Redis도
> 문제를 내지 않았다. 계기는 ⑤의 열린 질문(단순함)이었고, 재본 뒤 한때 분산 락을 걷어냈다가
> 결국 행 락을 **더하는** 쪽으로 갔다. 조건을 성능으로만 적어두면 성능이 멀쩡한 동안 구조를
> 다시 볼 기회가 오지 않는다는 것은 이번에 배웠다.

- 락 대기가 **길어지거나** 획득 실패(`outcome=timeout`)가 잡히기 시작할 때
- Redis가 잔액 경로의 **단일 장애점**으로 실제 문제를 낼 때
- 수평 확장에서 **Redis가 병목**이 될 때 (제한 카운터와 락이 같은 Redis를 쓴다 — ROADMAP)

### D-005 · Redisson을 지금은 넣지 않는다 (근거였던 문제가 0으로 측정됐다)

> **2026-09-14 — 뒤집었다. 다만 아래 조건 때문이 아니다.** `lost`는 여전히 0이고 대기가 종결 p99를
> 좌우한다는 측정도 없다. 소유자가 Redisson을 넣기로 정했다(처음엔 Sentinel과 함께, 같은 날 Sentinel은 실험용으로 내렸다) → **D-006**.
> 이 기록은 "측정이 교체를 보류시켰던 판단"으로 남긴다 — 뒤집은 근거가 측정이 아니라는 것까지가 기록이다.

**면접 한 줄**: "직접 만든 `SET NX PX` 락을 Redisson으로 갈아타려고 했다. 근거는
**watchdog** — 우리 락은 TTL 기반이라 임계 구역이 TTL보다 길면 락이 풀린 채로 진행되는데,
그게 **에러율에도 대사에도 안 나타나서** 있는지 없는지조차 몰랐다. 그래서 교체 전에
**해제 실패를 세는 카운터를 먼저 넣었다.** 재봤더니 34,200번 놓는 동안 **0건**이었다.
막으려던 문제가 없었으므로 교체를 보류했다. **측정이 교체를 취소시킨 사례**다."

**결정**: Redisson으로 **지금은 바꾸지 않는다**(취소가 아니라 `⏭️` 조건 대기)
· **근거**: 2026-08-31 측정 (`PROGRESS.md`의 "락은 안 새고 있었다")

#### ① 무엇을 재고 무엇이 나왔나

```
70 TPS · 8조각 · 데워진 상태 · 두 실행 누적
  release{released}  34,200      release{lost}  0     ← watchdog이 막으려던 것
  wait{acquired}     34,200      wait{timeout}  0
  최대 대기 605ms                 LOCK_TTL 3초        ← 여유 5배
```

**`lost`가 0이라는 건 임계 구역이 TTL을 넘긴 적이 없다는 뜻이다.** watchdog은 그 상황을
없애주는 장치이므로, **없는 상황을 없애주는 값**은 0이다.

#### ② 남은 근거는 하나뿐이고, 그 크기도 쟀다

```
대기 분포 (34,200건)
     ≤ 1ms   27,077   79.2%
   1 ~ 5ms    2,732    8.0%
  5 ~ 50ms       90    0.3%   ← 비어 있다
 50 ~ 100ms   2,774    8.1%   ← 여기 몰린다
100 ~ 250ms   1,403    4.1%
```

`RETRY_INTERVAL`이 50ms라 **한 번에 못 잡으면 락이 5ms 만에 풀렸어도 50ms를 채운다.**
그 몫이 **4,301건(12.6%)**이다. Redisson의 pub/sub 대기는 이걸 지운다 —
**그러나 종결 p99는 2,714ms이다.** 12.6%에 붙는 수십~수백 ms는 **지배 요인이 아니다.**

#### ③ 왜 그래도 안 하나 — 이 저장소의 잣대를 나에게도 적용한다

한도 서비스(Phase 6.6)와 Config Server(Phase 4)를 자른 이유가 **"아직 아프지 않다"**였다.
같은 잣대를 여기 들이대면 Redisson도 **지금은 근거가 약하다.**

> *"손댈 때 무엇으로 할지는 현업 기술이 기본"*은 **손대기로 정한 뒤에** 적용되는 규칙이다.
> **손댈 이유 자체를 만들어주지는 않는다.** 이 둘을 섞으면 "표준이니까 넣었다"가 된다.

#### ④ 언제 이 결정을 뒤집나 (조건)

- **`release{lost}`가 0이 아니게 될 때** — TTL 누수가 실재하면 watchdog 근거가 되살아난다
- **`wait{timeout}`이 잡히거나 대기가 종결 p99의 유의미한 몫이 될 때** — 그때는 폴링이 근거가 된다
- **재진입이 실제로 필요해질 때** — 지금 `guarded()`는 중첩 락을 쓰지 않는다

**감시는 이미 붙어 있다.** 카운터와 대시보드 패널이 그대로 남으므로,
조건이 오면 **누가 찾아보지 않아도 보다.** 그것이 1번 작업이 남긴 값이다.

### D-006 · 분산 락은 Redisson으로, Redis가 없으면 행 락만으로 (소유자 결정 · 측정 전)

> **같은 날 한 번 줄였다 (2026-09-14).** 처음에는 Sentinel(주 1 · 복제 1 · Sentinel 3)을 운영 구성으로 뒀다.
> 그런데 폴백을 넣고 나니 Redis를 쓰는 두 곳 — 잔액 락과 게이트웨이 요청 제한 — 이 **모두 Redis 없이
> 맞게 돈다.** 노드 다섯이 더해 주는 것이 "폴백 상태를 몇 초로 줄이는 것"뿐이고, 한 머신이라 머신 장애도
> 못 막는다. 그래서 기본은 **단일 Redis + 폴백**으로 두고, Sentinel은 설정 한 줄로 켜는 **장애 전환
> 실험용 오버레이**로 내렸다. 코드는 두 모드를 모두 지원한다.

**면접 한 줄**: "직접 만든 `SET NX PX` 락을 Redisson으로 갈아탔다. 이 락은 **효율용**이고 정합성은 뒤의
행 락이 지킨다(D-004) — 그래서 Redis에 닿지 못하면 락 없이 행 락만으로 진행한다(폴백). 잔액 락도 게이트웨이
요청 제한도 Redis 없이 맞게 돌기 때문에 **Redis 고가용성은 필수가 아니었다.** Sentinel은 설정 한 줄로 켤 수
있게 두고 평소엔 단일 노드로 운영한다. ZooKeeper 같은 합의 기반 락은 효율용 락에 과한 보장이다."

**결정**: Redisson 4.7.0(코어만) + **Redis에 닿지 못하면 행 락만으로 진행(폴백 · 회로 차단기)**.
Redis는 **단일 노드가 기본**이고, Sentinel(주 1 · 복제 1 · Sentinel 3)은 `docker-compose.sentinel.yml`로 얹는 실험용
· **근거**: 소유자 결정 (2026-09-14). D-005의 뒤집는 조건(`lost` ≠ 0, 대기가 p99의 몫)은 **오지 않았다**

#### ① 문제

- **Redis가 하나다.** 죽으면 락을 못 잡아 잔액 변경이 멈춘다. 코드상 Saga 컨슈머는 Redis 연결 예외를
  경합으로 보지 않으므로 1·2·4초 재시도 뒤 DLT로 보낸다 — 7초 넘게 멈추면 송금이 `DEBIT_COMPLETED`에
  갇힌다(측정한 것은 아니다). 게이트웨이 요청 제한도 같은 Redis를 쓴다(그쪽은 fail-open)
- **자체 락의 한계 둘** — watchdog이 없어 임계 구역이 TTL보다 길면 락이 풀린 채 진행되고,
  못 잡으면 50ms마다 다시 물어 락이 5ms 만에 풀려도 50ms를 채운다(08-31 측정 12.6%)

#### ② 자체 구현이 가르쳐준 것

- **남의 락은 지우지 않는다** — Lua로 토큰을 비교해 지웠다. Redisson은 소유 스레드를 비교해 같은 일을 한다
- **대기와 보유를 나눠 재야 처방이 갈린다** — 지표 이름(`remittance.lock.wait/hold/release`)을 그대로 뒀다.
  바꾸면 지나간 기록의 숫자와 이어지지 않는다
- **새는지는 세어야 안다** — `lost` 카운터가 08-31에 34,200건 중 0을 냈고, 그게 D-005의 보류 근거였다.
  이제 `lost`는 "watchdog이 연장하지 못함"(Redis 단절 · 장애 전환)을 센다

#### ③ 대안 비교

| 후보 | 판단 |
|---|---|
| **Redisson + 단일 Redis + 폴백** | ← **선택.** watchdog + pub/sub 대기. Redis가 죽으면 행 락만으로 진행한다. 새 인프라가 없다 |
| Redisson + Sentinel 상시 | 처음엔 이걸 골랐다 → **같은 날 실험용 오버레이로 내렸다.** 폴백 뒤에는 Sentinel이 더해 주는 것이 "폴백 구간을 몇 초로 줄이는 것"뿐이다. 게이트웨이도 fail-open이라 Redis 없이 멈추지 않는다. 그 대가로 노드 다섯(주 · 복제 · Sentinel 셋)을 한 머신에 두는데, 머신 장애는 못 막는다. 코드는 설정만으로 이 모드를 지원한다(Lettuce도 설정만) |
| ZooKeeper (Curator) | 락 자체가 합의로 안전하다 — **효율용 락에는 과한 보장**이다. 앙상블 3대를 새로 운영해야 하고, Kafka 4.x가 ZooKeeper를 없앤 스택에 되들이는 셈이다 |
| Redlock (독립 Redis 여럿) | 효율용 락에는 과하고, 안전성에 대한 반론(Kleppmann, 2016)도 있다 |
| Redis Cluster | 샤딩이 필요할 만큼 데이터가 크지 않다 |

#### ④ 왜 이걸 골랐나

- **락이 새도 되는 구조라서 Redis 없이도 돈다.** Redis에 닿지 못하면 락을 건너뛰어도 행 락이 두 번째
  요청을 기다리게 한다. 같은 이유로 Sentinel을 켰을 때의 약점(장애 전환 중 비동기 복제로 락이 사라짐)도
  받아들일 수 있다. LAYERED가 아니었다면 둘 다 안전하지 않다
- **Redis를 쓰는 두 곳이 모두 Redis 없이 맞게 돈다** — 잔액 락은 폴백, 게이트웨이 요청 제한은 fail-open.
  그래서 Redis 고가용성은 "필수"가 아니라 "폴백 구간을 줄이는 선택"이다. 설정 키가 `spring.data.redis.*`
  하나라, Sentinel을 켜도 둘이 다른 주 노드를 볼 수 없다
- **스타터가 아니라 코어만 쓴다** — Boot 4용 자동 설정에 기대지 않고 `RedissonClient`를 직접 조립한다
  (D-002와 같은 방식). 모드는 설정만 보고 고른다(`RedissonConfig`)

#### ⑤ 무엇을 포기했나 ★

- **측정 근거 없이 넣었다.** D-005가 보류한 이유는 그대로다. 얻는 것을 숫자로 보인 적이 없다
- **의존성이 늘었다.** Redisson 코어가 Kryo · RxJava · Jackson 2를 끌고 온다. Netty는 Boot BOM이
  4.2.15로 고정한다(Redisson 4.7.0은 4.2.16 기준) — 테스트는 통과했지만 어긋나 있다
- **Redis 클라이언트가 서비스마다 다르다.** account는 Redisson 하나(락 + `/actuator/health`), gateway는
  Lettuce(요청 제한)다. 둘 다 `spring.data.redis.*`를 읽지만 `RedissonConfig`는 host · port · sentinel만 읽는다 —
  timeout · password · ssl · database는 gateway만 따라간다.
  처음엔 account에도 health용 Lettuce(스타터)를 두었다가 **2026-09-15에 뺐다.** 설정이 둘이라 health와 락이
  다른 말을 했다 — 09-14 장애 시험에서 그 Lettuce에만 명령 타임아웃이 없어 health가 60초 붙들렸고, 비밀번호가
  걸린 Redis에서는 health가 UP인데 락은 폴백이었다(`RedisHealthIndicatorTest`로 재현). 이제 account health는
  락과 같은 연결로 주 노드에 PING한다
- **Redis health를 직접 만들었다.** Boot가 주는 Redis health는 Spring Data Redis 위에서 돈다. 쓰려면 스타터(Lettuce)나
  `redisson-spring-data` 연결 팩토리가 필요한데, 앞은 클라이언트가 다시 둘이 되고 뒤는 "코어만 쓴다"와 어긋난다.
  `RedisHealthIndicator` 한 클래스다
- **watchdog 타임아웃 5초** — 락을 쥔 인스턴스가 죽으면 그 조각이 최대 5초 막힌다(자체 구현 TTL 3초보다 길다)
- **Redis 고가용성은 없다.** 기본 구성에서 Redis가 죽어 있는 동안은 폴백(줄 세우기 없음)이고 게이트웨이
  요청 제한이 꺼진다(fail-open). 게이트웨이를 지나는 요청은 그동안 하나하나 명령 타임아웃(1초)을 기다린 뒤
  지나간다 — 끊긴 동안의 명령도 줄을 서기 때문이다(2026-09-14 홈서버, 타임아웃을 넣기 전에는 60초). Sentinel 오버레이를 켜면 이 구간이 장애 전환 몇 초로 줄지만, 한 머신에
  노드 다섯이라 머신 장애는 여전히 못 막는다. 운영이라면 관리형 Redis의 다중 AZ 구성으로 받을 자리다
- **Redis가 통째로 죽어도 멈추지 않게 했다 — 대신 줄 세우기가 빠진 채 돈다.** 락을 잡는 단계에서 Redis에
  닿지 못하면 행 락만으로 진행하고(폴백, LAYERED에서만), 연속 3번이면 회로를 열어 5초 동안 부르지 않는다.
  그동안 요청이 DB에서 줄을 서므로 커넥션 대기가 늘 수 있다 — `remittance.balance.lock.fallback`이
  0이 아니면 그 상태다. 송금 도메인에서 보호 장치 때문에 송금이 멈추면 안 된다는 소유자 판단이다
- **Redis 없이도 뜨게 했다** — 연결을 첫 사용 때로 미뤘다(lazy). 대신 기동이 성공해도 Redis가 살아
  있다는 뜻은 아니다. `/actuator/health`의 Redis 항목으로 본다(쿠버네티스 readiness에는 넣지 않는다 —
  넣으면 Redis 하나에 account 전체가 트래픽에서 빠진다)
- **Sentinel 모드는 평소에 돌지 않는다** — 모드를 고르는 분기만 단위 테스트로 고정했고, 실제 장애 전환은
  홈서버에서 오버레이를 얹었을 때만 본다. 안 쓰는 경로는 썩기 쉽다는 것을 받아들였다

#### 언제 뒤집나

- **폴백 구간이 받아들일 수 없을 때** — Redis 장애 시험에서 커넥션 대기가 SLO를 깨거나, 게이트웨이 요청
  제한이 꺼지는 것(fail-open)이 받아들일 수 없게 되면 Sentinel(또는 관리형 다중 AZ)을 **기본으로 올린다.**
  코드는 그대로이고 설정만 바꾼다. **2026-09-14 40 TPS에서는 오지 않았다** — pending 0 · SLO 통과.
  60 TPS 이상은 아직 안 쟀다. 게이트웨이를 지나는 요청은 장애 동안 1초씩 늦는다 — 부하로는 안 쟀다
- 장애 전환 시험에서 **클라이언트가 새 주 노드를 따라가지 못할 때** — Sentinel 모드를 코드에서 뺀다
- Redisson이 **Boot 업그레이드를 막을 때** — 코어만 쓰므로 바꿀 곳은 `DistributedLock`과 `RedissonConfig` 둘이다
- LAYERED를 재서 **Redis 락을 뺄 때**(D-004) — 그러면 Redisson은 필요 없어지고, Redis는 게이트웨이를 위해 남는다.
  account의 Redis health(`RedisHealthIndicator`)도 함께 뺀다 — account가 Redis를 안 쓰면 볼 이유가 없다

### D-007 · Outbox 릴레이를 커밋이 깨운다 — 폴링은 안전망으로 (소유자 결정 · 측정 전)

**면접 한 줄**: "Outbox 릴레이가 500ms마다 폴링해서, 요청이 밀리지 않을 때도 커밋된 이벤트가 다음 주기까지
기다렸다. 송금 한 건이 Kafka를 세 번 건너니 종결에 폴링 몫만 최대 1.5초가 붙었다. CDC로 가면 없앨 수 있지만
Kafka Connect라는 인프라가 하나 는다. 그래서 먼저 **커밋 직후 릴레이를 깨우는** 것만 넣었다 — Outbox에 먼저
적는 건 그대로라 유실 0 보장은 안 바뀌고, 주기는 전송 실패를 줍는 안전망으로 남겼다. 대가는 릴레이가
스케줄러를 떠나 전용 스레드가 됐다는 것, 요청이 적당할 때 배치가 작아져 트랜잭션이 는다는 것이다."

**결정**: Outbox 행이 커밋되면 릴레이를 깨운다(`OutboxRelayLoop`) · 500ms 주기는 안전망으로 유지 · transfer · account 두 벌
· **근거**: 소유자 결정 (2026-09-15). 폴링이 병목이라는 측정은 아직 없다 — **측정 전**

#### ① 문제

- **폴링 대기가 종결의 바닥이다.** 적체가 없으면 커밋된 행이 다음 주기까지 0~500ms를 기다린다. 송금 한 건이
  `requested` → `debited` → `credited` 세 홉을 건너므로 최대 1.5초다(SLO.md ②). 40 TPS 종결 p99 2,048ms
  (2026-09-14 기준선)의 상당 부분이 여기라고 본다 — **나눠 잰 적은 없다**
- 이 바닥은 부하와 반대로 움직인다. 요청이 밀리면 릴레이가 배치를 이어서 비우므로 대기가 없다(Phase 6 Step 2).
  **덜 붐빌수록 커 보이는 지연**이다
- 계기는 "결제 도메인은 p99 200ms"라는 비교였다. 그 숫자는 접수(동기) 기준이라 이 변경과 무관하다 — 여기서
  줄이는 것은 종결이다. 목적은 SLO(5초)를 지키는 것이 아니라 **비동기인데도 사용자에게 거의 동기처럼 보이게**
  하는 것이다

#### ② 자체 구현이 가르쳐준 것

- **주기가 정하는 것은 처리량이 아니라 무부하 지연 바닥이다** — 2026-09-11에 "500 → 200ms로 줄였다"는 기록이
  실행된 적 없는 실험이었음을 찾으면서 갈랐다. 그래서 바닥을 없애는 데 주기를 건드릴 필요가 없었다
- **Outbox의 보장은 테이블과 폴링이 한다** — 깨우기는 그 위에 빨라지는 길을 하나 더할 뿐이라, 신호가 사라져도
  늦을 뿐 빠지지 않는다. 이걸 알기 때문에 "커밋 뒤 직접 발행"(원자성이 깨짐)과 구분할 수 있다

#### ③ 대안 비교

| 후보 | 판단 |
|---|---|
| **커밋 뒤 릴레이 깨우기 + 주기 유지** | ← **선택.** 인프라가 늘지 않는다. 보내는 코드(`OutboxBatchPublisher`)는 그대로라 `SKIP LOCKED` · 순서 · 첫 실패에서 멈추기가 안 바뀐다 |
| 커밋 뒤 그 행만 바로 보내기 | 보내는 길이 둘이 된다. 같은 송금의 뒤 이벤트가 앞질러 나갈 수 있다(견디지만 새로 생기는 경우다). **이벤트마다 발행 표시 커밋이 하나씩** 는다 — 핫 계좌 입금 시간의 63%가 이미 커밋이었다 |
| 주기를 줄인다 (500 → 50ms) | 트래픽이 없어도 빈 조회가 10배다. SLO.md가 이미 거절한 길이다 |
| CDC (Debezium) | 폴링 조회 · 발행 표시 · 테이블이 자라는 문제까지 없앤다. 대신 Kafka Connect · binlog 운영이 붙는다 — **깨우기로 모자란다는 숫자가 나온 뒤**로 미뤘다(교체 예정 5번) |
| Outbox 없이 커밋 뒤 직접 발행 | 커밋과 발행 사이에 죽으면 이벤트가 사라진다. Outbox를 쓰는 이유가 없어진다 |

#### ④ 어떻게 깨우나

```
업무 트랜잭션:  … + outboxEventRepository.save(행)   ← Spring Data가 @DomainEvents 신호를 낸다
                → 커밋
                   └ @TransactionalEventListener(AFTER_COMMIT) → 자리 하나짜리 큐에 표시
릴레이 스레드:  표시가 오거나 500ms가 지나면 한 바퀴 (OutboxRelay.publishPending — 전과 같은 코드)
```

- **커밋 뒤에만 깨운다.** 커밋 전에 깨우면 릴레이는 아직 안 보이는 행을 찾다 빈손으로 돌아가고, 그 행은 다음
  주기를 기다린다 — 효과가 조용히 사라진다. 시험이 이것을 가른다(⑥)
- **쓰는 곳을 고치지 않았다.** 행을 적는 네 곳(transfer 1 · account 3)이 모두 `save`를 거치므로 엔티티가 신호를
  낸다. 새로 적는 곳이 생겨도 따로 부를 필요가 없다
- **신호는 합쳐진다.** 큐의 자리가 하나라 한 바퀴 도는 사이 커밋이 여럿 와도 다음 한 바퀴가 한 배치로 가져간다

#### ⑤ 무엇을 포기했나 ★

- **릴레이가 스케줄러를 떠났다 — 스레드의 생사를 우리가 맡는다.** 신호를 기다리며 스레드를 쥐어야 해서
  `@Scheduled`를 버리고 전용 스레드로 돌린다(스케줄러에서 기다리면, 스레드가 하나인 transfer는 보관 기간 정리가
  영영 못 돈다). `@Scheduled`는 예외를 삼키고 다음 주기를 돌려줬지만 이제는 예외가 새면 스레드가 죽고 발행이
  조용히 멈춘다 — 한 바퀴의 예외를 잡게 했고 시험으로 고정했다. 종료도 우리가 한다(`SmartLifecycle`)
- **요청이 적당할 때 트랜잭션이 는다.** 전에는 500ms마다 한 배치였는데 이제 커밋마다 깨어나므로 한 바퀴가
  가져가는 배치가 작다. 바퀴마다 조회 + 발행 표시 UPDATE + 커밋이다. 밀리면 배치가 차서 전과 같다.
  **재지 않았다** — 바퀴 수를 볼 수 있게 `remittance.outbox.relay.runs{trigger=wakeup|interval}`을 넣었다
- **줄어드는 것은 무부하 바닥뿐이다.** 컨슈머 처리 · 커밋 비용 · 폴링 조회는 그대로이고 용량도 늘지 않는다
- **통합 시험의 힘에 조건이 붙는다.** 릴레이를 켠 다른 테스트 컨텍스트가 캐시돼 있으면 그 릴레이가 같은 DB를
  훑어 대신 발행할 수 있다. 그래서 `OutboxRelayWakeupTest`가 결함을 가르는 힘은 그 클래스만 돌릴 때 온전하다.
  루프의 약속은 컨텍스트 없는 `OutboxRelayLoopTest`가 가른다

#### ⑥ 어떻게 확인하나

| 무엇 | 방법 | 결과 |
|---|---|---|
| 커밋되면 주기를 기다리지 않는가 | `OutboxRelayWakeupTest` (두 서비스) — 주기를 10분으로 두고 10초 안에 발행되는가 | 통과 |
| 커밋 전에 깨우지 않는가 | 같은 시험 — 저장한 뒤 커밋을 500ms 미룬다. 커밋 전에 깨우면 빈손으로 10분을 잔다 | 통과 |
| 루프가 신호에 답하는가 · 실패해도 사는가 · 바로 멈추는가 | `OutboxRelayLoopTest` (두 서비스, 컨텍스트 없음) | 통과 |
| 시험이 결함을 잡는가 | 결함 넷을 심었다 — 커밋 전에 깨움(`@EventListener`) · 신호를 안 냄(`@DomainEvents` 제거) · 한 바퀴의 예외를 안 잡음 · 멈출 때 안 깨움 | **넷 다 겨눈 시험이 실패** |
| 기존 동작 | transfer-service 170건 · account-service 275건 (2026-09-15) | 통과 |
| **효과 (홈서버)** | 40 TPS 종결 p99 전후 — 2026-09-14 기준선 2,048ms | **아직 안 했다** |
| **대가 (홈서버)** | 70 TPS 용량이 줄지 않는가 · `relay.runs{trigger=wakeup}` 비율 · 커밋 수 | **아직 안 했다** |

#### 언제 뒤집나

- **40 TPS 종결 p99가 안 움직일 때** — 바닥이 폴링이 아니었다는 뜻이다. 깨우기를 걷어내고 원인을 다시 찾는다
- **70 TPS 용량이 줄 때** — 늘어난 트랜잭션이 원인이면 바퀴 사이에 최소 간격을 둬 배치를 모으거나, 깨우기를 걷어낸다
- **깨운 뒤에도 폴링이 병목일 때** — CDC로 간다 (교체 예정 5번)

### 왜 이 순서인가

**1 → 2 → 3이 한 덩어리였다.** 지금 `@Version`이 하는 일은 *"락이 TTL로 샜을 때 잡는 것"*인데,
**Redisson의 watchdog은 애초에 안 새게 한다.** 그러니 2번을 먼저 하면 3번이 *"비관적으로
바꿀까"*가 아니라 *"2차가 아직 필요한가"*로 질문 자체가 바뀔 예정이었다.
그리고 어느 쪽으로 가든 **1번(탐지기)이 없으면 판단할 근거가 없었다.**

> **★ 2026-08-31에 이 덩어리가 풀렸다.** 1번을 재보니 `lost`가 **0건**이라
> 2번의 근거가 사라졌고(→ **D-005**), 2번이 서지 않으니 3번의 질문도 바뀌지 않았다.
> **1번은 2번을 위한 준비였는데, 결과적으로 2번을 취소시켰다** — 그게 탐지기를 먼저
> 넣은 값이다. 순서를 반대로 했다면 Redisson을 넣고 나서 *"뭐가 좋아졌지"*에
> 답하지 못했을 것이다.
>
> **2026-09-13 ~ 14 — 결국 둘 다 했고, 순서는 3 → 2였다.** 3번(행 락, `LAYERED`)을 먼저 넣어
> `@Version`은 막는 장치가 아니라 탐지기가 됐고(→ **D-004**), 2번(Redisson)은 측정 근거 없이
> 소유자 결정으로 넣었다(→ **D-006**). 둘 다 측정이 시킨 교체가 아니다. 1번의 탐지기는 그대로 남아
> 두 교체 뒤에도 "락이 새는가"를 센다.

**그래서 지금 살아 있는 것은 4번뿐이다.**

**4번은 나머지와 성격이 다르다** — 측정이 아니라 **일정**이 조건이다.
replica를 2로 늘리는 순간 버그이므로 **Phase 8을 시작하기 전에** 끝나 있어야 한다.

**5·6·7은 조건이 아직 안 왔다**(`ROADMAP.md`의 `⏭️`).

### 2 · 맨 `@Scheduled` → ShedLock

> **면접 한 줄**: "Outbox 릴레이와 정합성 대사가 `@Scheduled`로 도는데, 전부 **인스턴스가 하나**라는
> 전제였다. K8s에서 HPA로 replica를 늘리는 순간 같은 이벤트를 두 번 발행하고 대사 회차가
> 중복 생성된다. **스케일 아웃이 곧바로 버그가 되는 상태**라 ShedLock으로 잠금을 걸었다.
> 대신 잠금 저장소가 새 의존성이자 새 장애점이 된다."

**① 문제** — `@Scheduled`가 **열 군데**다 (2026-08-30 기준. 셋이던 것이 계속 늘었다).

```
account/OutboxRelay            Outbox 발행       → replica 2개면 같은 이벤트를 두 번 발행
account/OutboxRetention        보관 기간 정리     → 같은 행을 두 곳에서 지우려 다툰다
account/ExternalCreditProber   모르는 돈 확인     → 상대 은행을 쓸데없이 두 번 두드린다
account/ShardRouter            샤드 갱신
transfer/OutboxRelay           Outbox 발행
transfer/OutboxRetention       보관 기간 정리
reconciliation/Scheduler       대사 회차          → 회차 중복 생성, 같은 어긋남을 두 번 보고
```

> **늘어난 것 자체가 신호다.** 새 배치를 만들 때마다 이 목록이 길어지는데,
> **아무도 "이게 replica에서 어떻게 되나"를 묻지 않았다.** 어제 만든 보관 기간 정리도
> 그대로 여기 들어왔다 — **만든 것이 곧바로 숙제가 됐다.**

**③ 대안**

| 후보 | 판단 |
|---|---|
| **ShedLock** | 스케줄 하나를 클러스터에서 한 번만. Redis/DB를 잠금 저장소로 — **둘 다 이미 있다** |
| 리더 선출 (Kubernetes Lease) | K8s에 묶이다. 로컬 실행이 어려워짐 |
| 스케줄러만 replica 1개 고정 | 그 인스턴스가 죽으면 릴레이가 통째로 멈춘다 |
| Quartz 클러스터 모드 | 스케줄 자체를 DB로 관리 — 지금 필요보다 훨씬 무겁다 |

**⑤ 포기하는 것** — 잠금 저장소 장애 시 스케줄이 안 돈다. 그리고 **잠금 시간을 잘못 잡으면**
작업이 아직 도는데 잠금이 풀려 중복 실행된다(분산 락과 같은 함정).

**왜 Phase 8 전인가** — ROADMAP에 "HPA로 확장성 검증"이 있는데, 이게 없으면 **검증하려는 그
동작이 곧 버그**다.

### 3 · `SET NX PX` + Lua → Redisson

> ✅ **2026-09-14에 바꿨다 → D-006.** 아래는 바꾸기 전에 쓴 계획이라 그대로 둔다.
> 두 가지가 계획과 달라졌다. ⑤의 *"Redis 장애 시 락이 없는 상태"*는 폴백으로 받았다 —
> `LAYERED`에서는 Redis가 없어도 행 락이 남으므로 락이 없는 상태가 아니다. 그리고 "왜 Phase 6인가"의
> 조건(대기와 실패를 숫자로 본 뒤)은 오지 않았다 — 측정이 아니라 소유자 결정으로 바꿨다(D-005).

> **면접 한 줄**: "계좌별 분산 락을 Redis `SET NX PX`와 Lua로 직접 구현했다. 해제 시 단순
> `DEL`을 쓰면 TTL로 제 락이 풀린 뒤 남의 락을 지우게 돼서, 값이 제 토큰일 때만 지우도록
> Lua로 원자성을 맞췄다. **다만 watchdog이 없어** TTL(3초)을 넘기면 락이 풀린 채 작업이
> 계속된다. 낙관적 락이 받아주긴 하지만 그건 방어선이지 설계가 아니라서 Redisson으로
> 갈아탔다. 대신 Redisson 자체가 무겁고 내부 동작이 블랙박스가 된다."

**① 문제** — 코드 주석에 이미 적혀 있다.

> Redisson 같은 라이브러리와 달리 **자동 갱신(watchdog)이 없다.** 따라서 TTL은 임계 구역이
> 걸리는 최대 시간보다 넉넉해야 하고, 그보다 오래 걸리는 작업을 이 락으로 감싸면 안 된다.

DB가 느려져 잔액 변경이 3초를 넘기면 **락이 풀린 채로 작업이 계속된다.**
그리고 대기가 **폴링**이라 경합이 심할수록 Redis를 계속 찌른다.

**③ 대안**

| 후보 | 판단 |
|---|---|
| **Redisson** | watchdog, 재진입, **pub/sub 기반 대기**(폴링 아님), Fair lock |
| 자체 구현 유지 + watchdog 직접 | 만들 수는 있지만 **이미 검증된 걸 다시 만드는** 일이다 |
| DB 비관적 락 (`SELECT FOR UPDATE`) | Redis 의존이 사라지지만 DB 커넥션을 오래 잡는다 — 커넥션 고갈로 직행 |

**⑤ 포기하는 것** — Redisson은 **의존성이 크고** 내부가 블랙박스가 된다. 그리고 여전히
**Redis 장애 시 락이 없는 상태**이므로, 낙관적 락은 그대로 둬야 한다.

**왜 Phase 6인가** — Phase 6 Step 1(핫 계좌)에서 **락 대기 시간과 획득 실패를 숫자로 본 뒤**
바꾼다. 그래야 "watchdog이 없어서 불안했다"가 아니라 **"대기가 얼마였고 실패가 몇 %였다"**로
말할 수 있다.

> ⚠️ 그리고 Phase 6에서 **락을 아예 빼는 실험**을 먼저 한다(낙관적 락 + 재시도만).
> 충돌이 적은 계좌는 그게 더 빠르다는 걸 확인하면, **"락을 더 좋은 락으로 바꾸는 것"과
> "락을 안 쓰는 것"이 다른 선택지**라는 게 드러난다 — 이게 훨씬 나은 답변이다.

### 4 · 손으로 쓴 `openapi.yaml` → springdoc-openapi

> **면접 한 줄**: "API 스펙을 손으로 관리했는데 **이미 코드와 어긋나 있었다** — 새로 추가한
> 개시 이월·알림 엔드포인트가 스펙에 없었다. Gateway가 이 스펙을 계약으로 쓸 예정이라
> 어긋난 채로 두면 안 돼서 springdoc으로 자동 생성으로 바꿨다. 대신 컨트롤러에 애노테이션이
> 늘고, **내부 API를 노출에서 걸러내는 설정**이 따로 필요했다."

**⑤ 포기하는 것** — 스펙이 코드에 종속된다. **설계 먼저(spec-first)가 어려워진다.**
그리고 `/internal/*`이 외부 스펙에 섞이면 그것대로 사고라, 필터링을 반드시 걸어야 한다.

### 5 · 폴링 Outbox 릴레이 → Debezium (CDC)

> **면접 한 줄**: "Outbox 릴레이가 500ms마다 테이블을 폴링한다. 트래픽이 없어도 계속 찌르고,
> 인스턴스를 늘리면 중복 발행된다. 부하 테스트에서 이게 병목으로 잡히는 걸 확인한 뒤
> Debezium CDC로 바꿨다 — binlog를 읽으니 폴링이 사라지고 지연도 커밋 직후로 줄었다.
> 대신 **Kafka Connect라는 인프라가 하나 더** 생겼고, binlog 설정·스키마 변경 대응이라는
> 운영 부담이 붙었다."

**② 자체 구현이 가르쳐준 것** — Outbox **패턴 자체**는 그대로 간다. 바뀌는 건 **발행 방식**뿐이다.
직접 만들어봤기 때문에 "Debezium이 어느 부분을 대신해주는지"를 정확히 말할 수 있다.

**③ 대안**

| 후보 | 판단 |
|---|---|
| **Debezium** | binlog 기반. **우아한형제들이 실제로 쓰는 방식**([출처](https://techblog.woowahan.com/17386/)) |
| 폴링 유지 + 간격 조정 | 지연과 부하를 맞바꿀 뿐 근본이 안 바뀐다 |
| 트랜잭션 커밋 후 직접 발행 | **원자성이 깨진다.** Outbox를 쓰는 이유가 사라진다 |
| Outbox 유지 + 커밋 뒤 릴레이 깨우기 | ← **2026-09-15에 먼저 넣었다 (D-007).** 위와 달리 Outbox에 먼저 적으므로 원자성은 그대로다. 폴링 **대기**만 없앤다 — 폴링 조회 · 발행 표시 · 테이블이 자라는 문제는 남는다 |

> 배민은 순서 보장을 위해 **커넥터당 태스크를 1개로 강제**하고, 처리량을 위해 **outbox 테이블을
> 토픽별로 분리하고 식별자 기반 N개로 샤딩**한다고 한다. 태스크 1개면 그게 병목이 되니
> 테이블을 쪼개 커넥터를 늘리는 구조다 — **면접에서 이 정도까지 말하면 깊이가 보다.**

**⑤ 포기하는 것** — Kafka Connect 클러스터가 새로 뜬다(**새 장애점**). binlog 권한과
`ROW` 포맷 설정이 필요하고, **DB 스키마를 바꿀 때 커넥터가 깨질 수 있다.**

**왜 Phase 6인가** — Phase 5 baseline에서 **50 TPS 천장의 원인으로 지목된 뒤** 바꾸면
"측정하고 고쳤다"는 답변이 된다. 그냥 바꾸면 "좋다길래 썼다"가 된다.

### 6 · Choreography Saga → Temporal / Camunda 8

> **면접 한 줄**: "Choreography로 만들었더니 **흐름 전체를 볼 수 있는 코드가 없고, 타임아웃이
> 없었다.** 응답이 영영 안 오면 대사가 나중에 발견할 뿐 흐름은 멈춰 있다.
> 오케스트레이션으로 바꾸면 흐름이 한 곳에 모이고 타임아웃·재개가 생기지만,
> **지휘자가 단일 장애점이 되고 서비스 간 결합도가 올라간다.** 그래서 지우지 않고 둘을
> 나란히 두고 비교했다."

**③ 대안**

| 후보 | 판단 |
|---|---|
| **Temporal** | Durable Execution. 워크플로가 그냥 자바 코드인데 죽어도 그 줄부터 재개 |
| **Camunda 8 (Zeebe)** | BPMN이 곧 실행 정의. **금융권에서 실제로 많이 쓴다** |
| Eventuate Tram Saga | 오케스트레이션 Saga 전용이지만 **이미 만든 Outbox와 정면으로 겹친다** |
| Axon Framework | 이벤트 소싱 + CQRS까지 딸려온다. 받아들이는 결정이 너무 큼 |
| 직접 구현 | 상태 테이블 + 타임아웃 스케줄러면 된다. **먼저 이걸 해보는 게 순서** |

**⑤ 포기하는 것** — 지휘자가 **단일 장애점**이 된다. transfer가 account의 사정을 알게 되어
**결합도가 오른다.** 지금은 notification을 붙일 때 기존 코드를 한 줄도 안 고쳤는데,
오케스트레이션이면 새 단계마다 지휘자를 고쳐야 한다.

## 도입 대신 **대체**한 것 — CI/CD

기준으로 삼은 스택(토스)에는 GoCD·Jenkins·Harbor·Vault·Spinnaker·Consul·Ceph가 있다.
**전부 세우지 않는다.** 대신 더 가벼운 것으로 대체하고 **왜 대체했는지**를 남긴다.

> **면접에서는 "안 써봤습니다"가 아니라 "원래 것이 주는 가치가 무엇이고, 그중 무엇을
> 어떻게 대신했고, 무엇은 못 얻었는지"를 말하면 된다.** 그게 훨씬 강하다.

| 원래 | 대체 | 원래 것이 주는 가치 | 무엇으로 대신했나 | **못 얻은 것** |
|---|---|---|---|---|
| **Harbor** | GHCR + Trivy | 사내망 격리, 취약점 스캔, 이미지 서명, 지역 복제 | 스캔은 Trivy로 CI에서 | **격리·서명·복제.** 로컬 학습에선 재현 실익이 낮음 |
| **Vault** | Sealed / External Secrets | 동적 시크릿, 자동 회전, 감사 로그, 리스 | 정적 시크릿 암호화까지만 | **회전·감사·동적 발급.** 금융이면 실제로는 필요한 것들 |
| **Spinnaker** | Argo Rollouts | 배포 전략 + **자동 카나리 분석**, 멀티 클라우드 | Rollouts가 Prometheus 보고 단계 승격/롤백 | 멀티 클라우드, 복잡한 파이프라인 오케스트레이션 |
| **GoCD / Jenkins** | GitHub Actions | 파이프라인 as code, 플러그인 생태계, 사내 실행기 | Actions로 동일한 CI | 사내망 실행기, 대규모 팀의 공유 파이프라인 |
| **Consul** | K8s 디스커버리 + Istio | 디스커버리, KV 설정, 헬스체크, 멀티 DC | K8s Service + Istio | **K8s 밖의 워크로드**를 못 다룸. 지금은 전부 안에 있어 무관 |
| **Ceph** | — | 분산 블록·오브젝트 스토리지 | 대체 안 함 | 스토리지 계층. 이 프로젝트 범위 밖 |
| **Istio** | 빼고 별도 학습 | mTLS, L7 트래픽 정책, 카나리, 사이드카 트레이싱 | mTLS 외에는 **적용할 자리가 없음**. 카나리는 Argo Rollouts + Ingress로 | L7 트래픽 정책 전반. 아래 참고 |

### Istio를 뺀 이유 ★ 면접에서 반드시 나온다

토스 스택에 Istio가 있으니 **"왜 안 쓰셨나요?"는 거의 확실히 나온다.** 준비된 답이 필요하다.

> **면접 한 줄**: "서비스 간 동기 호출이 사실상 없는 구조라 메시가 얻을 게 mTLS 정도였다.
> 트래픽 분할은 나눌 서비스 간 트래픽이 없고, 회로 차단은 Kafka 컨슈머에 안 걸려서
> `DefaultErrorHandler`로 이미 하고 있었고, 트레이싱은 사이드카가 있어도 Kafka를 건너면
> 끊겨서 어차피 애플리케이션에서 붙여야 했다. **비용은 다 치르고 배우는 건 적다**고 판단해
> 범위에서 뺐고, 대신 동기 호출이 많은 별도 샘플에서 공부하기로 했다."

| Istio가 주는 것 | 이 프로젝트에서 |
|---|---|
| 트래픽 분할·카나리 | ❌ 나눌 **서비스 간** 트래픽이 없음 (대사의 읽기 조회 하나뿐) |
| 재시도·타임아웃·회로 차단 | ❌ **Kafka 컨슈머에 안 걸림.** 이미 `DefaultErrorHandler`로 처리 |
| 분산 트레이싱 | 🟡 **Kafka를 건너면 끊김.** trace context를 이벤트에 싣는 건 애플리케이션 몫 |
| mTLS | 🟢 이건 됨 — 얻는 게 사실상 이것뿐 |

**중요한 건 "설계가 잘못된 게 아니라 도구가 안 맞는다"는 구분이다.**
비동기 이벤트 중심은 Phase 2의 의도된 선택이고(부분 실패에 강해진다),
Istio는 서비스들이 서로 HTTP/gRPC로 부르는 구조에서 빛난다.

> ⚠️ **Istio를 쓰려고 동기 호출을 만들면 안 된다.** 아키텍처를 도구에 맞추는 건 거꾸로이고,
> 면접에서 **"왜 이벤트 기반인데 동기 호출이 있죠?"**로 되돌아온다.
> "도구가 안 맞아서 안 썼다"가 "도구에 맞추려고 설계를 비틀었다"보다 훨씬 나은 답변이다.

**카나리까지 포기하지는 않는다.** 트래픽 분할은 Ingress로도 되고, 메시가 주는 건
*더 정밀한 분할*이지 *카나리 그 자체*가 아니다 → Phase 9에서 Argo Rollouts로 한다.

### ArgoCD는 실제로 세운다 (Phase 8)

대체하지 않는 이유는 **GitOps가 개념이지 도구가 아니기 때문**이다. 가볍기도 하고,
직접 겪어야 아는 게 있다.

- **Pull 기반** — 클러스터가 Git을 보고 스스로 맞춘다. CI가 클러스터 자격증명을 들고 있을 필요가 없다
- **Drift 감지** — 누가 `kubectl edit`으로 손대면 잡힌다
- **되돌리기가 `git revert`** — 배포 이력이 곧 Git 이력

> **ArgoCD vs Spinnaker는 좋은 면접 소재다.**
> ArgoCD는 **"상태를 맞추는"**(선언형·pull) 쪽이고, Spinnaker는 **"절차를 밟는"**(파이프라인·push)
> 쪽이다. 카나리 자동 분석처럼 **절차가 복잡한 일**은 Spinnaker가 강하고,
> 그래서 Argo 진영도 Rollouts라는 별도 컨트롤러로 그 자리를 메운다.

## 왜 버전에 커밋 해시를 넣지 않았나

**"무엇이 배포됐는지 구분할 수 없다"는 문제는 맞지만, 버전 문자열은 그 답이 아니다.**

| | 무엇을 위한 것인가 |
|---|---|
| **아티팩트 버전** (`0.0.1-SNAPSHOT`) | *제품*이 몇 번째 판인가. 사람이 읽는 것 |
| **이미지 태그** (`github.sha`) | 어떤 이미지를 배포했나. 배포하는 쪽이 쓰는 것 |
| **build-info** (`/actuator/info`) | **지금 떠 있는 이 프로세스가 어느 커밋인가** |

셋째가 진짜 필요한 것이다. 장애 대응 중에 필요한 건 "이 파드에 물어보면 답이 나오는 것"이고,
버전 문자열을 커밋 해시로 바꿔도 **실행 중인 프로세스에 물어볼 수단은 여전히 없다.**

그리고 버전에 해시를 넣으면 커밋마다 아티팩트 이름이 바뀌어 Gradle 캐시가 계속 무효화된다.
얻는 것 없이 빌드만 느려진다.

```
GET /actuator/info
{ "build": { "commit": "9994bacb802f", "branch": "develop", "time": "...", ... } }
```

`BuildInfoTest`가 이걸 고정한다 — 루트 `build.gradle`의 `bootBuildInfo` 설정이 사라지면 빨개진다.
Docker가 필요 없어 `unitTest`에 포함된다.

> **면접 한 줄**: "버전을 커밋 해시로 바꾸는 것도 방법이지만, 정작 필요한 건 **실행 중인 프로세스에
> 물어보는 것**이라 build-info로 심었다. 아티팩트 버전은 제품 버전으로 두고, 이미지 태그는
> 커밋 SHA, 런타임 식별은 `/actuator/info`로 역할을 나눴다."

## 배포 순서 문제 — 이 저장소 고유의 숙제

**독립 배포하기로 해놓고, 계약 변경은 함께 배포해야 하는 모순이 있다.**

공유 모듈을 두지 않기로 해서 `TransferEvents`·`AccountEvents`가 **네 서비스에 중복 정의**되어
있다(`ARCHITECTURE.md` §1). 그래서 이벤트에 필드를 하나 바꾸면:

```
transfer의 이벤트 필드 변경  →  account·ledger·notification도 고쳐야 함
                            →  그런데 배포는 서비스별로 따로 나감
                            →  ★ 배포 사이 구간에 이벤트를 못 읽는 창이 생김
```

CD가 생기면 **바로 이게 첫 사고**가 된다. 지금은 손으로 다 띄우니 안 보일 뿐이다.

| 대응 | 내용 | 비용 |
|---|---|---|
| **하위 호환만 허용** | 필드 **추가만** 되고 삭제·의미 변경 금지 | 규율에 의존. 강제 수단이 없음 |
| **Consumer 먼저 배포** | 읽는 쪽을 먼저 올리고 쓰는 쪽을 나중에 | 배포 순서를 사람이 기억해야 함 |
| **스키마 레지스트리** | Avro/Protobuf로 **빌드 타임에 호환성 강제** | 계약이 코드 밖으로 나감. 지금 구조를 크게 바꿈 |

지금은 `@JsonIgnoreProperties(ignoreUnknown = true)`가 **필드 추가에 한해** 절반을 해주고 있다.
**삭제와 의미 변경은 막을 장치가 없다.** Phase 8에서 CD를 세울 때 정할 문제다.

## 방어하기 어려운 선택 — 미리 준비할 것

**면접에서 반드시 물어볼 것들이다.** 숨기는 것보다 반박을 준비하는 게 낫다.

### "왜 원장(ledger)에 MongoDB를 쓰셨나요?" ★ 가장 위험

금융에서 원장은 정합성의 최후 보루인데, **MongoDB는 단일 노드에서 다중 문서 트랜잭션을 쓸 수
없다.** 실제로 코드 주석에도 그 이유로 Outbox를 안 뒀다고 적혀 있다.
현업 금융 원장은 대부분 RDB + 파티셔닝이다.

**준비할 답** — 이 원장은 **정합성의 원천이 아니라 파생 데이터**다. 원천은 account의
잔액이고, 원장은 그걸 이벤트로 재구성한 것이며, 어긋나면 대사가 잡는다. 조회 트래픽이
압도적으로 몰리는 쪽이라 읽기에 맞춰 골랐다.

> ⚠️ **다만 이 답에는 빈틈이 있다.** 파생 데이터인데 **대사의 한쪽 기준**으로 쓰이고 있어
> 역할이 애매하다. 되물으면 정직하게 인정하는 게 낫다 — "지금 설계의 약점이고,
> 원장을 MySQL로 옮기고 MongoDB는 조회 캐시로 내리는 게 맞다고 본다"까지 준비해둔다.

### "시크릿이 평문으로 커밋되어 있는데요?"

`application.yml`에 `username: root` / `password: root`가 그대로 있다.

**준비할 답** — 로컬 개발용 값이고 운영 자격증명이 아니지만, **변명이 아니라 부채로 보고 있다.**
Phase 8에서 Sealed/External Secrets로 걷어내는 게 계획에 있다. 지금 구조에서도
환경변수로 빼는 건 언제든 할 수 있는데, **컨테이너화 전에 하면 두 번 일이 되어** 묶어뒀다.

> ⚠️ 이건 방어하기보다 **먼저 인정하는 게 낫다.** 금융 도메인을 다루는 프로젝트에서
> 시크릿 관리를 안 했다는 건 지적당하기 딱 좋고, "알고 있고 언제 처리할지도 정해뒀다"가
> 최선의 답이다.

### "왜 Kotlin이 아니라 Java인가요?"

토스는 Kotlin 비중이 높고 배민도 늘고 있다.

**준비할 답** — 분산 시스템 패턴 연습이 목적이라 **언어를 바꾸는 데 드는 시간을 패턴에 쓰기로**
했다. 다만 이 프로젝트의 대부분이 DTO·이벤트 계약이라 Kotlin의 data class와 null 안정성이
잘 맞는 영역인 건 맞다.

### "서비스를 왜 이렇게 잘게 나눴나요?"

5개는 이 도메인 규모에 비해 많다.

**준비할 답** — 서비스 수가 늘 때 생기는 문제(디스커버리, 트래픽 정책, 크로스 서비스 관측)를
겪어보는 게 목적 중 하나였다. **분리 기준은 있다** — 대사는 세 저장소를 가로질러야 해서,
알림은 송금을 막으면 안 돼서다.

### "공유 모듈 없이 DTO를 중복 정의한 이유는?"

**준비할 답** — 공유 모듈은 배포 결합을 만든다. 한 서비스가 필드를 바꾸면 전부 다시 배포해야
한다. 대신 **계약이 어긋날 위험**을 떠안았고, `@JsonIgnoreProperties(ignoreUnknown = true)`로
필드 추가는 견디게 했다. 규모가 커지면 **스키마 레지스트리(Avro/Protobuf)**로 가야 할 자리다.
