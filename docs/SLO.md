# 서비스 수준 목표 (SLO)

**"초당 몇 건 나오나"는 목표가 될 수 없습니다.** 지연을 포기하면 처리량은 얼마든지 나오기
때문입니다. 실제로 이 저장소는 2026-08-23에 종결 처리량을 19 → 80건/s로 올렸는데,
같은 측정에서 **종결 p95가 32.8초**였습니다. 처리량만 보면 성공이고 사용자 입장에서는 실패입니다.

그래서 **처리량·지연·오류율을 묶어서** 겁니다. 이 문서는 그 기준을 정합니다.

## 무엇을 재는가 (SLI)

측정 대상을 먼저 못 박습니다. **어디서 어디까지인지가 흐리면 숫자를 비교할 수 없습니다.**

| 이름 | 정의 | 왜 나눴나 |
|---|---|---|
| **접수 지연** | `POST /transfers` 요청 → `202` 응답 | 사용자가 화면 앞에서 **직접 기다리는 시간** |
| **종결 지연** | `POST /transfers` 요청 → 상태가 `COMPLETED`/`FAILED` | **돈이 실제로 움직이기까지**. 진짜 지표 |
| **접수 오류율** | 2xx가 아닌 응답 ÷ 전체 요청 | 시스템이 요청 자체를 못 받은 비율 |
| **종결 실패** | 시스템 원인으로 `FAILED`가 되거나 끝내 종결되지 않음 | 잔액 부족 같은 **업무적 실패는 제외** |

> **접수와 종결을 반드시 나눠야 합니다.** `POST /transfers`는 접수만 하고 202를 돌려줍니다 —
> 그 시점에 돈은 아직 안 움직였습니다. 접수만 재면 "초당 수천 건"이 나오는데
> 그건 `INSERT` 두 번의 속도일 뿐입니다.

## 목표

| 지표 | 목표 | 성격 |
|---|---|---|
| **접수 지연 p99** | **< 500ms** | 사용자 체감 |
| **종결 지연 p99** | **< 5초** | 사용자 체감 |
| **접수 오류율** | **< 0.1%** | 가용성 |
| **종결 실패율(시스템 원인)** | **0** | 정합성 |
| **유실 · 중복 · 갇힘** | **0** | 정합성 — 타협 불가 |

---

## 각 목표가 무슨 뜻인가

### ① 접수 지연 p99 < 500ms

**뜻**: 100번 중 99번은 0.5초 안에 "접수됐습니다"가 뜬다.

**왜 p99인가** — 평균과 p95만 보면 꼬리를 놓칩니다. 하루 100만 건이면 **1%는 1만 명**입니다.
"100명 중 1명"은 작아 보이지만 **매일 1만 명이 겪는 일**입니다.

**왜 500ms인가** — 접수 한 건은 커넥션을 세 번 잡습니다(키 선점 → 저장+Outbox → 키에 결과 기록).
지금 커밋 하나가 약 14ms이므로 **이론상 바닥은 50ms 언저리**입니다.
500ms는 거기에 **GC·네트워크·순간적인 큐잉까지 감안한 10배 여유**입니다.

**깨지면 무슨 뜻인가** — 요청 스레드가 커넥션이나 락을 기다리고 있다는 뜻입니다.
baseline에서 실제로 그랬습니다: 접수는 `INSERT` 두 번이 전부인데 p99가 8.9초였고,
원인은 일이 무거워서가 아니라 **커넥션 10개에 200개 스레드가 줄 서 있어서**였습니다.

### ② 종결 지연 p99 < 5초

**뜻**: 100번 중 99번은 5초 안에 돈이 실제로 도착한다.

**왜 밀리초가 아니라 초인가** — 이 시스템은 **비동기 Saga**입니다. 송금 한 건이
Kafka를 세 번 거치고(`requested` → `debited` → `credited`), 그 사이마다 Outbox 릴레이가
최대 200ms를 기다립니다. **구조적으로 1초 아래로는 못 내려갑니다.**
동기로 만들면 빨라지지만 그건 다른 설계이고, 그 경우 한 서비스가 죽으면 송금 전체가 멈춥니다.

**왜 5초인가** — 위 바닥값(약 1초)의 **5배 여유**입니다. 그리고 사용자 기준으로도
"보냈습니다" 후 몇 초 안에 상대가 받는 것이 실시간 이체의 체감선입니다.

**깨지면 무슨 뜻인가** — 어딘가 큐에 밀려 있다는 뜻입니다. 오늘 뚫은 것들이 전부
이 신호에서 출발했습니다 — 릴레이, 리스너 스레드, 원장 인덱스.

### ③ 접수 오류율 < 0.1%

**뜻**: 1,000번 중 1번 미만으로만 요청 자체가 실패한다.

**왜 0이 아닌가** — 배포·재기동·순간적인 네트워크 문제로 몇 건은 실패합니다.
**0을 목표로 걸면 목표가 아니라 소원**이 됩니다. 다만 이건 **재시도로 회복되는 실패**라
0.1%를 허용합니다 — `Idempotency-Key`가 있어 같은 요청을 다시 보내도 안전합니다.

### ④ 종결 실패율(시스템 원인) = 0

**뜻**: 접수된 송금은 **반드시** `COMPLETED`나 `FAILED` 중 하나로 끝난다.

**왜 여기만 0인가** — ③과 성격이 다릅니다. 접수 실패는 **사용자가 다시 누르면 됩니다.**
그런데 접수된 뒤 종결이 안 되면 **돈이 어중간한 상태로 갇힙니다** — 출금은 됐는데 입금은 안 된
상태로 남는 것이 최악입니다.

**업무적 실패는 여기 안 들어갑니다.** 잔액 부족으로 `FAILED`가 되는 건 시스템이 제 일을 한 것이고,
보상 트랜잭션으로 출금이 되돌아갑니다.

### ⑤ 유실 · 중복 · 갇힘 = 0 (타협 불가)

**뜻**: 이건 목표가 아니라 **전제**입니다.

| | 무슨 일인가 |
|---|---|
| **유실** | 이벤트가 사라져 송금이 영영 안 끝난다 |
| **중복** | 같은 출금이 두 번 일어난다 |
| **갇힘** | 어느 상태에서 더 나아가지도 되돌아가지도 못한다 |

지연이나 처리량은 **깎아서 타협할 수 있지만 이건 못 합니다.** 돈이 틀리면 시스템의 존재 이유가
없어집니다. 성능을 위한 변경은 전부 이 셋을 지킨다는 전제 위에서만 유효합니다.

> 2026-08-23 측정에서 실제로 확인했습니다 — 부하로 밀어 넣은 **송금 28,819건이 전부 종결**됐고,
> 알림은 **57,638건 = 28,819 × 2로 정확히 일치**했습니다. 리스너 스레드를 3배로 늘린 뒤에도
> 그대로였습니다.

## 용량(capacity)의 정의

> **위 SLO를 전부 지키면서 견디는 최대 도착률.**

"초당 80건을 처리한다"와 "초당 80건을 **서비스한다**"는 다릅니다.
전자는 **밀린 큐를 비우는 속도**이고, 후자는 **약속한 지연 안에 응답하는 속도**입니다.
용량은 후자입니다.

**감당 못 하는 부하를 부어놓고 잰 지연은 시스템 지연이 아니라 대기열 길이입니다.**
`spread.js`가 초당 400건까지 올리는 것은 **천장을 찾기 위한 포화 시험**이지 용량 측정이 아닙니다.

## 어떻게 재는가

```bash
k6 run load-test/scenarios/capacity.js
```

도착률을 **계단으로 올리면서 각 단계마다 SLO를 지키는지** 봅니다.
단계 사이에는 큐를 비우는 시간을 둡니다 — **앞 단계의 적체가 다음 단계 숫자를 오염시키기** 때문입니다.

```
20 TPS → 통과      40 TPS → 통과      60 TPS → 깨짐
                                       ↑ 용량은 40 TPS
```

## 측정된 용량 — 40 TPS (2026-08-23, 커밋 `79507ed`)

| 도착률 | 접수 p99 | 종결 p99 | 종결 성공률 | 판정 |
|---|---|---|---|---|
| 20 TPS | 165ms | 2,173ms | 100% | ✅ |
| **40 TPS** | **258ms** | **2,611ms** | **100%** | **✅ 여기까지** |
| 60 TPS | 358ms | **7,721ms** | 100% | ❌ |
| 80 TPS | 392ms | 42,844ms | 100% | ❌ |
| 100 TPS | 387ms | 59,578ms | 82.98% | ❌ |
| 120 TPS | 546ms | 59,881ms | 26.89% | ❌ |

**읽는 법이 세 가지 있습니다.**

**① 접수는 병목이 아닙니다.** 120 TPS에서도 p99가 546ms로 목표를 겨우 넘겼을 뿐입니다.
커넥션 풀을 10 → 30으로 올린 것이 여기서 값을 하고 있습니다.

**② 무너지는 건 종결이고, 60 TPS가 무릎입니다.** 40 → 60에서 2.6초 → 7.7초로 **세 배**,
그다음은 42초로 폭발합니다. 평평하다가 어느 지점에서 급격히 꺾이는 **전형적인 포화 곡선**입니다.

**③ 성공률만 보면 80 TPS까지 멀쩡해 보입니다.** 100%거든요. 다들 60초 안에는 끝났으니까요.
**지연을 같이 보지 않았으면 못 잡았을 것**이고, 이게 목표를 셋으로 나눠 건 이유입니다.

### 왜 80건/s가 아니라 40 TPS인가

큐를 비우는 속도는 80건/s가 맞습니다. 하지만 그건 **이미 밀린 것을 처리할 때의 속도**입니다.
지연 목표를 지키려면 **큐가 짧게 유지되어야 하므로 여유가 필요합니다.**

40 / 80 = **가동률 50%**입니다. 대기행렬은 가동률이 100%에 가까워질수록 대기 시간이
급격히 늘어나므로, 지연을 약속하려면 **절반 남짓에서 운영하는 것이 정상**입니다.
용량을 처리 능력과 같게 잡으면 **평소에도 목표를 못 지킵니다.**

측정 환경과 절차는 `HOMELAB.md`를 따릅니다. **노트북에서 잰 값은 용량으로 쓰지 않습니다.**

## 핫 계좌 용량 — 30 → 60 TPS (2026-08-24, 커밋 `f754b58`)

**위의 40 TPS와 다른 숫자입니다.** 저쪽은 돈이 여러 계좌로 흩어질 때이고,
이쪽은 **입금이 한 계좌로 몰릴 때**입니다. 정산 계좌·가맹점 대표 계좌가 그렇습니다.

한 계좌의 잔액이 한 행이면 그 계좌의 입금이 전부 그 행에 줄을 섭니다.
**서버를 늘려도 안 변하는 상한**이라 따로 잽니다 (`load-test/scenarios/hot-account.js`).

종결 p99 (ms), 목표는 5,000ms:

| 도착률 | 1조각 | 2조각 | 4조각 | 8조각 |
|---|---|---|---|---|
| 30 TPS | 2,551 ✅ | 2,128 ✅ | 2,116 ✅ | 2,106 ✅ |
| 45 TPS | **17,048 ❌** | | | |
| 60 TPS | **32,356 ❌** | | 7,099 ❌ | **3,617 ✅** |
| 70 TPS | | | | 9,696 ❌ |
| 80 TPS | | | | 14,091 ❌ |

**30 TPS에서는 조각 수가 아무 차이를 안 만듭니다.** 그 부하가 상한 아래이기 때문입니다 —
샤딩은 상한에 부딪힌 뒤에만 의미가 있습니다.

### 재는 법

```bash
CPUSET=0-9 ./scripts/homelab-services.sh restart
./scripts/measure-hot-account.sh 60 8
```

두 가지를 반드시 지킵니다. 둘 다 실제로 틀렸던 것들입니다.

| 규칙 | 안 지키면 |
|---|---|
| **재기동 직후 첫 실행은 버린다** | 식은 실행과 데워진 실행을 비교하게 됩니다. 2026-08-24에 32.0초 vs 2.1초로 **15.4배**라고 적을 뻔했고, 다시 재니 둘 다 2.1초였습니다 |
| **측정 사이에 큐를 비운다** | 앞 실행의 적체가 다음 실행의 지연으로 잡힙니다 |

`measure-hot-account.sh`가 두 번째를 대신해줍니다. 첫 번째는 사람이 지켜야 합니다.
