# 서비스 수준 목표 (SLO)

**"초당 몇 건 나오나"는 목표가 될 수 없습니다.** 지연을 포기하면 처리량은 얼마든지 나오기
때문입니다. 실제로 이 저장소는 2026-08-23에 종결 처리량을 19 → 80건/s로 올렸는데,
같은 측정에서 **종결 p95가 32.8초**였습니다. 처리량만 보면 성공이고 사용자 입장에서는 실패입니다.

그래서 **처리량·지연·오류율을 묶어서** 겁니다. 이 문서는 그 기준을 정합니다.

## 무엇을 재는가 (SLI)

측정 대상을 먼저 못 박습니다. **어디서 어디까지인지가 흐리면 숫자를 비교할 수 없습니다.**

| 이름 | 정의 | 왜 나눴나 |
|---|---|---|
| **접수 지연** | `POST /transfers` 요청 → `202` 응답 | 사용자가 화면 앞에서 **직접 기다리는 시간** |
| **종결 지연** | `POST /transfers` 요청 → 상태가 `COMPLETED`/`FAILED` | **돈이 실제로 움직이기까지**. 진짜 지표 |
| **접수 오류율** | 2xx가 아닌 응답 ÷ 전체 요청 | 시스템이 요청 자체를 못 받은 비율 |
| **종결 실패** | 시스템 원인으로 `FAILED`가 되거나 끝내 종결되지 않음 | 잔액 부족 같은 **업무적 실패는 제외** |

> **접수와 종결을 반드시 나눠야 합니다.** `POST /transfers`는 접수만 하고 202를 돌려줍니다 —
> 그 시점에 돈은 아직 안 움직였습니다. 접수만 재면 "초당 수천 건"이 나오는데
> 그건 `INSERT` 두 번의 속도일 뿐입니다.

## 목표

| 지표 | 목표 | 성격 |
|---|---|---|
| **접수 지연 p99** | **< 500ms** | 사용자 체감 |
| **종결 지연 p99** | **< 5초** | 사용자 체감 |
| **접수 오류율** | **< 0.1%** | 가용성 |
| **종결 실패율(시스템 원인)** | **0** | 정합성 |
| **유실 · 중복 · 갇힘** | **0** | 정합성 — 타협 불가 |
| **잔액–원장 대사 불일치** | **0** | 정합성 — 부하 종료·drain 뒤 판정 |
| **내부 종결 지연 p99 (상대 은행이 아플 때)** | **< 5초** | 격리 — 아래 ⑥ |
| **5분 넘게 결과를 모르는 입금** | **0** | 정합성 — 아래 ⑥ |

> **위 여섯 줄은 전부 우리 안의 일입니다.** 상대 은행으로 나가는 송금의 지연은
> 여기 없습니다 — **남의 속도를 우리 목표로 걸 수 없기 때문**입니다. 자세한 것은 ⑥.

## 각 목표가 무슨 뜻인가

### ① 접수 지연 p99 < 500ms

**뜻**: 100번 중 99번은 0.5초 안에 "접수됐습니다"가 뜬다.

**왜 p99인가** — 평균과 p95만 보면 꼬리를 놓칩니다. 하루 100만 건이면 **1%는 1만 명**입니다.
"100명 중 1명"은 작아 보이지만 **매일 1만 명이 겪는 일**입니다.

**왜 500ms인가** — 접수 한 건은 커넥션을 세 번 잡습니다(키 선점 → 저장+Outbox → 키에 결과 기록).
지금 커밋 하나가 약 14ms이므로 **이론상 바닥은 50ms 언저리**입니다.
500ms는 거기에 **GC·네트워크·순간적인 큐잉까지 감안한 10배 여유**입니다.

**깨지면 무슨 뜻인가** — 요청 스레드가 커넥션이나 락을 기다리고 있다는 뜻입니다.
baseline에서 실제로 그랬습니다: 접수는 `INSERT` 두 번이 전부인데 p99가 8.9초였고,
원인은 일이 무거워서가 아니라 **커넥션 10개에 200개 스레드가 줄 서 있어서**였습니다.

### ② 종결 지연 p99 < 5초

**뜻**: 100번 중 99번은 5초 안에 돈이 실제로 도착한다.

**왜 밀리초가 아니라 초인가** — 이 시스템은 **비동기 Saga**입니다. 송금 한 건이
Kafka를 세 번 거치고(`requested` → `debited` → `credited`), 그 사이마다 Outbox 릴레이가
최대 200ms를 기다립니다. **구조적으로 1초 아래로는 못 내려갑니다.**
동기로 만들면 빨라지지만 그건 다른 설계이고, 그 경우 한 서비스가 죽으면 송금 전체가 멈춥니다.

**왜 5초인가** — 위 바닥값(약 1초)의 **5배 여유**입니다. 그리고 사용자 기준으로도
"보냈습니다" 후 몇 초 안에 상대가 받는 것이 실시간 이체의 체감선입니다.

**깨지면 무슨 뜻인가** — 어딘가 큐에 밀려 있다는 뜻입니다. 오늘 뚫은 것들이 전부
이 신호에서 출발했습니다 — 릴레이, 리스너 스레드, 원장 인덱스.

### ③ 접수 오류율 < 0.1%

**뜻**: 1,000번 중 1번 미만으로만 요청 자체가 실패한다.

**왜 0이 아닌가** — 배포·재기동·순간적인 네트워크 문제로 몇 건은 실패합니다.
**0을 목표로 걸면 목표가 아니라 소원**이 됩니다. 다만 이건 **재시도로 회복되는 실패**라
0.1%를 허용합니다 — `Idempotency-Key`가 있어 같은 요청을 다시 보내도 안전합니다.

### ④ 종결 실패율(시스템 원인) = 0

**뜻**: 접수된 송금은 **반드시** `COMPLETED`나 `FAILED` 중 하나로 끝난다.

**왜 여기만 0인가** — ③과 성격이 다릅니다. 접수 실패는 **사용자가 다시 누르면 됩니다.**
그런데 접수된 뒤 종결이 안 되면 **돈이 어중간한 상태로 갇힙니다** — 출금은 됐는데 입금은 안 된
상태로 남는 것이 최악입니다.

**업무적 실패는 여기 안 들어갑니다.** 잔액 부족으로 `FAILED`가 되는 건 시스템이 제 일을 한 것이고,
보상 트랜잭션으로 출금이 되돌아갑니다.

### ⑤ 유실 · 중복 · 갇힘 = 0 (타협 불가)

**뜻**: 이건 목표가 아니라 **전제**입니다.

| | 무슨 일인가 |
|---|---|
| **유실** | 이벤트가 사라져 송금이 영영 안 끝난다 |
| **중복** | 같은 출금이 두 번 일어난다 |
| **갇힘** | 어느 상태에서 더 나아가지도 되돌아가지도 못한다 |

지연이나 처리량은 **깎아서 타협할 수 있지만 이건 못 합니다.** 돈이 틀리면 시스템의 존재 이유가
없어집니다. 성능을 위한 변경은 전부 이 셋을 지킨다는 전제 위에서만 유효합니다.

> 2026-08-23 측정에서 실제로 확인했습니다 — 부하로 밀어 넣은 **송금 28,819건이 전부 종결**됐고,
> 알림은 **57,638건 = 28,819 × 2로 정확히 일치**했습니다. 리스너 스레드를 3배로 늘린 뒤에도
> 그대로였습니다.

### ⑥ 상대 은행이 아플 때 — 무엇을 약속할 수 있나 (Phase 6.5)

Phase 6.5에서 **우리가 제어할 수 없는 남**이 들어왔습니다. 그래서 목표를 하나 더 거는 게 아니라
**무엇을 목표로 걸 수 있는지부터** 다시 봐야 합니다.

#### 외부 송금의 지연은 SLO가 아니다

상대가 2초를 끌면 우리 송금도 2초 뒤에 끝납니다. **그건 우리 시스템의 성능이 아닙니다.**
목표로 걸면 두 가지가 나빠집니다 — 남의 사정으로 우리 SLO가 깨지고, 그걸 지키려다
**느리지만 멀쩡한 상대를 우리가 끊게** 됩니다 (`DECISIONS.md` D-003).

**대신 갈라 잽니다.** `kind:internal`과 `kind:external`을 나눠 재고,
**약속은 내부에만** 겁니다. 외부는 재되 목표를 걸지 않습니다.

> 섞어 재면 아무 말도 못 합니다. 2026-08-27 측정에서 합쳐 본 종결 성공률은 0.91인데,
> 갈라 보니 **내부 1.00 / 외부 0.44**였습니다. 합친 숫자는 "우리가 문제인가"에 답을 못 합니다.

#### 그래서 무엇을 약속하나 — 격리와 정합성

| 약속 | 목표 | 뜻 |
|---|---|---|
| **내부 종결 지연 p99** | **< 5초** (상대가 아플 때도) | 남의 사정으로 **우리 일이 멈추지 않는다** |
| **내부 종결 성공률** | **1.00** (상대가 아플 때도) | 위와 같은 약속의 다른 면 |
| **5분 넘게 결과를 모르는 입금** | **0** | 넘으면 대사가 사람에게 넘긴다(`UNKNOWN_EXTERNAL_CREDIT`) |
| **차단된 건의 유실** | **0** | 회로가 막은 건은 전부 `sent=false`로 남고, 상대가 살아나면 전부 나간다 |
| **이중 입금** | **0** | 타협 불가. 답이 없을 때 **재시도하지 않고 조회로만** 결론짓는다 |

**앞의 둘이 이 Phase의 핵심입니다.** "상대가 아파도 우리는 멀쩡한가"가 걸 수 있는 유일한
성능 약속이고, 나머지 셋은 **돈이 틀리지 않는다**는 정합성 조건입니다.

#### 측정된 값 (2026-08-27 · 2026-08-28, `home2`)

상대를 **2초 지연**으로 두고 30 TPS · 외부 비율 20%:

| | 값 | 판정 |
|---|---:|---|
| 내부 종결 p99 | **2,580ms** | ✅ |
| 내부 종결 성공률 | **1.00** | ✅ |
| 외부 종결 p99 | 54,571ms | — **목표 없음** (상대가 2초인데 6건/s가 온다) |
| 외부 종결 성공률 | 0.44 | — **목표 없음** |

상대를 **연속 실패(5xx)**로 두면:

| | 값 | 판정 |
|---|---:|---|
| 차단된 호출 | 801건 → 전부 미전송 보관 | ✅ 유실 0 |
| 상대 회복 뒤 | 320건 **전부 해소**, pending 0 | ✅ |
| 정식 대사 | **findings 0** | ✅ |

> **리스너 분리 전에는 내부 p99가 58,790ms였습니다.** 같은 부하, 같은 상대에서
> 우리 쪽 구조만 바꿔 2,580ms가 됐습니다. **이 표의 첫 줄이 그 작업의 목표였습니다.**

#### 임계값도 이 결정에 맞춰 고쳤다

`mixed-bank.js`가 외부 지연과 **합친 성공률**에 목표를 걸고 있었습니다. 상대가 느리면
매 실행이 실패로 찍히는데, 그건 우리가 뭘 잘못해서가 아닙니다. 둘 다 뺐습니다.

> ⚠️ **부분지표 선언까지 지우면 안 됩니다.** k6는 threshold가 있어야 부분지표를 만들어주므로,
> 통째로 지웠더니 요약의 **외부 p95·p99가 `—`로 사라졌습니다.** 그래서
> `p(99)>=0`으로 남겨뒀습니다 — 목표가 아니라 **계속 재겠다**는 뜻입니다.
> **목표를 지우는 것과 재기를 그만두는 것은 다릅니다.**
>
> 고친 뒤 같은 조건으로 재확인: 내부 p99 **2,123ms** · 성공률 **1.00**,
> 외부 p99 57,649ms(목표 없음), 미발사 0, 임계값 위반 없음.

#### 외부가 섞인 용량은 아직 안 쟀다

`spread` 100 TPS와 핫 계좌 70 TPS는 **전부 우리 안에서만 도는 송금**의 값입니다.
외부 호출이 지연을 지배하므로 **그 숫자를 외부 섞인 부하의 용량으로 쓰면 안 됩니다.**
계단 측정은 아직 하지 않았고, 하려면 **상대의 상태(지연·오류율)를 함께 적어야** 합니다 —
같은 부하라도 상대가 다르면 다른 측정입니다.

## 용량(capacity)의 정의

> **위 SLO를 전부 지키면서 견디는 최대 도착률.**

"초당 80건을 처리한다"와 "초당 80건을 **서비스한다**"는 다릅니다.
전자는 **밀린 큐를 비우는 속도**이고, 후자는 **약속한 지연 안에 응답하는 속도**입니다.
용량은 후자입니다.

**감당 못 하는 부하를 부어놓고 잰 지연은 시스템 지연이 아니라 대기열 길이입니다.**
`spread.js`가 초당 400건까지 올리는 것은 **천장을 찾기 위한 포화 시험**이지 용량 측정이 아닙니다.

## 어떻게 재는가

```bash
k6 run load-test/scenarios/capacity.js
```

도착률을 **계단으로 올리면서 각 단계마다 SLO를 지키는지** 봅니다.
단계 사이에는 큐를 비우는 시간을 둡니다 — **앞 단계의 적체가 다음 단계 숫자를 오염시키기** 때문입니다.

```
80 TPS → 통과      100 TPS → 통과      120 TPS → 깨짐
                                        ↑ 용량은 100 TPS
```

## 측정된 용량 — 100 TPS (2026-08-26, 커밋 `ae15f81`)

`spread` 계열입니다 — 돈이 여러 계좌로 흩어질 때. 입금이 한 계좌로 몰리는 경우는
아래 "핫 계좌 용량"에 따로 있습니다(**70 TPS**).

| 도착률 | 접수 p99 | 종결 p99 | 종결 성공률 | 판정 |
|---|---|---|---|---|
| 20 TPS | 46ms | 2,046ms | 100% | ✅ |
| 40 TPS | 100ms | 2,107ms | 100% | ✅ |
| 60 TPS | 173ms | 2,656ms | 100% | ✅ |
| 80 TPS | 222ms | 2,694ms | 100% | ✅ |
| **100 TPS** | **329ms** | **4,673ms** | **100%** | **✅ 여기까지** |
| 120 TPS | 312ms | **18,874ms** | 100% | ❌ |

### Phase 6 전과 비교 — 40 → 100 TPS

같은 시나리오, 같은 절차입니다.

| 도착률 | 2026-08-23 종결 p99 | 2026-08-26 종결 p99 |
|---|---:|---:|
| 40 TPS | 2,611ms ✅ | 2,107ms ✅ |
| 60 TPS | **7,721ms ❌** | 2,656ms ✅ |
| 80 TPS | **42,844ms ❌** | 2,694ms ✅ |
| 100 TPS | **59,578ms ❌** (성공률 82.98%) | **4,673ms ✅ (100%)** |
| 120 TPS | 59,881ms ❌ (성공률 **26.89%**) | 18,874ms ❌ (100%) |

**성공률이 전 구간 100%인 것도 달라진 점입니다.** 전에는 100 TPS에서 17%가 60초 안에
끝나지 못했고 120 TPS에서는 73%가 그랬습니다. 지금은 120 TPS에서도 **늦을 뿐 다 끝납니다.**

**읽는 법이 세 가지 있습니다.**

**① 접수는 여전히 병목이 아닙니다.** 120 TPS에서도 p99가 312ms입니다.

**② 무너지는 건 종결이고, 무릎이 100 → 120 사이로 옮겨갔습니다.** 전에는 40 → 60이었습니다.

**③ 성공률만 보면 120 TPS도 멀쩡해 보입니다.** 100%거든요. 다들 60초 안에는 끝났으니까요.
**지연을 같이 보지 않았으면 못 잡았을 것**이고, 이게 목표를 셋으로 나눠 건 이유입니다.

### 왜 처리 속도가 아니라 100 TPS인가

밀린 큐를 비우는 속도와 **약속한 지연 안에 서비스할 수 있는 속도**는 다릅니다.
전자는 100% 가동에서 나오는 값이고, 후자는 **큐가 짧게 유지되어야** 하므로 여유가 필요합니다.

대기행렬은 가동률이 100%에 가까워질수록 대기 시간이 급격히 늘어납니다.
120 TPS에서 종결 p99가 2.7초에서 18.9초로 **일곱 배**가 되는 것이 그 곡선입니다 —
처리 능력을 조금 넘겼을 뿐인데 지연은 자릿수로 늘어납니다.
그래서 용량은 **깨지기 직전이 아니라 깨지지 않는 마지막 지점**으로 잡습니다.
용량을 처리 능력과 같게 잡으면 **평소에도 목표를 못 지킵니다.**

측정 환경과 절차는 `HOMELAB.md`를 따릅니다. **노트북에서 잰 값은 용량으로 쓰지 않습니다.**

> ⚠️ **2026-08-29에 같은 100 TPS를 다시 재니 종결 p99가 5,044ms로 목표를 넘었습니다**
> (사흘 전 4,673ms). 게이트웨이 탓이 아니었습니다 — 직접 경로도 같았습니다.
>
> **원인은 발행이 끝난 Outbox 행 360만 건(1.6GB)이었습니다.** 지우는 주체가 없어서
> 버퍼 풀(1GB)에 안 들어가는 데이터의 69%가 쓸모없는 행이었습니다.
> 지우고 다시 재니 **4,639ms**로 돌아왔습니다.
>
> **용량은 한 번 재고 끝나는 값이 아닙니다.** 여기 적힌 100 TPS는 *그때의 데이터 크기에서*
> 잰 값입니다. 보관 기간 배치를 넣어 막아뒀지만(`ROADMAP.md`의 "상시 — 보관 기간"),
> **용량을 말할 때는 그때 데이터가 얼마였는지도 함께 봐야 합니다.**

### 게이트웨이를 통과하면 (2026-08-29, Phase 4)

같은 부하를 **서비스 직접**과 **게이트웨이 경유**로 번갈아 쟀습니다.

| 도착률 | 접수 p99 (직접 → 경유) | 종결 p99 (직접 → 경유) |
|---|---|---|
| 60 TPS | 112.25 → **136.52ms** (+24.3) | 2,103.00 → 2,104.00ms (+1.0) |
| 100 TPS | 185.58 → **182.92ms** (−2.7) | 5,044.40 → 5,061.40ms (+17) |

**접수에만 홉이 더해지고 종결은 그대로**입니다 — 게이트웨이는 접수 경로에만 있고,
그 뒤는 Kafka·Outbox로 도는 내부 흐름이기 때문입니다.

100 TPS에서 차이가 **음수**로 나온 것은 게이트웨이가 빠르다는 뜻이 아니라
**차이가 측정 노이즈에 묻혔다**는 뜻입니다. 그래서 *"게이트웨이가 접수 p99에 +24ms"*는
**60 TPS에서만 할 수 있는 말**이고, 100 TPS에서는 *"구분되지 않는다"*가 정확합니다.

## 핫 계좌 용량 — 25 → 60 TPS (2026-08-24, 커밋 `be466f0`)

**위의 40 TPS와 다른 숫자입니다.** 저쪽은 돈이 여러 계좌로 흩어질 때이고,
이쪽은 **입금이 한 계좌로 몰릴 때**입니다. 정산 계좌·가맹점 대표 계좌가 그렇습니다.

한 계좌의 잔액이 한 행이면 그 계좌의 입금이 전부 그 행에 줄을 섭니다.
**서버를 늘려도 안 변하는 상한**이라 따로 잽니다 (`load-test/scenarios/hot-account.js`).

종결 p99 (ms), 목표는 5,000ms. **고정 도착률**입니다.

| 도착률 | 1조각 | 8조각 |
|---|---|---|
| 20 TPS | 2,115 ✅ | |
| 25 TPS | 2,723 ✅ | |
| 30 TPS | **7,770 ❌** | 2,118 ✅ |
| 45 TPS | | 2,600 ✅ |
| 50 TPS | | **4,112 ✅** |
| 60 TPS | | 24,145 ❌ → **3,354 ✅** (파티션 6) |
| 70 TPS | | 13,279 ❌ → **3,094 ✅** (redo 1GB) |
| 80 TPS | | **7,641 ❌** |

**25 → 70 TPS, 2.8배입니다.** 잔액 샤딩으로 25 → 50, 파티션 3 → 6으로 50 → 60,
**MySQL redo log 100MB → 1GB로 60 → 70.**
뒤쪽이 덜 오른 이유는 **스레드를 늘리면 건당 처리 시간도 함께 늘기** 때문입니다
(입금 52.5 → 80ms). 경합이 락에서 MySQL로 옮겨갔습니다. 쪼개기 전 상한 25 TPS는 예전에 락 보유 시간으로
추정했던 **"한 계좌 초당 26건"**과 맞아떨어집니다 — 추정과 실측이 처음으로 만났습니다.

구간별 계측(`07d741c`)을 올려 다시 잰 60 TPS도 접수 p99 381ms · 종결 p99 3,354ms ·
종결 성공률 100%로 통과했습니다. 재기동 직후 워밍업은 25,734ms라 버렸고,
드레인 뒤 같은 조건의 두 번째 실행만 기록했습니다.

> **측정 규칙이 하나 늘었습니다.** 이 값을 한 번 버렸는데, MySQL에 실험용
> `binlog_group_commit_sync_delay=1000`이 켜져 있는 줄 모르고 쟀기 때문입니다.
> 앱 커밋 해시는 확인했는데 **DB 설정은 아무도 확인하지 않았습니다.**
> 서버 설정을 손으로 바꿨으면 **되돌리는 것까지가 실험**이고,
> 재기 전에 **지금 설정이 저장소와 같은지** 봐야 합니다.

**70 TPS에서 무너지는 이유는 계좌가 아닙니다.** 입금 한 건이 80ms이고 스레드가 6개라
상한이 **75건/s**입니다. 70 TPS면 가동률 93%라 지연이 부풉니다.
다음 지렛대는 스레드가 아니라 **건당 80ms를 줄이는 것**입니다.

### 재는 법

```bash
CPUSET=0-9 ./scripts/homelab-services.sh restart
./scripts/measure-hot-account.sh 50 8
```

세 가지를 반드시 지킵니다. **셋 다 실제로 틀렸던 것들입니다.**

| 규칙 | 안 지키면 |
|---|---|
| **재기동 직후 첫 실행은 버린다** | 식은 실행과 데워진 실행을 비교하게 됩니다. 32.0초 vs 2.1초로 **15.4배**라고 적을 뻔했고, 다시 재니 둘 다 2.1초였습니다 |
| **대량 DML 직후 첫 실행도 버린다** | 2026-08-29에 Outbox 360만 건을 지우고 **곧바로** 쟀더니 종결 p99가 5,044 → **11,768ms**로 두 배 나빴습니다. InnoDB가 뒤에서 삭제 흔적을 치우는 중이었고(`History list length`), 다 치워진 뒤 다시 재니 **4,639ms**였습니다. **"정리가 성능을 나쁘게 한다"고 적을 뻔했습니다** |
| **측정 사이에 큐를 비운다** | 앞 실행의 적체가 다음 실행의 지연으로 잡힙니다 |
| **도착률이 진짜 고정인지 본다** | `ramping-arrival-rate`에 `startRate`가 남아 있으면 RATE=60이 **10 → 60 램프**가 됩니다(평균 35). 요약은 "고정 도착률 60"이라 찍는데 실제로는 아니었고, **그 값으로 "용량 60 TPS"라고 적었습니다** |
| **`미발사`(dropped_iterations)가 0인지 본다** | 0이 아니면 요청한 부하가 안 걸린 것이라 그 실행의 지연은 의미가 없습니다 |
| **전체 대사 조건을 A/B에서 같게 둔다** | 한쪽에서만 60초 전체 스캔을 끄면 애플리케이션 개선이 아니라 대사 부하 제거 효과를 재게 됩니다 |
| **drain 뒤 대사를 통과한다** | p99가 빨라도 잔액–원장 불일치·미종결·갇힌 키가 하나라도 남으면 서비스 가능한 TPS가 아닙니다 |

워밍업 폐기와 drain은 `measure-hot-account.sh`가 수행하고, 실제 도착률과 미발사는 요약에서
확인합니다. 대사 조건과 사후 대사 결과는 실행 기록에 별도로 남깁니다.

### 성능 측정과 정식 대사를 분리한다

전체 계좌 잔액과 원장 합을 훑는 대사는 성능 경로가 아니라 **독립적인 정확성 검증**입니다.
Phase 6에서는 부하 중 주기 스캔이 결과를 흔들지 않도록 정식 대사를 분리하되, 다음 순서를
용량 판정의 일부로 고정합니다.

```text
같은 대사 설정으로 A/B 측정
  → 새 요청 중단
  → Kafka·Outbox drain
  → 기준 시각(cutoff) 확정
  → 정식 대사 1회
  → 불일치·미종결·갇힘 0건 확인
```

최종 운영 목표는 **기준 시각이 있는 EOD 전체 대사**입니다. 60초마다 현재값 전체를 서로 다른
서비스에서 읽으면 진행 중인 정상 Saga와 조회 시각 차이를 불일치로 오인할 수 있습니다.
대신 오래된 미종결 송금·갇힌 멱등성 키는 짧은 주기 감시로, Kafka lag·Outbox 연령·DLT는
상시 메트릭으로 분리합니다. EOD 구현 전까지는 기존 스케줄을 한쪽 실험에서만 임의로 끄지 않습니다.
