# CONTRIBUTING

이 저장소에서 작업하는 모든 기여자/에이전트가 따라야 할 규칙이다.

## 커밋 컨벤션

[Conventional Commits](https://www.conventionalcommits.org/) 형식을 따른다.

```
<type>: <설명>

<본문 (선택, 변경 이유·상세 내용)>
```

### type 목록

| type | 용도 |
|---|---|
| `feat` | 새로운 기능/모듈/도메인 모델 추가 |
| `fix` | 버그 수정 |
| `chore` | 빌드 설정, 의존성, `.gitignore` 등 코드 동작에 영향 없는 잡무 |
| `docs` | 문서(README, ROADMAP, API 설계 문서 등)만 변경 |
| `refactor` | 기능 변경 없는 코드 구조 개선 |
| `test` | 테스트 코드 추가/수정 |
| `style` | 포맷팅 등 코드 의미에 영향 없는 변경 |
| `perf` | 성능 개선 |
| `build` | Gradle/Docker 등 빌드 시스템 변경 |
| `ci` | CI 파이프라인 설정 변경 |

### 규칙

- 제목은 명령형, 한글 설명 뒤 마침표 생략
- **제목 한 줄, 50자 안팎.** 무엇을 했는지만 적는다
- 하나의 커밋은 하나의 관심사를 담는다 — 여러 type이 섞이면 커밋을 분리
- **본문은 불릿. 한 줄에 한 가지.** 문단으로 풀어쓰지 않는다
- **"왜"는 필요할 때만, 한두 줄.** 코드나 주석을 보면 아는 것은 적지 않는다
- 볼드·이모지를 쓰지 않는다

### 제목에 서사를 담지 않는다

발견한 경위, 잘못 짚을 뻔한 이야기, 인용부호로 넣은 대사는 제목에 넣지 않는다.
읽는 쪽은 `git log --oneline`으로 훑는데, 사연이 들어가면 무엇을 한 커밋인지
한눈에 안 보인다. 사연이 남길 가치가 있으면 `docs/PROGRESS.md`에 적는다.

```
✅ fix: 종결 지연 판정을 p95에서 p99로 고친다
❌ fix: 측정 판정이 두 군데에서 거짓을 말하고 있었다

✅ style: 주석에서 HTML 태그를 제거한다
❌ style: 주석에서 HTML 태그를 걷어낸다 — 렌더링되지도 않으면서 문장만 끊고 있었다

✅ docs: 릴레이 2대 측정 결과를 적는다
❌ docs: "2.4배 느리다"가 아니라 "무너진다"였다 — 세 번 재고 나서 보였다
```

> ⚠️ **위 ❌ 예시는 전부 이 저장소에 실제로 있는 커밋이다.**
> 이 규칙은 2026-09-11에 생겼고 그 전 커밋과 PR 본문은 서사체다.
> **`git log`를 본보기로 삼지 않는다** — 고쳐야 할 쪽이다.
> 이미 푸시된 것은 그대로 두고 다음 커밋부터 적용한다.

### 예시

```
feat: Phase 0 프로젝트 기반 설정 (멀티모듈 구조 및 도메인 모델)

- Gradle 멀티모듈 구조 전환 (account-service, transfer-service,
  ledger-service, gateway, config-server)
- 도메인 모델 설계: Account, Transfer/IdempotencyKey, Transaction(원장)
```

```
style: 주석에서 HTML 태그를 제거한다

javadoc을 생성하지 않으므로 태그가 렌더링되는 곳이 없다.

- <b> 1146, <p> 492, <h2>·<h4> 121, <br> 1 제거
- <ul>/<li> 63 → "-", <ol>/<li> 9 → "1." 번호
- <pre> 18 → 태그 줄만 삭제
- <table> 7 → 공백으로 열을 맞춘 평문
- {@link}/{@code}는 유지 (IDE에서 동작하는 참조)
```

## 브랜치 전략

[git flow](https://nvie.com/posts/a-successful-git-branching-model/)를 따른다.
단, git flow의 `master` 역할은 `main` 브랜치가 맡는다.

| 브랜치 | 역할 | 분기 원본 | 머지 대상 |
|---|---|---|---|
| `main` | 제품으로 출시될 수 있는 상태 | — | — |
| `develop` | 다음 출시 버전을 개발하는 통합 브랜치 | `main` | — |
| `feature/*` | 기능 개발 | `develop` | `develop` |
| `release/*` | 이번 출시 버전 준비 | `develop` | `main` + `develop` |
| `hotfix/*` | 출시 버전에서 발생한 버그 수정 | `main` | `main` + `develop` |

### 명명 규칙

- `feature/phase-2-data-consistency` — Phase 단위 작업은 `feature/phase-{번호}-{주제}`
- `release/phase-2` — 출시 준비
- `hotfix/{요약}` — 예: `hotfix/transfer-balance-mismatch`

### 규칙

- **`main`에 직접 커밋하지 않는다.** 항상 `release/*` 또는 `hotfix/*`를 거친다.
  **저장소 설정으로 강제된다** — `main`은 PR을 거쳐야 하고 CI(`unit`/`build`/`lint-workflows`)가
  통과해야 머지된다. force push와 브랜치 삭제도 막혀 있다. 관리자 우회는 열어뒀지만
  **의도적으로 설정을 끌 때만** 되는 것이지 실수로는 안 된다. `develop`은 통합 브랜치라 보호하지 않았다.
- `main`은 언제나 빌드/테스트가 통과하는 상태를 유지한다.
  실패하는 테스트(문제 재현용 등)는 `feature/*` 안에서만 존재할 수 있다.
- 하나의 `feature/*` 브랜치 안에서는 작업 흐름 단위로 커밋을 쪼갠다.
  (예: Phase 2는 Step 0~5를 각각 별도 커밋으로)

### 출시 주기와 태그

`ROADMAP.md`의 **Phase 하나를 한 번의 출시로 본다.**

```
feature/phase-N-* → develop → release/phase-N → main (+ 태그) → develop 역머지
```

Phase 완료 시 `main`에 `phase-N-complete` 형식의 annotated 태그를 단다.
나중에 특정 Phase 시점의 코드로 되돌아가거나, 카나리 배포·롤백 실습(Phase 7~8)의
기준점으로 활용한다.

#### ⚠️ Phase가 끝나면 **그때 낸다** — 모아서 내지 않는다

**두 번 데였다.**

| 언제 | 무슨 일이 |
|---|---|
| 2026-08-22 | Phase 2·3을 모아 냈더니 릴리스 브랜치가 `unit` 잡보다 **앞선 코드**라, 보호 규칙이 보고되지 않는 검사를 영원히 기다렸다. 두 릴리스를 하나로 합쳐야 했다 |
| 2026-08-28 | Phase 5·6·6.5가 밀려 **197 파일 · +18,224줄**. CodeRabbit이 *"Review skipped: 197 files exceed the limit of 100"*으로 리뷰 자체를 건너뛰었다 |

**리뷰할 수 없는 PR은 리뷰를 안 받은 것과 같다.** 그리고 보호 규칙은 *지금*의 CI를 요구하는데
릴리스 대상은 *그때*의 코드라, 미룰수록 그 어긋남이 벌어진다.

- **PR은 항목 단위로 쪼갠다** (2026-08-28에 규칙을 한 번 더 좁혔다).
  `feature/phase-N-{주제}` → **PR → `develop`**을 항목마다 낸다. `develop`은 보호되지 않지만
  PR로 넣는 이유는 셋이다 — CI가 돌고, 리뷰 도구가 실제로 읽을 크기이고, **무엇을 왜 바꿨는지가
  PR 단위로 남는다.** 로컬 머지는 그 기록을 안 남긴다
- **`main` 출시는 여전히 Phase 단위**다. 태그가 `phase-N-complete`이므로 그 단위를 바꾸면
  지나간 기록의 뜻이 달라진다. 즉 **PR은 잘게, 출시는 Phase마다.**
  Phase가 닫히는 그날 낸다
- **릴리스 브랜치에서는 새 커밋을 만들지 않는다.** 출시 노트·문서는 **`develop`에서 먼저**
  쓰고 나서 브랜치를 낸다. 그래야 역머지가 머지 커밋 하나로 끝난다
- **역머지는 선택이 아니다.** GitHub의 머지 커밋은 `main`에만 생기므로,
  안 하면 `develop`이 영영 뒤처진다. 끝나고 확인:

  ```bash
  git rev-list --count develop..main   # 0 이어야 한다
  ```

## PR 작성

리뷰어가 훑어서 필요한 것만 집어가는 문서다. 골격을 고정하고 문장을 짧게 쓴다.
서사체와 과한 강조는 읽는 시간을 늘리기만 한다.

참고한 형식: [f-lab-edu/limited-drop-commerce#56](https://github.com/f-lab-edu/limited-drop-commerce/pull/56)

```markdown
## 개요
- 이슈 번호와 목적. 한두 줄

## 작업 내용
### <소제목>
- 무엇을 했는지 명사형 단문

## 변경 사항
### 스크립트/AI가 처리한 내용
### 직접 수정한 내용
### 유지한 것

## 리뷰 참고 사항
- 검증 결과, 리뷰어가 알아야 할 것, 다른 PR과의 관계
```

### 규칙

- **명사형 단문 불릿.** `~제거`, `~분리`, `~이동`. 서술형 문장으로 풀지 않는다
- **볼드는 라벨에만.** 문장을 통째로 굵게 쓰지 않는다
- **도입부를 극적으로 쓰지 않는다.** `## 개요` 불릿으로 바로 시작한다
- **소제목은 골격 그대로.** `★ 그런데 ~`, `~라는 걸 안다` 같은 서사체 제목을 만들지 않는다
- 이모지는 쓰지 않는다
- 코드·diff는 **판단이 갈리는 부분만** 보여준다. 전후 비교를 나열하지 않는다
- **직접 고친 것과 도구가 일괄 처리한 것을 나눠 적는다.** 리뷰 밀도를 어디에 둘지 알려주는 정보다

### 리뷰 참고 사항에 반드시 적을 것

- 검증한 방법과 결과 (테스트 건수, 확인한 항목)
- **파일 수가 많으면 왜 안전한지 근거.** "코드 줄 변경 0건, diff에서 주석 아닌 줄을 걸러 확인"처럼 확인 방법까지
- 열려 있는 다른 PR과 겹치는 파일이 있는지
- 이 결정의 전제가 나중에 바뀔 수 있다면 그 조건

> 커밋 메시지도 같은 원칙이다 — [커밋 컨벤션](#커밋-컨벤션) 참고. PR 본문 쪽이
> 조금 더 길 뿐, 둘 다 서사를 풀지 않는다.

## 주석 스타일

**주석에 HTML 태그를 쓰지 않는다.** 평문과 빈 줄로만 구분한다.

이 프로젝트는 javadoc HTML을 생성하지 않는다(`build.gradle`에 javadoc 태스크가 없다).
태그가 렌더링되는 곳은 IDE의 Quick Documentation 팝업뿐인데, 주석은 팝업보다
**소스 그대로** 읽는 시간이 훨씬 길다. `<b>어느 조각에</b>`는 문장 중간을 끊어
읽기를 방해하고, 그 대가로 얻는 것이 팝업의 굵은 글씨 하나다.

| 쓰지 않는다 | 대신 |
| --- | --- |
| `<h2>제목</h2>` | 빈 줄 → 제목 한 줄 → 본문 |
| `<b>강조</b>` | 강조하지 않는다. 강조가 필요하면 문장을 고친다 |
| `<p>` | 빈 줄(` *`) |
| `<ul>` / `<li>` | `-` 로 시작하는 줄 |
| `<ol>` / `<li>` | `1.` `2.` 로 시작하는 줄 |
| `<pre>` | 앞뒤 빈 줄로 감싼 들여쓴 블록 |
| `<table>` | 공백으로 열을 맞춘 평문 (한글은 2칸) |

**`{@link}` / `{@code}` 는 남긴다.** HTML 태그가 아니라 IDE에서 클릭되는 실제 참조이고,
`{@code /internal/*}`처럼 코드와 산문을 구분해 주므로 가독성을 오히려 돕는다.

## 진행 방식

`ROADMAP.md`의 Phase 단위로 진행하며, Phase 완료 시 체크박스를 갱신한다.
