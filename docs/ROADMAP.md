# 프로젝트 로드맵 — 송금/결제 시스템

## 확정된 방향
- **도메인**: 송금/결제 시스템 (계좌, 이체, 잔액 정합성, 거래 내역)
- **언어**: Java (Spring Boot)
- **지금의 최우선 목표**: **정합성과 내구성을 낮추지 않고 Choreography Saga의 SLO 용량을
  최대한 높인다.** 접수 TPS가 아니라 종결 p99·유실·중복·갇힘·대사 결과까지 함께 통과해야 한다
- **인프라**: 로컬 K8s(minikube/kind) 실제 구축 — 다만 Saga의 단일 인스턴스 병목을 충분히
  줄인 뒤로 미룬다. DB 관문이 남은 채 Pod만 늘려 대기열을 키우지 않는다
- **서비스 메시(Istio)는 범위에서 뺐습니다** — 이 시스템은 서비스 간 통신이 거의 Kafka라
  메시가 줄 수 있는 게 mTLS 정도입니다. 비용은 다 치르고 배우는 건 적어, **별도로 공부**합니다.
  판단 근거는 `DECISIONS.md`에 있습니다
- **최종 형태**: **현업에서 실제로 쓰는 구조.** 패턴을 먼저 손으로 만들어 이해한 뒤,
  검증된 기술로 갈아탑니다. 교체 대상과 시점은 `DECISIONS.md`에 있습니다.

## 커버해야 할 요구사항
- 대규모 트래픽 환경에서 발생할 수 있는 문제점
- 분산 환경에서의 데이터 정합성 보장 방법
- 시스템 과부하 상황에 대한 대응 방안
- 확장성을 고려한 아키텍처 설계

## 실제 진행 순서

**문서의 순서가 곧 진행 순서입니다. 번호는 순서가 아닙니다.**

```
0 → 1 → 2 → 3 → 5(측정) → 6(Saga 용량·정합성) → 4(Gateway) → 6.5(상대 은행) → 6.6(한도) → 7 → 8 → … → 13
                 ↑ 앞으로 당김             ↑ 종료 조건 강화                    ↑ 내용을 바꿈      ↑ 배포는 후순위
```

> **6.5·6.6은 나중에 끼운 것**이라 번호가 소수점입니다. 뒤 번호를 밀면
> `phase-N-complete` 태그와 지나간 커밋 메시지의 뜻이 달라집니다.

두 번 움직였고, Phase 6의 종료 조건과 6.5의 내용을 각각 한 번씩 바꿨습니다.

| | 무엇을 | 왜 |
|---|---|---|
| **5를 앞으로** | 측정을 고동시성보다 먼저 | 아래 "재고 나서 고친다" |
| **4를 뒤로** | Gateway를 측정·고동시성 다음으로 | 측정 경로에 계층을 하나 더 두면 병목을 가리기 어렵다 |
| **6을 깊게** | 배포보다 Saga 용량·정합성을 먼저 | K8s는 애플리케이션·DB 병목을 없애지 못한다. 수평 확장 전에 단일 흐름의 한계와 비용부터 설명한다 |
| **6.5를 상대 은행으로** | 한도 서비스 → 상대 은행 (한도는 6.6으로) | 한도는 **이미 있는 문제의 양**을 바꾸고, 상대 은행은 **없던 문제**(보냈는데 결과를 모른다)를 들여온다. 지금 입금·출금이 같은 DB라 그 상태가 아예 존재하지 않는다 |

**번호를 다시 매기지 않았습니다.** `PROGRESS.md`의 기록과 커밋 메시지, `phase-N-complete`
태그가 이미 이 번호를 쓰고 있어서, 번호를 바꾸면 **지나간 기록의 뜻이 달라집니다.**

## 순서의 원칙 — **재고 나서 고친다**

Phase 5(측정 기반)가 Phase 6(고동시성)보다 **앞에 있는 건 의도된 것**입니다.

```
❌ 캐시를 넣는다 → 나중에 부하 테스트한다      "느릴 것 같아서 넣었습니다"
✅ 부하를 걸어 천장을 잰다 → 병목을 지목한다   "X TPS에서 막혔고 원인이 Y였습니다"
   → 고친다 → 같은 시나리오로 다시 잰다        "Z로 올랐고 대신 W를 잃었습니다"
```

**숫자 없는 개선은 안 한 것과 같습니다.** 그리고 면접에서도 앞의 답변은 통하지 않습니다.
개선마다 전후 숫자를 `DECISIONS.md`에 남깁니다.

CI는 `.github/workflows/build.yml` 하나가 이미 돌고 있습니다(actionlint + JDK 21 + `./gradlew build`).
아래 셋은 **뒤 Phase의 전제**라 늦어지면 곧바로 발목을 잡습니다.

- [x] **빌드가 자기 커밋을 알게 하기** — `bootBuildInfo`로 커밋·브랜치·빌드 시각을 새겨
      `GET /actuator/info`가 답하게 했습니다.
      > 원래 계획은 "Gradle 버전을 커밋 SHA로"였는데 **바꿨습니다.** 아티팩트 버전은 *제품* 버전이고,
      > "지금 떠 있는 게 어느 커밋이냐"는 **실행 중인 프로세스에 물어봐야** 답이 됩니다.
      > 이미지 태그는 Phase 7에서 `github.sha`를 그대로 씁니다. 근거는 `DECISIONS.md`
- [x] **브랜치 보호** — `main`에만 걸었습니다. PR 필수 + CI(`unit`/`build`/`lint-workflows`)
      통과 필수 + force push·삭제 금지. **승인자는 0명**(혼자라 1명 이상이면 자기 PR을 자기가
      승인 못 해 잠깁니다), **관리자 우회는 허용**(실수는 막고 의도적 우회는 열어둠).
      `develop`은 통합 브랜치라 자유롭게 뒀습니다.
      > Phase 2·3을 e2e 없이 `main`에 올렸다가 되돌린 적이 있습니다. 이제 실수로는 안 됩니다
- [x] **테스트 분리** — `./gradlew unitTest`(Docker 불필요, **9초 / 331건**)와
      `./gradlew test`(전체, 1분 43초 / 431건)로 갈랐습니다.
      CI는 `unit` → `build` 순으로 돌아, 오타 하나 때문에 컨테이너를 띄우지 않습니다
- [x] **Gradle 캐시가 실제로 채워지게** — `setup-gradle`는 기본 브랜치가 아니면 캐시를
      **읽기만** 합니다(`cache-read-only: true`). 그런데 이 저장소는 작업이 거의 `develop`에서
      일어나므로, **캐시를 켜뒀는데 작동하지 않는 상태**였습니다. `develop`에서도 쓰게 열었습니다
- [ ] **CI 시간 단축 — Phase 7에서 한다** ⏭️
      지금은 5분이고 **아무것도 막지 않습니다.** Phase 6의 반복 루프는 CI를 거치지 않고
      (`HOMELAB.md`의 rsync → 빌드 → 재기동, 약 1분), CI는 푸시 뒤에서 돌 뿐입니다.
      **Phase 7에서 이미지 빌드·푸시·Trivy가 붙으면 그때 실제로 아픕니다.**
      숫자가 아플 때 고치는 게 이 저장소의 원칙이라 그때로 미룹니다.

      2026-08-22 실측 (총 5분, 오버헤드는 10초뿐이라 전부 Gradle에 있음):
      | 대상 | 시간 | 손댈 방법 | 예상 |
      |---|---|---|---|
      | `build` 잡의 모듈별 테스트 (순차) | account 61s · transfer 45s · ledger 39s · notification 30s · reconciliation 20s = **196s** | `org.gradle.parallel=true` | 80~100초. **컨테이너를 동시에 여러 벌 띄우므로 안정성 검증 필요** |

      | `build`가 `needs: unit`이라 직렬 | 52s | `needs` 제거 | 52초. 대가는 오타에도 컨테이너가 뜨는 것 (공개 저장소라 러너 시간은 무료) |
- [ ] (선택) **변경된 모듈만 빌드** — 모노레포인데 `notification-service`만 고쳐도 5개를 다 돌립니다

      **첫 번째가 맞았고 나머지는 전부 2ms 아래였다.**
      - [x] **내부 구간별 계측** — 처리 흔적 flush, 잔액 조회·flush, Outbox enqueue,
            지연 쓰기+commit을 Timer로 분리했다. 정상 commit과 중복 rollback도 따로 센다.
            Grafana 패널과 통합 테스트까지 완료 (`d51449e`)
      - [x] 홈서버 60 TPS에서 구간별 p95를 채웠다 — **지연 쓰기+commit이 평균 47.8ms,
            p95 102.3ms로 전체 평균의 91.3%**. 나머지는 전부 평균 2ms 아래.
            출금도 거의 같다(48.4ms) — **입금만의 문제가 아니다** (`07d741c`).
            ⚠️ 처음 잰 값(`ccef131`)은 MySQL에 실험용 `binlog_group_commit_sync_delay=1000`이
            켜져 있는 줄 모르고 잰 것이라 버렸다. 앱 커밋 해시는 확인했는데 **DB 설정은 아무도
            확인하지 않았다** — 서버 설정을 손으로 바꿨으면 되돌리는 것까지가 실험이다
      - [x] MySQL 부하 전후 delta로 group commit 확인 — **이미 잘 뭉치고 있다.**
            커밋 565/s에 로그 fsync 103/s = **5.5건당 1회**, `Innodb_log_waits=0`.
            그래서 47.8ms는 fsync 한 번의 값이 아니라 **줄 서 있는 시간**이다
            (565 × 47.8ms = 항상 27개 스레드가 커밋 안에 있다)
      - [x] **~~그룹 커밋 지연 튜닝~~ — 죽은 레버.** `delay=1000µs`로 더 뭉치게 하니
            종결 p99가 3,354 → **3,792ms로 나빠졌다.** 이미 뭉치고 있어서 지연만 더해진다
- [x] **접수를 한 트랜잭션으로 합쳤다** ✅ — `transfer_db` **6.05 → 5.06회** (`7db3622`).
      "송금은 커밋됐는데 키에는 안 적힌" 실패 모드도 함께 사라졌다.
      **그런데 용량은 그대로 60 TPS다** — 12회 중 1회는 8%라 재현 편차(3,130~4,376ms)에 묻힌다.
      **커밋 하나로는 안 되고 자릿수를 바꿔야 한다**는 것을 배웠다
- [x] **측정 스크립트가 판정까지 한다** — 부하 → 중단 → Kafka·Outbox drain →
      정식 대사 1회 → **지연·회복·정합성 셋을 모두** 본다.
      ⚠️ 처음엔 지연을 빼먹어서 70 TPS(p99 11.7초)를 "✅ 통과"라고 찍었다.
      k6를 파이프로 넘겨 **종료 코드를 잃어버린** 것이 원인이다
- [x] **알림의 커밋을 반으로 줄였다** ✅ — 한 소식의 알림 둘을 한 트랜잭션으로 (`51bdc3c`).
      `notification_db` 28,781 → 14,488커밋, 송금당 총 **11.07 → 9.12회**.
      **그런데 용량이 1건도 안 움직였다**(70 TPS p99 11,613 → 11,789ms) —
      커밋 수가 진짜 제약이 아니라는 신호였다
- [x] **redo log 100MB → 1GB** ✅ — **용량 60 → 70 TPS** (`dc4d0a5`).
      fsync를 직접 재보니 2.9ms로, 커밋 32.5ms의 9%뿐이었다. 나머지를 찾다가
      MySQL 설정이 회전 디스크 기본값인 것을 봤다. 넷을 바꾼 뒤 하나씩 되돌려 가르니
      **redo 하나가 전부**였다(`io_capacity`는 원인 아님).
      커밋마다 redo를 쓰는데 100MB가 금방 차고, 차면 체크포인트가 커밋을 붙잡는다.
      **총량이 아니라 용량이 문제**였으므로 커밋 수를 줄여도 안 줄었던 것이다.
      내구성은 그대로다 — redo 크기는 체크포인트 주기이지 커밋의 의미가 아니다
- [x] **80 TPS에서 왜 멈추는가 — 답을 찾고 여기서 멈춘다** (2026-08-26)

      | | 값 |
      |---|---:|
      | 입금 리스너 건당 | **60.7ms** × 6스레드 = **상한 99건/s** |
      | 그중 지연 쓰기+commit | 38.1ms (**63%**) |
      | 80 TPS의 가동률 | **81%** → 대기행렬이 부푼다 |

      **더 가려면 둘 중 하나다.** 스레드를 더 늘리거나(파티션 6 → 12),
      건당 60.7ms를 줄이거나. 그런데 **앞엣것은 이미 해봤고 수확이 줄었다** —
      3 → 6에서 건당 시간이 52.5 → 80ms로 함께 늘어 1.2배밖에 못 얻었다.
      뒤엣것은 63%가 커밋이라 **커밋을 자릿수로 줄여야** 하고, 그건 Saga의
      트랜잭션 경계를 다시 긋는 일이라 **Phase 6의 범위를 넘는다**
- [ ] ~~알림 커밋 배경~~ — 커밋 전체의 **35.5%**를 알림이 썼다
      (알림 2건 × 선점+발송). 그런데 **알림은 종결 경로가 아니다** —
      잎사귀가 같은 MySQL 커밋 관문을 35.5% 쓰고 있다. 지금 가장 큰 덩어리다
- [ ] ~~송금 1건당 커밋 10.5회를 줄인다~~ — 실제로는 **12.05회**였다(알림 lag 때문에 덜 세어졌다).
      지금은 **11.07회**.  아래는 원래 적어둔 배경이다. 커밋 하나가 47.8ms짜리 관문을

- [x] **~~내구성 트레이드오프~~ — 보지 않는다.** `sync_binlog=0`이나

## Phase 6.5. 상대 은행(external bank) — **Kotlin으로 만든다**

> **원래는 한도 서비스였습니다** (2026-08-26에 바꿈). 왜 바꿨는지는 아래 "왜 한도가 아니라
> 상대 은행인가"에 있습니다. 한도 서비스는 **지우지 않고 Phase 6.6으로 미룹니다** —
> 나쁜 아이디어라서가 아니라 지금 더 급한 구멍이 있어서입니다.

### 지금 시스템에 없는 것

**지금은 입금과 출금이 같은 `account-service`, 같은 DB에서 일어납니다.**
그래서 "받는 계좌"는 사실상 같은 트랜잭션 옆자리이고, 송금이라기보다 **한 은행 안의 계좌 이체**입니다.

실제 송금은 상대가 **우리가 제어할 수 없는 남**입니다. 그러면 이런 일이 생깁니다.

```
입금 요청 전송  ─▶  타임아웃
                     들어갔나? 안 들어갔나?
```

**이 상태가 지금 저장소에 존재하지 않습니다.** 그리고 이건 실제 송금 시스템에서 가장 어려운
부분입니다 — 재시도하면 이중 입금이고, 실패로 처리하면 돈이 사라집니다.
**답은 재시도가 아니라 조회**입니다.

### 왜 한도가 아니라 상대 은행인가

| | 한도 서비스 | **상대 은행** |
|---|---|---|
| 새로 생기는 것 | 홉이 하나 늘어난다 | **결과를 모르는 상태** |
| 문제의 성격 | 이미 있는 문제(지연·용량)의 **양** | **종류가 다른 문제** |
| Kotlin의 명분 | "한도 로직에 `when`이 잘 맞아서" | **"남이 만든 시스템이니까"** |

앞의 것은 *"그럼 Java로 못 쓰나요?"*를 받습니다. 뒤의 것은 질문 자체가 안 나옵니다 —
**다른 조직의 시스템이 다른 언어인 건 설명이 필요 없고, 그게 MSA에서 언어를 섞는 진짜 이유입니다.**

### 부르는 방식은 HTTP 동기 (2026-08-26 결정)

| 후보 | 판단 |
|---|---|
| **HTTP 동기 + 타임아웃** | ← 채택. **"보냈는데 결과를 모른다"가 진짜로 생긴다.** 실제 은행 인터페이스에 가깝다 |
| Kafka 이벤트 | 지금 구조와 일관되지만 **외부 조직과 토픽을 공유하는 건 현실적이지 않고**, 브로커가 재전송을 책임져 불확실성이 사라진다 — 이 작업을 하는 이유가 없어진다 |

### 계약

```
POST /transfers/{transferId}/credit    입금 요청. 멱등성 키는 transferId
     → 200 { status: ACCEPTED | REJECTED, reason }
     → 응답 없음(타임아웃) / 5xx / 느린 응답

GET  /transfers/{transferId}           거래 조회 — 타임아웃 뒤에 결과를 확인하는 유일한 방법
     → 200 { status: ACCEPTED | REJECTED | NOT_FOUND }
```

**멱등성이 우리 손을 떠납니다.** 지금까지는 우리 DB의 unique 제약이 중복을 막았지만,
상대 은행에는 우리가 제약을 걸 수 없습니다. **상대가 `transferId`로 막아준다고 믿어야 하고,
그 믿음 자체가 계약입니다.** 이게 서비스 경계를 넘는 멱등성의 실제 모습입니다.

### 일부러 나쁘게 굴어야 한다 ★

**이걸 안 하면 그냥 홉 하나 늘어난 한도 서비스와 똑같아집니다.** 상대 은행 쪽에 스위치를 둡니다.

| 스위치 | 무엇을 만들어내나 |
|---|---|
| `latency` | 느린 상대. 우리 스레드가 묶인다 → Bulkhead의 근거 |
| `timeoutRate` | **결과를 모르는 상태.** 이 작업의 핵심 |
| `errorRate` (5xx) | 재시도해도 되는 실패 |
| `rejectRate` | 업무적 거절(계좌 없음 등) — 재시도하면 안 되는 실패 |

**세 가지 실패를 구분하는 것**이 이 Phase의 진짜 내용입니다.
지금 시스템은 실패가 한 종류(업무적 실패)뿐이라 그 구분을 연습할 자리가 없었습니다.

### 우리 쪽에 생기는 것

- [ ] `Transfer`에 **`CREDIT_UNKNOWN`** — 보냈는데 결과를 모르는 상태.
      **여기서 재요청하면 안 된다.** 조회부터 한다
- [ ] **조회 기반 확인 루프** — 타임아웃 난 건을 주기적으로 `GET`으로 물어본다.

## Phase 8. Kubernetes 배포
- [ ] **🔁 단일 인스턴스 전제의 `@Scheduled` → 중복 실행 방지** — replica가 늘면 Outbox 릴레이와 EOD 대사가

      **다만 둘에 같은 처방을 쓰면 안 됩니다** (2026-08-23에 갈라 적음):
      - **EOD 대사 배치 → ShedLock.** 처리량이 필요 없으니 **기준 시각마다 리더 하나만 돌면 충분**합니다
      - **Outbox 릴레이 → `SELECT ... FOR UPDATE SKIP LOCKED`** (또는 ID 샤딩).
        여기에 ShedLock을 쓰면 **릴레이가 1대분으로 묶여**, Phase 6에서 올려놓은 발행 처리량을

- [ ] **리스너 `concurrency`를 인스턴스 수와 함께 다시 계산한다.**

      **스레드 9개가 파티션 3개를 두고 경합**해 6개는 놉니다.
      **파티션을 먼저 늘리거나 인스턴스당 `concurrency`를 낮춰야** 합니다 —
      스케일 아웃이 처리량으로 이어지지 않는 대표적인 함정입니다
- [ ] minikube 또는 kind로 로컬 클러스터 구성
- [ ] 서비스별 Deployment/Service/ConfigMap/Secret manifest 작성
- [ ] **Kustomize로 환경별 차이 관리** (Helm보다 배우기 쉽고 K8s 네이티브)
- [ ] **🆕 ArgoCD 설치 — 여기서 처음으로 CD가 생깁니다**

### Istio는 왜 뺐나

**적용할 자리가 거의 없어서**입니다. 이 시스템은 서비스 간 동기 호출이 사실상 없습니다
(대사의 읽기 전용 조회 하나뿐). 그래서:

| Istio가 주는 것 | 여기서는 |
|---|---|
| 트래픽 분할·카나리 | 나눌 **서비스 간** 트래픽이 없음 |
| 재시도·타임아웃·회로 차단 | **Kafka 컨슈머에는 안 걸림.** 이미 `DefaultErrorHandler`로 처리 중 |
| 분산 트레이싱 | **Kafka를 건너면 끊김.** 애플리케이션에서 trace context를 이벤트에 실어야 함 |
| mTLS | 이건 됨 — 얻는 게 사실상 이것뿐 |

**설계가 잘못된 게 아니라 도구가 안 맞는 것**입니다. 비동기 이벤트 중심으로 간 건 Phase 2의
의도된 선택이고, Istio는 서비스들이 서로 HTTP/gRPC로 부르는 구조에서 빛납니다.

> ⚠️ **Istio를 쓰려고 동기 호출을 일부러 만들면 안 됩니다.** 아키텍처를 도구에 맞추는 건
> 거꾸로이고, 면접에서 "왜 이벤트 기반인데 동기 호출이 있죠?"로 되돌아옵니다.

리소스도 현실적인 벽입니다. Phase 8~9쯤이면 서비스 5개 + 인프라 + Prometheus/Grafana + ArgoCD가
동시에 떠 있어야 하는데, 여기에 사이드카와 istiod까지 붙으면 **16GB로도 빠듯**합니다.

- [ ] Istio는 **별도 프로젝트로 학습** — 동기 호출이 많은 작은 샘플에서 하는 편이 훨씬 잘 보입니다

## 진행 방식
